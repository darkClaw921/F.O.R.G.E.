# cancelledByScroll

cancelledByScroll(prevTop, nextTop, threshold?) -> boolean (tmux-web/static/js/telegram/follow.js) — отменил ли пользователь «следование» собственной прокруткой вверх.

ЛОГИКА: `prev - next > threshold`, где threshold по умолчанию FOLLOW_CANCEL_UP_PX (24px). То есть true только при движении ВВЕРХ и только сверх порога. Оба значения через `Number(...) || 0`, threshold через Number.isFinite.

РЕШЕНИЕ ПО НАПРАВЛЕНИЮ, А НЕ ПО ФЛАГУ «ЭТО СКРОЛЛИЛ Я». Присваивание scrollTop (и вызов scrollTo) порождает событие `scroll` АСИНХРОННО — синхронный флаг «сейчас двигаю сам» успел бы сброситься до доставки события, и собственный доскролл гасил бы собственное же следование. Направление такой гонки не имеет: scrollTargetForRow никогда не тянет вверх, значит все автоматические движения УВЕЛИЧИВАЮТ scrollTop и под условие не попадают в принципе.

ПОЧЕМУ ПОРОГ, А НЕ ЛЮБОЕ УМЕНЬШЕНИЕ: инерционная прокрутка и «подпрыгивание» ленты при смене высоты полосы reply-клавиатуры дают отскок в единицы пикселей — по правилу «любое уменьшение» следование гасло бы сразу после включения.

ПОТРЕБИТЕЛЬ: chat.js::bindScroll — на каждом событии scroll сравнивает local.lastScrollTop с текущим scrollTop и при true зовёт stopFollow(); затем безусловно обновляет local.lastScrollTop. Начальное значение lastScrollTop берётся в момент привязки обработчика.

СВЯЗАННЫЕ: FOLLOW_CANCEL_UP_PX, scrollTargetForRow (гарантия «только вниз»), chat.js::stopFollow.

ТЕСТЫ: telegram_follow.test.mjs секция «Отмена ручной прокруткой» (граница ровно 24px не отменяет, 25px отменяет, движение вниз не отменяет никогда), telegram_scroll_edge.test.mjs — секция «дребезг против настоящего ухода вверх».
