# portalPrefs

js/bitrix/visibility.js::portalPrefs(settings, portalId) и normalizeFilter(settings, portalId) — фронтовая сторона пер-портальных настроек Битрикса (Ф7.4).

МОДУЛЬ ОСТАЁТСЯ ЧИСТЫМ. portal_id приходит АРГУМЕНТОМ: читай visibility.js активный портал сам, он знал бы про api.js, а его node-тест — про сеть. Покрытие — tmux-web/tests/frontend/bitrix_visibility.test.mjs (116 ассертов).

ЭКСПОРТЫ: PORTAL_PREFS_KEY ('bitrix_portal_prefs'), portalPrefs(settings, portalId) -> запись из пяти полей в терминах КАРТЫ (одна форма и для карты, и для плоских ключей — вызывающий не ветвится), portalPrefsPatch(portalId, fields) -> тело PATCH; normalizeFilter вторым аргументом принимает портал. Правило чтения — как у хоста (см. bitrix_portal_prefs).

ЧЕТЫРЕ ТОЧКИ ПРИМЕНЕНИЯ теперь спрашивают настройки СВОЕГО портала:
  1-3 (колонка dialogs.js::visibleSource, счётчики renderDirs, бейдж main.js::recomputeUnread) — через state.js::currentVisibilityFilter(portalId), умолчание = activePortal() из api.js (а не b24State: clearB24AccountData обнуляет состояние ровно в момент переключения портала). Кэш разбора стал картой ПО ПОРТАЛАМ — одна ячейка пересобиралась бы на каждом чередовании своих и чужих кадров.
  4 (тосты main.js::maybeToast) — фильтр ПОРТАЛА КАДРА.

СНЯТОЕ ОГРАНИЧЕНИЕ Ф8. Раньше тост чужого портала при действующем фильтре подавлялся всегда. Теперь подавление осталось ровно в одном узком случае: фильтр ТОГО портала действует, диалог не отмечен в нём поимённо, а вид диалога из DIALOG_ID у Битрикса не выводится (chat7 — и групповой чат, и чат задачи, различает entity_type). Фоновый портал без настроек тостит свободно; поимённо отмеченный диалог тостит без загруженного списка. Полного кэша состояния на портал нет и не будет — это осознанное ограничение панели.
