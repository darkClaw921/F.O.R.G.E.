# renderHistory

renderHistory(messages, dialog) (tmux-web/static/js/telegram/chat.js, внутренняя) — рисует страницу истории в #tg-log: разделители дат, строки сообщений, индекс local.rows.

ПОРЯДОК: resetMediaCards() → цикл по сообщениям (needsDateSep ⇒ buildDateSep; buildMessageRow; appendChild; local.rows.set) → applyHistoryKeyboard(messages) → ВОССТАНОВЛЕНИЕ ПОДСВЕТКИ по local.flashId → ВОССТАНОВЛЕНИЕ НАБЛЮДЕНИЯ за ростом строки.

ПОЧЕМУ ВНИЗУ ФУНКЦИИ ТРИ «ВОССТАНОВЛЕНИЯ» ПОДРЯД — у них одна причина: renderHistory перерисовывает ленту ЦЕЛИКОМ, все узлы пересоздаются, и всё, что было привязано к УЗЛУ, обязано быть переставлено заново.
 * applyHistoryKeyboard — reply-клавиатура пересчитывается ПО ВСЕЙ ленте, а не накапливается по событиям: страница истории вверх приносит СТАРЫЕ сообщения, а актуальной обязана остаться клавиатура из самого нижнего сообщения бота;
 * подсветка живёт по id, а не по узлу: переход к оригиналу сам вызывает подгрузку истории, и без переприменения класс исчезал бы ровно в тот момент, когда пользователь его ждёт;
 * НАБЛЮДЕНИЕ ЗА РОСТОМ (добавлено при исправлении дефекта автопрокрутки): `const follow = followTarget(Date.now()); if (follow && follow.messageId) observeFollowRow(local.rows.get(follow.messageId) || null);` — ResizeObserver, оставшийся на старом узле, молча замолчал бы навсегда, и добор отложенного роста перестал бы работать после первой же подгрузки истории.

УСЛОВИЕ `follow.messageId` НЕ СЛУЧАЙНО: при следовании за диалогом целиком (messageId===0, кнопка reply-клавиатуры) наблюдать нечего — конкретной строки нет, и доскролл идёт через onNewMessage.

ГДЕ ЗОВЁТСЯ: openDialog (первая страница) и loadOlder (подгрузка вверх, с якорем по scrollHeight). В обоих случаях local.loading === true на момент вызова, поэтому поставленное здесь наблюдение начнёт двигать ленту только после снятия флага — гард стоит в scrollBlockIntoView.

СВЯЗАННЫЕ: follow.js::followTarget, observeFollowRow, clearLog (снимает наблюдение перед перерисовкой), botkb.js::applyHistoryKeyboard.
