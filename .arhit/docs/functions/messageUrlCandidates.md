# messageUrlCandidates

messenger/meet-core.js::messageUrlCandidates(msg, panel) — все адреса-кандидаты сообщения в том порядке, в каком их видит человек. panel: 'telegram' | 'vk' | 'bitrix'; любое другое значение — режим «всё сразу», чтобы новая панель работала до того, как её здесь пропишут.

ИСТОЧНИК ТЕКСТА В КАЖДОЙ ПАНЕЛИ РАЗНЫЙ, и это неочевидно — ошибка здесь выглядит как «кнопка не появляется на некоторых сообщениях», то есть как случайность.

TELEGRAM — только msg.text. Приватная messageText() из telegram/chat.js:626 НЕ ГОДИТСЯ: она подмешивает '[photo]' и '[voice 7s]', то есть кладёт в детект мусор. Здесь она просто не вызывается.

VK — msg.text ПЛЮС вложения. VK регулярно выносит адрес из текста в отдельное вложение, и на самом типовом сообщении со ссылкой текст оказывается пустым. Две формы вложения, обе живые: (а) ОСНОВНАЯ — нормализованный MediaDto, у которого kind='other' (plugins/vk/src/attach.rs схлопывает сырой тип 'link' в 'other'), а адрес лежит в link_url; (б) сырое вложение VK type='link' с адресом в link.url — так приезжают кадры WS, собранные предыдущей версией плагина. ВНИМАНИЕ: план фазы говорит «вложения kind === "link"», и в живых данных это НЕ ТАК — проверять надо link_url.

БИТРИКС — обход msg.segments через collectUrlsFromSegments; msg.text используется только как запасное поле кадров без дерева (по образцу bitrix/chat.js: segmentsText(...) || msg.text).

Порядок: текст, затем вложения (VK), либо порядок сегментов (Битрикс). detectMeetInMessage берёт ПЕРВУЮ подошедшую встречу, а не «лучшую»: выбор между двумя ссылками по приоритету платформ был бы для человека непредсказуемым.
