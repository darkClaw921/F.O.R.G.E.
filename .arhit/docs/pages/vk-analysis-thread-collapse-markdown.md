# Анализ чата VK: тред на бэкенде, сворачивание разбора, Markdown (эпик C, АЧ-И2)

Доработка родилась из трёх жалоб живого использования.

## 1. «После обновления страницы история вопросов пропадает»

До доработки local.thread (js/vk/analysis.js) наполнялся ТОЛЬКО своими ответами и умирал вместе со страницей. Теперь тред хранится на сервере рядом с разбором и заметкой беседы (plugins/vk/src/analysis/prompts.rs, ChatPrompt.thread: Vec<QaTurn>), приезжает полем thread ответа GET /api/vk/dialogs/:id/analysis и рисуется при открытии попапа и при смене беседы.

Почему на бэкенде, а не в localStorage: разбор уже там, и разъезд «разбор виден со второго устройства, а вопросы к нему — нет» выглядел бы поломкой. Плюс тред уезжает модели полем history — источник истины должен быть один.

Дедупликации не потребовалось: renderThread() перерисовывает список целиком из local.thread, а свои свежие пары дописываются в тот же список. Сравнивать DOM с массивом пришлось бы по содержимому (у пар нет id), и первая же расхожая пара дала бы дубль.

ДВА ЛИМИТА, И ОНИ РАЗНЫЕ НАМЕРЕННО:
- clampThreadForView / MAX_THREAD_TURNS = 12 — сколько пар ПОКАЗЫВАЕМ и помним (зеркало сервера);
- clampThread / MAX_HISTORY_TURNS = 6, MAX_HISTORY_CHARS = 8000 — сколько уезжает модели.
Помним больше, чем отправляем: контекст модели дорог, история пользователя — нет. Обрезать показанное по бюджету промпта значило бы стирать с экрана вопросы, которые сервер прекрасно хранит.

## 2. Две очистки, два адреса

CLEAR ✕ — DELETE /api/vk/dialogs/:id/analysis (разбор; тред цел).
CLEAR Q&A — DELETE /api/vk/dialogs/:id/analysis/thread (тред; разбор цел).

Отдельный путь вместо ?thread=1 выбран потому, что query-параметры в этом плагине разбираются вручную через RawQuery: Query<T> ломает auth-лестницу маршрута. Побочная выгода — независимость стала буквальной: кнопки физически не могут стереть чужое.

Обе кнопки правят экран ТОЛЬКО по успеху сервера. Обратный порядок при упавшем запросе показал бы пустоту вместо целых данных, и пользователь узнал бы правду лишь при следующем открытии попапа.

## 3. Сворачивание — только блок разбора

Сворачивается РОВНО #vk-analysis-out. Метка «разобрано до …», строка статуса и тред лежат снаружи сворачиваемого узла: свёрнутый разбор не должен уносить с экрана то, ради чего его и сворачивают.

Состояние ГЛОБАЛЬНОЕ (localStorage, ключ vk.analysis.collapsed), а не на беседу — это привычка смотреть в вопросы, а не свойство конкретного чата. Чтение и запись обёрнуты try/catch: хранилище умеет бросать и на чтении (Safari private mode), а падение на верхнем уровне оставило бы попап без единого обработчика.

Старт ANALYZE и REFRESH разворачивает блок ПРИНУДИТЕЛЬНО и запоминает это. Иначе дельты текли бы в невидимое, и пользователь смотрел бы на пустой экран, считая, что сломано.

## 4. Markdown рисуется по analysis_done, а не на каждой дельте

Во время стрима блок показывает сырой текст (white-space: pre-wrap), и только по кадру analysis_done содержимое перерисовывается деревом (renderMarkdownInto -> js/messenger/markdown.js). Причина: парсить незакрытую разметку на каждой дельте — это и мерцание, и лишняя работа восемь раз в секунду (сервер коалесцирует дельты по 120 мс / 400 символов).

Перерисовывается только ЦЕЛЫЙ ответ (ok && reason === null). У оборванного (отмена, таймаут, ошибка) незакрыты таблицы и списки, и «дорисовать» их значило бы показать структуру, которой модель не писала.

Сохранённый разбор и ответы треда из GET — уже целые тексты, поэтому рисуются Markdown'ом сразу, без стадии сырого текста. Вопрос пользователя остаётся текстом: его писал человек в однострочном поле, а звёздочки и решётки в живом вопросе встречаются чаще, чем разметка.

Отдельного накопителя сырого текста НЕ заводили: источник — textContent блока после синхронного слива буфера. Это ровно тот текст, который сервер положил себе в хранилище. Важная тонкость: сырой ответ для history снимается ДО перерисовки — после неё textContent вернул бы текст без символов разметки, и в историю модели уехал бы ответ, которого она не давала.

Инвариант «никакого innerHTML в js/vk/*» не задет: markdown.js строит узлы через createElement/createTextNode, ссылки пропускает только со схемами http/https (проверка через new URL), запрещённые оставляет обычным текстом.
