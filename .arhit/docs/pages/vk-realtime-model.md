# Модель realtime плагина VK

Как событие ВКонтакте становится строкой в ленте devforge, и почему именно так.

## Шесть решений, которые определяют всё остальное

### 1. Обогащение пачки одним запросом, а не запросом на сообщение

Событие 4 приезжает урезанным. Три пути рассматривались:

- разбор плоских полей attach1_type / attach1 — ОТВЕРГНУТ: второй параллельный
  парсер второго недокументированного формата, физически не отдающий
  fwd_messages, reply_message, action, keyboard. Кадр new_message начал бы
  расходиться по полноте с GET /messages, и фронт получил бы «мигающие»
  карточки при reconcile;
- messages.getById на каждое событие — ОТВЕРГНУТ: один запрос на СООБЩЕНИЕ.
  При бюджете 3 rps залп из десяти сообщений съедает три секунды бюджета,
  начинает генерировать код 6, а троттлер принимается задерживать
  интерактивные запросы пользователя ради фоновой доставки;
- messages.getLongPollHistory(ts, pts) — ВЫБРАН: один запрос на ПАЧКУ
  независимо от числа событий, полноценные объекты сообщений плюс
  profiles/groups (бесплатно закрывает резолв имён), new_pts как курсор.

Условие работоспособности: need_pts=1 И бит 32 в mode. Это не две опции, а одна
пара — без pts метод вызвать нечем.

Деградация: код 10 или иная ошибка -> getById не более чем на
MAX_FALLBACK_GETBYID = 3 сообщений, остаток закрывается кадром resync.

### 2. Холодного catch-up нет и изображать его нельзя

getLongPollHistory с ts старше суток отвечает кодом 10. Прямого аналога
телеграмному catch_up (pts-догон за офлайн-период) VK не даёт. На старте берётся
свежий ts и поток идёт «с сейчас»; история беседы подтягивается обычным
messages.getHistory при её открытии. Сохранённый курсор нужен только для тёплого
догона ВНУТРИ суток — перезапуск процесса, обрыв связи.

Отсюда PersistedCursor { cursor, saved_at }: ts LongPoll — это ВНУТРЕННИЙ
счётчик событий VK, а не unix-время, и без отметки времени записи нельзя понять,
протух ли курсор. Протухший выбрасывается ПРИ ЗАГРУЗКЕ, иначе код 10 приходил бы
на каждом цикле и поток не поднялся бы никогда.

### 3. failed:2 не берёт ts из ответа

Дословно по протоколу: failed:1 -> взять ts из ответа, ключ прежний;
failed:2 -> перезапросить getLongPollServer, но ts СВОЙ сохранить;
failed:3 -> перезапросить всё, курсор сбросить, послать resync.

Смысл второй ветки: пока ключ протухал, на сервере копились события, и ts из
свежего ответа указывает на «сейчас». Взяв его, мы молча потеряли бы всё
накопленное, и заметно это стало бы только у пользователя. Проверяется
интеграционным сценарием на стенде (последовательность ts = 100, 101, 101 при
ts из свежего ответа = 500).

### 4. Событие LongPoll — массив, а не объект

[4, 7011, 17, 2000000001, 1800000000, "привет", {...}]. Позиции зависят от кода.
Неизвестный код становится LpEvent::Unknown(code) с warn и игнорируется — ровно
то же правило, что у битого WS-кадра во фронте: новая фича VK не имеет права
сломать realtime целиком.

Два места, где нумерация не совпадает с peer_id: события 51 и 62 несут НОМЕР
беседы, к нему прибавляется CHAT_PEER_BASE. У событий 8/9 id друга приходит со
знаком минус. У 63/64 порядок from_ids и peer_id в разных версиях документации
описан по-разному, поэтому разбор идёт по ТИПУ элемента, а не по позиции.

### 5. Три новых кадра WS и два удалённых

+ unread_total{count} — событие 80: VK отдаёт общий счётчик готовым, и бейдж
  перестаёт быть суммой по загруженной странице списка;
+ history_cleared{dialog_id, up_to_id} — событие 13: id удалённых сообщений VK
  не присылает, только границу, поэтому message_deleted неприменим;
+ dialog_changed{dialog_id} — события 51/52.
- notify_defaults_changed — глобальных категорий mute у VK нет, глушение только
  per-peer;
- folders_changed — папок нет, их место заняли 4 серверных фильтра.

download_progress получает поле index: у сообщения VK до 10 вложений.

### 6. Ветки выхода воркера без реконнекта

Код 5 (токен отозван) -> on_auth_invalidated, реконнекта НЕТ: следующий виток
только после нового токена. Код 15 (нет права messages) -> on_scope_lost, то же
самое. Код 14 -> on_captcha, пауза до POST /api/vk/captcha. Всё остальное ->
backoff [1,2,5,10,30,60] со сбросом после успешного цикла.

spawn вызывается ВСЕГДА, даже без токена: воркер сам ждёт авторизации на
authorized_notify, поэтому вставка токена в работающем процессе поднимает
realtime БЕЗ рестарта devforge. notified().enable() обязан стоять ДО проверки
состояния — иначе токен, вставленный в этом окне, подвесит воркера до следующего
тика. Гонка шириной в несколько инструкций тестом по времени не ловится (между
чтением состояния и подпиской нет точки отмены), поэтому инвариант проверяется
ПО ИСХОДНИКУ: wait_authorized_subscribes_before_it_checks_the_state.

## Фронтовая половина

main.js::recomputeUnread — единственный путь обновления бейджа. Серверный
счётчик имеет приоритет над локальной суммой по загруженной странице; поправка
unreadSinceServer (множество БЕСЕД, а не сообщений) закрывает щель между
приходом сообщения и приходом события 80.

maybeToast — гейты «не своё / не заглушено / проходит белый список / не активная
беседа при открытой вкладке / троттлинг 5 с» и заголовок «VK · имя»: при двух
включённых панелях тосты падают в один стек #echo-toasts, и без префикса
пользователь не поймёт, куда его зовут. Канал уведомлений один —
js/echo/notifications.js::notify.

typing держится на TTL: VK не присылает «перестал печатать», он просто перестаёт
слать событие.
