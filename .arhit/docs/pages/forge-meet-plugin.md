Состояние на 18.08.2026: закрыты фазы 0-7 и 11, все фронтовые.
Ф8-Ф10 (Google Meet, Teams, Zoom) прогнаны, но НИ ОДНА ЗАДАЧА НЕ ЗАКРЫТА: живых встреч и

ЧТО ЭТО
Ссылка на встречу в ленте Telegram/VK/Битрикса -> кнопка -> бот в своём Chrome входит во встречу,
пишет пер-трековый звук -> ffmpeg сводит -> whisper.cpp расшифровывает -> имена спикеров -> Claude
делает саммари. Отдельный плагин, а не общий крейт с мессенджерами: зависимости нет ни по одному
направлению, ссылку приносит фронт, имена берутся из самой встречи.

ПЯТЬ РЕШЕНИЙ, ОПРЕДЕЛЯЮЩИХ ВСЁ ОСТАЛЬНОЕ (из плана)
1. ЗВУК ИДЁТ ЧЕРЕЗ CDP-БИНДИНГ, А НЕ ЧЕРЕЗ НАШ HTTP-СЕРВЕР. Runtime.addBinding ->
   window.__forge_<rand32> -> Runtime.bindingCalled. Между инжектом и сервером стоят четыре барьера
   (csrf_guard по Origin, Bearer-auth, connect-src в CSP, Private Network Access), и биндинг убирает
   их разом, потому что убирает сеть. Роут /ws/meet/ingest НЕ СОЗДАЁТСЯ НИКОГДА — это записано
   строкой в таблице роутов и закреплено тестом: исключение в csrf_guard по одноразовому токену
   превратило бы плагин записи встреч в drive-by RCE (токен лежит в памяти страницы, которой мы ещё
   и CSP отключили, а через главный сокет достижим /ws/attach, то есть терминал).
2. ПО ПРОВОДУ ИДЁТ ПЕР-ТРЕКОВЫЙ PCM16 16 кГц МОНО. Пер-трековый — потому что это и есть ответ на
   «кто говорит». PCM, а не Opus/WebM — потому что PCM адресуется СЭМПЛОВЫМ СМЕЩЕНИЕМ: потерянный
   чанк оставляет тишину, а не ломает хвост файла, и вся обвязка вокруг хрупкости контейнера
   исчезает. Побочно: whisper хочет ровно 16 кГц моно, то есть ffmpeg уходит с критического пути
   расшифровки — без него не будет только архивного файла.
3. VAD ЖИВЁТ В AudioWorkletProcessor, А НЕ В setInterval. Окно бота за экраном, то есть occluded,
   то есть Chrome троттлит таймеры рендерера до 1 с. Worklet работает в аудиопотоке и троттлингу не
   подвержен в принципе.
4. СЕЛЕКТОРЫ ПЛАТФОРМ — ДАННЫЕ, А НЕ КОД. Встроенный meet.probes.toml, переопределяемый файлом в
   ~/.config/forge/. Держащий всё инвариант: ЗАПИСЬ НЕ ЗАВИСИТ НИ ОТ ОДНОЙ DOM-ПРОБЫ. Протухшая
   вёрстка деградирует до «Участник 1..N», а не отменяет запись.
5. FAILED — ТОЛЬКО КОГДА НЕТ ТРАНСКРИПТА. Провал Claude переводит summarizing -> ready с
   summary_status=failed. Час расшифровки не имеет права пропасть из-за неответившего саммаризатора.
   Правило исполнено СТРУКТУРНО: переход summarizing -> failed запрещён таблицей can_transition, а
   исход саммаризации считает одна функция on_summary_finished.

СТАТУС-МАШИНА (src/status.rs — чистая таблица, без ввода-вывода)
queued -> launching -> joining -> [waiting_admit] -> recording -> leaving -> transcoding ->
transcribing -> [summarizing] -> ready, плюс failed(reason) и cancelled.
Три правила, ради которых модуль существует:
  * статуса detected в базе НЕТ — строка встречи появляется только по клику, иначе таблица росла бы
    от простого скролла ленты; отсутствие бейджа И ЕСТЬ «можно записать»;
  * stop и cancel — РАЗНЫЕ операции, и расходятся они ровно в одном месте: из recording stop ведёт
    в leaving (файлы сохраняются), cancel — в cancelled (выбросить);
  * failed разрешён только там, где транскрипта ещё нет.
Повтор этапа (Ф6) — единственный выход из терминального состояния, и что разрешено, определяется
тем, что осталось на диске: из ready можно в transcoding/transcribing/summarizing, из failed — в
transcoding/transcribing (транскрипта там нет по определению), из cancelled — никуда.
Матрица переходов выписана руками и сверяется exhaustive-тестом: 144 ячейки, добавление статуса НЕ
КОМПИЛИРУЕТСЯ, пока автор не допишет строку и столбец.

ЛИМИТЫ ХАБА (src/hub/mod.rs) — три ресурса с РАЗНЫМ поведением при переполнении
  запись   | 2         | Busy НЕМЕДЛЕННО | встреча идёт прямо сейчас; ожидание = бот войдёт, когда всё кончилось
  whisper  | 1, поднять нельзя | FIFO-очередь | Metal занимается процессом целиком, два прогона дерутся и суммарно идут медленнее
  саммари  | 2         | FIFO-очередь | результата никто не ждёт в реальном времени
Очередь видна честно: статус не меняется, но кадр progress несёт queued и queue_position. Отдельного
статуса «в очереди» нет — он размножил бы таблицу переходов вдвое ради временной информации.

СОСТАВ КРЕЙТА
  lib.rs        init / register_routes / spawn_workers / shutdown
  config.rs     MeetConfig: default -> file -> env -> validate_and_fix; load() не паникует
  state.rs      broadcast(1024), hub, db в OnceCell, тёплый индекс бейджей, jobs, shutdown
  providers.rs  канонизация URL и реестр четырёх платформ (матчинг ТОЛЬКО по host)
  status.rs     таблица переходов и SummaryStatus
  db/           SQLite (rusqlite bundled) + repo/{meetings,segments,participants,spans,sources,events}
  hub/          MeetHub, MeetEvent, MeetSink с ЕДИНСТВЕННЫМ методом emit
  bot/          trait MeetBot, ScriptedBot, inject/*.js (worklet, VAD, транспорт), probes.toml
  ingest/       писатель PCM по сэмпловому смещению, WAV, манифест, events.ndjson
  pipeline/     proc, ffmpeg, whisper (Metal-гард), speakers, render, run (+ enum Stage для retry)
  summary/      prompt.rs (СВОЙ промпт встречи) + прогон поверх forge-claude-runner
  deps.rs       пробы внешних бинарей; models.rs; reconcile.rs; recording.rs; routes/; ws/
Модули hub, bot, ingest, pipeline, summary, status, providers НЕ импортируют axum и http.

ХРАНИЛИЩЕ И ФАЙЛЫ
SQLite, а не JSON-стор: час встречи это 2000-4000 сегментов, и каждое сохранение переписывало бы
файл целиком. Каталог встречи самодостаточен: raw/track-N.wav, events.ndjson, manifest.json,
audio.m4a (AAC 32 кбит/с, 14,7 МБ на час), transcript.json, transcript.md, summary.md.
whisper.cpp НЕ ЧИТАЕТ m4a — вход расшифровки это отдельный work/mix.wav.
Одна активная запись на комнату держится частичным уникальным индексом ux_meetings_active_url, а не
мьютексом: мьютекс защищает один процесс и забывает всё при перезапуске.

ВНЕШНИЕ ЗАВИСИМОСТИ И ГЕЙТЫ ДЕРЕВА
forge-cdp (свой CDP-клиент), forge-atomic (атомарная запись), forge-claude-runner (саммари),
rusqlite/tokio-rusqlite из workspace. cargo tree -i openssl-sys пусто, libsqlite3-sys ровно один,
cargo tree -d — 49 дублей и не растёт.

ПРАВИЛО ПРОЕКТА, ИСПОЛНЕННОЕ СТРУКТУРНО
Локальные модели только на GPU: -ng/--no-gpu никогда не попадает в argv (юнит-тест на 4096
комбинаций), а Metal-гард ТРОЙНОЙ — маркер CPU, окно ожидания и проверка ПОСЛЕ выхода процесса
(быстрый CPU-прогон успевает закончиться сам и оставить готовый JSON).
