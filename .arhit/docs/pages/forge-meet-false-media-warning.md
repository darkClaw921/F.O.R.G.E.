# Ложное «запись будет пустой» на vcc.airlabs.pro — разбор 22.08.2026

## Жалоба
«Встреча не записывается, https://vcc.airlabs.pro/r/zqs-9zz-6xr идёт сейчас».

## Что показала проверка на ЖИВОЙ идущей встрече
Запись работает полностью. Запущенная для диагностики встреча (плагин --meet, старт через POST /api/meet/meetings): бот вошёл, увидел обоих участников, 105 секунд писал две дорожки с нормальным уровнем (mean -23 dB, пик -3 dB), расшифровка через polza.ai готова с разделением по говорящим, status=ready/summary_ready.

Попытка пользователя (4e0645a2, старт из Telegram в 14:00:47) прожила 37 секунд и закрылась событием recording_stopped reason=user_stop — то есть кнопкой ОСТАНОВИТЬ. Автоматических остановок в коде нет: /stop дёргается только из обработчика клика в meet-popup.js:1390.

## Настоящий дефект — ложная тревога
На ~0,8 с КАЖДОЙ записи vcc приходили два MediaWarning с текстом «медиа-канал до площадки не поднялся … запись будет пустой»: DNS live.airlabs.pro и TURN 403. Это штатный перебор ICE-кандидатов LiveKit, а не поломка. Проверено: с машины live.airlabs.pro резолвится (155.212.136.205), и в исправной диагностической записи те же две строки соседствуют с полноценным звуком.

Ложная тревога стоила записи: человек увидел её и остановил здоровую встречу.

## Исправление
MediaLogWatch::poll больше не выпускает предупреждение по факту строки в логе. Причины копятся и называются только вместе с подтверждённой глухотой (DOM показывает говорящего, VAD молчит), порог 10 с. Подробности и тесты — в доке элемента MediaLogWatch.

## Чего исправление НЕ трогает
Пост-обработочный гейт тишины в pipeline::run и сам DeafWatch остались как были. Обрыв медиа-канала В СЕРЕДИНЕ встречи по-прежнему не ловится ни одним из стражей: оба смотрят на latched-флаг «VAD хоть раз находил речь». Это осознанное ограничение, а не побочный эффект правки.
