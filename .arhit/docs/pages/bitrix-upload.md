# forge-bitrix — модель загрузки файлов (Фаза 9)

Отправка файла из панели «Битрикс24»: кнопка ⇪, drag&drop, Ctrl+V. Байты идут
браузер → devforge → портал двумя разными запросами, и это не оптимизация, а
следствие того, как устроена платформа.

## 1. Почему заливка одношаговая и что она стоит (Р7)

Классическая связка Диска — `im.disk.folder.get` → `disk.folder.uploadfile` →
`im.disk.file.commit` — требует scope `disk`, которого входящему вебхуку **не
выдают**. Живая проверка на тестовом портале: `insufficient_scope`,
«The request requires higher privileges than provided by the webhook token».

Единственный доступный путь — `im.v2.File.upload` со scope `im`, тем же, что у
всей остальной переписки:

```
POST im.v2.File.upload
{"dialogId":"chat27","fields":{"name":"probe.txt","content":"<base64>",
                               "message":"подпись"}}
→ {"result":{"file":{…},"messageId":97,"chatId":27,"dialogId":"chat27"}}
```

Три следствия, каждое из которых меняет архитектуру:

1. **Метод делает ДВА действия сразу** — заливает файл И отправляет сообщение,
   возвращая его `messageId`. Соблазн добавить следом `im.message.add` «чтобы
   отправить файл» стоил бы ВТОРОЙ строки в чате, и убрать её потом было бы
   нечем. Тест-страж: `the_upload_never_sends_a_second_message`.
2. **Тело — файл в base64.** Это ~1.33 размера файла в памяти плюс столько же
   на сериализованное JSON-тело. Потолок платформы 100 МБ дал бы ~266 МБ
   пиковой памяти на ОДНУ отправку, поэтому дефолт `max_upload_bytes` — **25
   MiB**, и он живёт в конфиге (`~/.config/forge/bitrix.toml`), а не в коде
   фронта.
3. **Прогресса заливки не существует.** Один POST без обратной связи — отсюда
   индетерминированная фаза `portal` (см. §4).

Приём файла от браузера при этом потоковый и RSS не двигает: чанк пришёл —
чанк записан.

## 2. Два запроса вместо одного

```
①  POST /api/bitrix/upload           тело = сырые байты файла
   заголовок X-Forge-File-Name       имя, percent-encoded
   → {upload_id, file_name, size, mime}          НИ ОДНОГО обращения к порталу

②  POST /api/bitrix/dialogs/:id/messages  {"upload_id":"…","text":"подпись"}
   → im.v2.File.upload → messageId → перечитывание строки → кадр message_new
```

Шаг ① не ходит в портал намеренно: пользователь вправе выбрать файл и
передумать, куда его слать. `upload_id` — идентификатор НАШЕГО полуфабриката, а
не адрес чего-либо в Bitrix24.

Шаг ② — тот же роут, которым уходит текст. Отдельного `/files` нет: у отправки
не должно быть двух путей со своими копиями дедупа (Р19), рассылки кадра
`message_new` и перечитывания строки. В ветке файла `text` становится ПОДПИСЬЮ
и может быть пустым (`require_caption` вместо `require_text`), а `reply_to`
уезжает только текстовой цитатой — `im.v2.File.upload` поля `REPLY_ID` не
принимает вовсе (для чтения это ничего не меняет: портал `REPLY_ID` при чтении
всё равно не отражает, Р10).

## 3. Строгий порядок проверок приёма

```
auth (409) → Content-Length (411) → лимит (413) → имя файла (400) → диск
```

Ступень «лимит» стоит **до единого прочитанного байта**. Иначе гигабайтный файл
был бы принят на диск ровно затем, чтобы его отвергнуть: клиент ждал бы минуты,
канал был бы занят, а результат — тот же 413. Инвариант закреплён двумя
тестами: `an_over_limit_body_is_never_polled` (телом служит поток, считающий
собственные опросы; счётчик обязан остаться нулевым) и
`test_upload_over_limit_is_413_before_reading_the_body` в
`tmux-web/tests/bitrix_smoke.rs` (сырой TCP: тело не отправляется вовсе, и если
бы сервер его ждал, тест упал бы по таймауту).

Мусорный `Content-Length` — это 400, а не 411: заголовок ЕСТЬ, он просто
нечитаем, и «пришли размер» было бы неверной подсказкой.

Проверки связи (503) на лестнице нет: staging — локальная операция, а сетевой
отказ штатно отдаётся там, где реально идёт сеть, — в `POST /messages`. Так
короткий сетевой чих не заставляет заново выбирать файл.

`POST /api/bitrix/upload` внесён в `RAW_UPLOAD_PATHS`
(`tmux-web/src/auth.rs`): слой `csrf_guard` требует `Content-Type:
application/json` от каждого мутирующего запроса, а тело загрузки — сырые
байты. Исключение точечное — по ПОЛНОМУ пути и только для
`application/octet-stream`; соседний мутирующий роут того же плагина защиту не
теряет.

## 4. Двухфазный прогресс (Р8)

| фаза | кто кому | проценты | `indeterminate` |
|---|---|---|---|
| `client` | браузер → devforge | точные (знаменатель = `Content-Length`) | `false` |
| `portal` | devforge → Битрикс24 | **не существует** | `true` |

Финальный кадр каждой фазы проходит **мимо троттлинга и в любом исходе**,
включая ошибку: полоса, застрявшая на 97 %, читается как «зависло», и отличить
это от «оборвалось» пользователь не может. Признаком успеха кадр при этом не
является — успех приезжает ответом REST.

Троттлер общий с приёмом медиа (Ф8): 100 мс ЛИБО 256 КиБ. Без него файл на сто
мегабайт дал бы десятки тысяч кадров, все подписчики получили бы `Lagged` и
ушли бы в `resync` — то есть индикатор прогресса сломал бы realtime.

## 5. Staging и одноразовость

`<cache_dir>/uploads/<upload_id>.part`, TTL 30 минут. Имя на диске строится
ТОЛЬКО из UUID — пользовательского ввода в пути нет ни байта, поэтому path
traversal через `X-Forge-File-Name` невозможен по построению.

Файл исчезает после отправки (в любом исходе), по TTL (GC-воркер раз в 5 минут
плюс ленивая подчистка на каждой новой загрузке), при рестарте процесса
(каталог чистится целиком: реестр живёт в памяти, значит все `.part` — сироты)
и при logout (невыбранный файл — данные аккаунта; пережив отвязку, он уехал бы
в чат следующего портала).

`take_upload` **потребляет** запись ещё до заливки. Повторный запрос с тем же
`upload_id` получает `409 invalid_state`, а не второй файл в чате. Двойной клик
по «Отправить» случается куда чаще, чем неудачная заливка, и цена ошибки у них
разная: лишний файл у собеседника не отзывается, а залить заново можно всегда.

## 6. Почему ничего не ретраится (Р9)

`im.v2.File.upload` стоит в `NO_RETRY_METHODS`, и запрет не обходится вложением
в `batch` (проверяется `is_retryable`). Дедуп-идентификатора у портала нет:
повтор означал бы второй файл на Диске и вторую строку в чате. Транспортный
отказ отдаётся как `503`, решение о повторе принимает пользователь кнопкой ⟳ на
карточке, и повтор начинается С ПЕРВОГО ЭТАПА — `upload_id` уже потреблён.

## 7. Фронт (`static/js/bitrix/upload.js`)

Три входа: кнопка `#b24-attach` → скрытый `#b24-file-input`; drag&drop по
панели с оверлеем `#b24-dropzone` (счётчик вложенности, иначе оверлей мигает на
каждом дочернем узле; перетаскивание ТЕКСТА оверлей не поднимает — зона не
должна мешать выделению); `Ctrl+V` в поле ввода, перехватываемый только когда в
буфере есть файл. Скриншот из буфера получает имя `pasted_YYYYMMDD_HHMMSS.png`:
браузер называет их все `image.png`, и в переписке они сливаются.

**Один файл = одно сообщение** (метод принимает ровно один файл), очередь
строго последовательная: два параллельных base64-тела по 33 МБ — это 66 МБ в
куче devforge разом.

Карточка живёт в `#b24-uploads` **над строкой ввода**, а не в ленте:
`chat.renderHistory()` пересобирает `#b24-log` целиком на любой правке и на
любом сообщении, вставшем не в конец, — карточка отправки исчезала бы вместе с
прогрессом. Да и по существу очередь отправки — это состояние строки ввода: в
переписке файл появляется только после того, как портал его принял.

XHR вместо `fetch`: у `fetch` нет прогресса ОТПРАВКИ. Следствие, о котором
легко забыть: XHR идёт мимо подменённого `window.fetch` из `core/auth.js`,
поэтому `Authorization: Bearer` ставится вручную — без этого отправка работала
бы только на localhost.

Клиентская проверка размера идёт по `max_upload_bytes` из
`GET /api/bitrix/status` (`b24State.maxUploadBytes`), а не по своей копии
числа: скрипты браузер держит в кэше PWA неделями, и копия разъехалась бы с
конфигом при первом же его изменении. Файл больше лимита не порождает НИ ОДНОГО
запроса.
