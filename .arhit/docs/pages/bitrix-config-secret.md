# forge-bitrix — конфиг плагина и секрет вебхука

Элементная запись Фазы 1 для `plugins/bitrix/src/config.rs`. Rust-файлы
`arhit arch build` в этом проекте не индексирует (индексируется только JS),
поэтому модульная документация ведётся именованными страницами с префиксом
`bitrix-`. Префикс обязателен: имена `config`, `state`, `routes` пересекаются
с плагинами vk и telegram, и запись без префикса затёрла бы соседнюю.

## Что здесь секрет

Секрет Bitrix24 — **весь URL входящего вебхука целиком**:
`https://<портал>/rest/<user_id>/<код>/`. Код криптографически связан с
`user_id`, поэтому «спрятать только код» бессмысленно: пара `user_id + code`
и есть учётные данные.

## `WebhookUrl` — newtype без `Serialize`

Ровно тот же приём, что у `SecretToken` в forge-vk:

- `#[derive(Clone, Default, PartialEq, Eq, Deserialize)] #[serde(transparent)]`
  — **`Serialize` не реализован и не будет**: DTO с секретом физически не
  соберётся, и это дешевле дисциплины и теста на каждое новое поле;
- `Debug` вручную → `"<redacted>"`;
- `new()` трим'ает (URL вставляют из буфера, где легко захватить перенос);
- `expose()` — ЕДИНСТВЕННАЯ точка чтения; названа так, чтобы выглядеть
  подозрительно в code review, и по ней же ищет тест-страж
  `no_source_line_logs_the_exposed_url` (Ф2);
- `fingerprint()` → `portal#uid…хвост6`; пусто → `<none>`, нераспознанная
  строка → `<malformed>` (если разбор не удался, мы не знаем, где в строке
  код, и печатать её опасно). **Только в логи, никогда в HTTP-ответ.**

## Разбор URL

`parts()` реализует регексп контракта
`^(https?://[^/\s]+)/rest/(\d+)/([A-Za-z0-9]+)/?$` вручную — тащить крейт
`regex` ради одной строки незачем. Принимает обе формы хвоста (со слэшем и
без), отвергает чужую схему, пустой хост, нечисловой `user_id`, неалфанумный
код и лишний сегмент пути (`.../abc/profile`).

Производные: `api_base()` (`<origin>/rest/<uid>/<code>` — СОДЕРЖИТ СЕКРЕТ),
`portal_host()` (только хост; наружу в `/status` всё равно не уходит).

## Поля `BitrixConfig`

| поле | дефолт | env |
|---|---|---|
| `webhook` | пусто | `FORGE_BITRIX_WEBHOOK` |
| `base_url_override` | пусто | `FORGE_BITRIX_BASE_URL` |
| `cache_dir` | `~/.forge/bitrix-cache` | `FORGE_BITRIX_CACHE_DIR` |
| `poll_active_secs` | 4 | `FORGE_BITRIX_POLL_ACTIVE_SECS` |
| `poll_idle_secs` | 20 | `FORGE_BITRIX_POLL_IDLE_SECS` |
| `recent_sync_secs` | 60 | `FORGE_BITRIX_RECENT_SYNC_SECS` |
| `max_upload_bytes` | 25 MiB | `FORGE_BITRIX_MAX_UPLOAD_BYTES` |
| `rate_limit_rps` | 2 | `FORGE_BITRIX_RATE_LIMIT_RPS` |
| `burst` | 5 | `FORGE_BITRIX_BURST` |
| `config_path` | `~/.config/forge/bitrix.toml` | `FORGE_BITRIX_CONFIG_PATH` |

Интервалы лежат в конфиге не для пользователя, а ДЛЯ ТЕСТОВ: воркеры Ф7
инжектируют сотни миллисекунд вместо боевых секунд и не спят минутами.

`max_upload_bytes = 25 MiB` (Р7) — платформенный лимит вдвое-вчетверо больше,
но заливка идёт одношагово через base64 в JSON-теле: 100 МБ файла это ~133 МБ
строки в памяти на каждую параллельную отправку.

`rate_limit_rps = 2` и `burst = 5` — портал даёт 2 req/s на пару портал+IP при
ёмкости ведра 50; наше ведро намеренно меньше, чтобы девять десятых бюджета
оставались живому пользователю.

## Цепочка загрузки

`load()` = defaults → `load_from_file` → `apply_env` → `validate_and_fix`.
Никогда не паникует и не возвращает `Err`:

- файла нет — штатный путь (у большинства `bitrix.toml` не существует, вебхук
  вставляется в UI);
- битый TOML — warn и ПОЛНЫЕ дефолты; частичного применения нет, иначе
  половина конфига была бы из файла, а половина из головы;
- мусор в env игнорируется с warn — env не должен уметь «сломать» конфиг;
- значения вне диапазона чинятся дефолтами.

`validate()` (проверка без изменений) существует отдельно ради `init`:
пустой `webhook` ошибкой НЕ является — «включён, но ещё не подключён» это
штатное стартовое состояние.

## `FORGE_BITRIX_CONFIG_PATH` — две роли

1. Герметичность тестов: без него `load()` читал бы живой
   `~/.config/forge/bitrix.toml` разработчика, а запись вебхука (Ф3) писала бы
   туда же — прогон `cargo test` отключал бы человека от портала.
2. Признак ТЕСТОВОГО режима для правила Р17 (Ф2): `http://127.0.0.1` в
   `base_url_override` законен только при непустом значении переменной
   (`is_isolated_env()`), в проде обязательна схема `https`.

## Тесты модуля

Отсутствующий файл даёт дефолты; битый TOML даёт ПОЛНЫЕ дефолты; интервалы
читаются из файла; частичный файл сохраняет остальные дефолты; `Debug`
конфига не содержит кода вебхука и содержит `<redacted>`; `fingerprint`
скрывает код, но опознаёт портал; `parts()` принимает обе формы хвоста и
отвергает восемь видов мусора; `validate` ловит выход за диапазоны;
`validate_and_fix` чинит вместо отказа; пустой вебхук валиден;
`base_url_override` побеждает вебхук.

## Транспортные поля (Фаза 2)

| поле | дефолт | зачем |
|---|---|---|
| `base_url_override` | пусто | подмена базы порталом-стендом; правило Р17 |
| `rate_limit_rps` | 2 | пополнение клиентского ведра (лимит портала — 2 req/s) |
| `burst` | 5 | ёмкость ведра; портальная — 50, наша намеренно меньше |
| `connect_timeout_secs` | 10 | отличает «сети нет» от «портал думает» |
| `request_timeout_secs` | 30 | закрывает ЗАВИСАНИЕ портала при превышении интенсивности |

Таймауты обязательны, а не желательны: превышение лимита интенсивности живьём
выглядит как зависание или обрыв TCP без JSON-ошибки. Без клиентского таймаута
такой вызов держал бы задачу неопределённо долго и не породил бы ошибки,
которую можно было бы повторить.

## Правило Р17 целиком

`check_base_url_override(raw, isolated) -> Result<(), String>` — ЧИСТАЯ функция;
признак изолированного окружения передаётся параметром, поэтому обе ветки
правила проверяются юнит-тестами без подмены переменных процесса.

Разрешено: пустая строка (переопределения нет); любой `https://…`;
`http://` — ТОЛЬКО на петлевой хост (`127.0.0.1`, `localhost`, `[::1]`) и
ТОЛЬКО при непустом `FORGE_BITRIX_CONFIG_PATH`. Всё остальное (`http://` на
чужой хост, чужая схема, мусор) отвергается всегда.

Причина: вебхук — это секрет, который клиент кладёт в ПУТЬ каждого запроса.
Схема `http` означает, что учётные данные портала уезжают по сети открытым
текстом. Петлевой адрес физически не покидает машину — но только он и только
там, где мы точно знаем, что это прогон тестов, а не боевая конфигурация с
опечаткой в схеме.

`validate()` возвращает ошибку (и `init` стартует без плагина);
`validate_and_fix()` СНИМАЕТ переопределение целиком, а не «чинит» его: тихо
подставить `https` к чужому хосту хуже, чем вернуться к базе из вебхука —
пользователь получил бы рабочий плагин, ходящий не туда, куда он просил.
Текст ошибки НЕ цитирует само значение: в нём может лежать полный путь вебхука.

## Запись секрета на диск (Фаза 3)

Единственный путь, которым вебхук покидает процесс, — `save_webhook_to(path,
webhook)`; стирание — `clear_webhook_to(path)`. Обёртки-методы
`BitrixConfig::save_webhook` / `clear_webhook` подставляют
`config_path` и обновляют значение в памяти.

Четыре инварианта записи:

1. **read-modify-write** — остальные ключи пользовательского `bitrix.toml`
   (интервалы, лимиты, любые незнакомые) переживают запись; битый TOML не
   запирает пользователя, а переписывается с нуля с warn'ом — иначе одна
   опечатка навсегда лишала бы возможности подключиться из UI;
2. **`0600` в момент СОЗДАНИЯ файла**: `OpenOptions::mode(0o600)` плюс явный
   `set_owner_only` ДО первого `write_all` (открываем `create`, а не
   `create_new`, — файл мог остаться от упавшего процесса, и тогда `mode()`
   не применяется вовсе);
3. **атомарность**: `.bitrix.toml.<pid>.tmp` в ТОМ ЖЕ каталоге → `fsync` →
   `rename`. Каталог тот же не случайно: `rename` атомарен только внутри одной
   файловой системы, а `/tmp` на многих машинах — другая. Без `fsync`
   переименование могло бы опередить сброс содержимого: при отключении питания
   остался бы файл нулевой длины ВМЕСТО старого;
4. при любой ошибке tmp удаляется, целевой файл остаётся прежним.

`WEBHOOK_KEY = "webhook"` совпадает с именем поля структуры: read-modify-write
работает с сырой таблицей, и разъехавшееся имя тихо создало бы ВТОРОЙ ключ
вместо перезаписи первого.

`tighten_perms_if_needed` вызывается на КАЖДОЙ загрузке, а не только при
записи: файл могли создать руками через `echo >`, скопировать с другой машины
или достать из бэкапа. Права шире `0600` чинятся с warn'ом.

Пустой вебхук сохранить НЕЛЬЗЯ (`save_webhook_to` возвращает ошибку): стирание
— отдельная операция, и подменять её записью пустой строки значит потерять
различие «logout» и «сохранили мусор». Стирание по несуществующему файлу —
no-op, файл ради пустоты не создаётся.

Мультипортальности в v1 нет (Р5): повторное сохранение ПЕРЕЗАПИСЫВАЕТ, второго
ключа появиться не может (тест `saving_twice_overwrites_instead_of_appending`).

Подробности автомата подключения, который эту запись вызывает, — на странице
`bitrix-login`.
