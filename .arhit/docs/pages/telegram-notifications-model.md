# Telegram: модель уведомлений (наследование глобальных настроек)

Дефект D1 из жалобы пользователя: «уведомления продолжают приходить от ненужных чатов».
Здесь описано, ПОЧЕМУ так было и что стало источником истины.

## Почему было сломано

Три независимых причины, дававшие один симптом:

1. **Наследование глобальных настроек не учитывалось.** Telegram НЕ дублирует настройки
   уведомлений в каждый диалог. Если пользователь заглушил «все личные чаты» / «все группы» /
   «все каналы» с телефона, у самих диалогов `PeerNotifySettings` приезжает пустым
   (`silent = None`, `mute_until = None`), а решение принимается по дефолту КАТЕГОРИИ
   (`account.getNotifySettings` с `InputNotifyUsers`/`InputNotifyChats`/`InputNotifyBroadcasts`).
   Плагин про эти дефолты не знал вовсе — такие диалоги считались незаглушёнными.

2. **Глобальный `updateNotifySettings` терялся.** Апдейт с unit-вариантом `NotifyPeer`
   (`NotifyUsers`/`NotifyChats`/`NotifyBroadcasts`) не разбирался. Заглушить категорию с
   телефона и увидеть эффект в вебе было невозможно.

3. **Решение принимал фронт по неполным данным.** `maybeToast` сверялся с `Set local.muted`,
   собранным из ЗАГРУЖЕННОЙ страницы `/dialogs` (верхняя сотня), а WS вещает по ВСЕМУ аккаунту.
   Чат вне страницы — заглушённый лично, заглушённый глобально или архивный — был фронту
   неотличим от незаглушённого. Архив вообще не участвовал в решении.

## Правило разрешения mute (единственное)

`dto::notify_muted_with_default(settings, now, default_muted)`. Порядок обязателен:

1. явный `silent == Some(true)` ⇒ **muted**;
2. явный `mute_until > now` ⇒ **muted**;
3. явный `mute_until` в прошлом или `0` ⇒ **НЕ muted** — точечный unmute перебивает даже
   «заглушить все чаты»;
4. `silent` и `mute_until` **оба** `None` ⇒ берётся глобальный дефолт категории.

Проверка «пусто целиком» смотрит на ОБА поля: объект с выставленным `silent` и унаследованным
`mute_until` считается настроенным ЯВНО.

Категория по типу peer: user (в т.ч. бот и Saved Messages) → `users`; малая группа И мегагруппа
→ `chats`; broadcast-канал → `broadcasts`.

## Кто где хранится

- `dto::NotifyDefaults { users, chats, broadcasts }` — уже РАЗРЕШЁННЫЕ булевы значения (срок
  глобального mute проверяется один раз при загрузке).
- `TelegramState::notify_defaults` / `notify_overrides` / `archived_ids` — серверные кэши.
  **Дополняются, а не пересеваются**: списки приходят страницами (основной, архив, папки), и
  полная замена стирала бы знание о соседних страницах, то есть возвращала бы дефект.
- `is_dialog_muted` возвращает `Option<bool>`: `None` — это «не знаем», а не «не заглушён».
  Ровно на этой разнице держится подстановка дефолта категории
  (`updates::resolve_dialog_flags`).

## Жизненный цикл

1. Supervisor на старте и на КАЖДОМ реконнекте зовёт `updates::refresh_notify_defaults` —
   три `account.getNotifySettings` под таймаутом 10 с (`NOTIFY_DEFAULTS_TIMEOUT`).
   **До** старта потока апдейтов: иначе первое же сообщение из заглушённой категории уедет во
   фронт как звенящее. Апдейты в это время копятся в канале рантайма и не теряются.
   Частичный результат не принимается — две категории из трёх дали бы «иногда каналы звенят».
2. `GET /api/telegram/dialogs` считает `muted` с наследованием и зовёт
   `TelegramState::remember_dialogs` — засев кэшей. Всё, что сервер когда-либо перечислял, он помнит.
3. `updateNotifySettings` → `updates::notify_outcome` → `NotifyOutcome::Defaults` (обновить
   дефолты + кадр `notify_defaults_changed`) | `Dialog` (per-peer, muted уже разрешён) |
   `Ignored` (`NotifyForumTopic`). Побочные эффекты вынесены в `CacheEffect`, `apply_effects`
   пишет кэши **до** broadcast — иначе клиент, дёрнувший REST в ответ на кадр, прочитал бы
   устаревшее состояние.
4. Кадр `new_message` несёт поля УРОВНЯ КАДРА `muted` / `archived`
   (`updates::resolve_dialog_flags`). Промах кэша ⇒ дефолт КАТЕГОРИИ, а не слепой `false`.

## Фронт

- `main.js::dialogRings(frame, localMuted, localArchived)` — единственная точка решения
  «показывать тост и считать в бейдже». Кадр перебивает локальное знание В ОБЕ стороны
  (`muted:false` = «mute сняли с телефона»). Фолбэк на локальное включается ТОЛЬКО когда поля
  нет: проверка `typeof === 'boolean'` (`frameFlag`), а не `!frame.muted` — иначе «не знаю»
  старого сервера превратилось бы в «не заглушён», то есть в регресс ровно в сторону жалобы.
- `main.js::badgeUnread` — бейдж на ✈ = `unreadTotal(dialogsForDir(dialogs, {type:'inbox'}), muted)`:
  без заглушённых и БЕЗ АРХИВА. Раньше цифра расходилась со счётчиком `~/inbox` на непрочитанное
  в архиве.
- `local.flagsExtra` (dialog_id → {muted, archived}) и `local.pendingUnread` — знание о диалогах
  ВНЕ загруженной страницы; снимаются, как только диалог появится в списке (список авторитетнее).
  `pendingUnread` нужен потому, что `dialogs.bumpUnread` по неизвестному диалогу молча выходит —
  раньше тост был, а бейдж не рос.
- Кадр `notify_defaults_changed`: запомнить дефолты, сбросить производные карты (они посчитаны по
  СТАРЫМ дефолтам) и перечитать список диалогов. Пересчитать поимённо на фронте нельзя —
  признака «унаследовано» в `DialogDto` нет, а перечислить все диалоги категории сервер не может.
  Флаг `defaultsReloading` не даёт пачке кадров наплодить запросы.

## Известные ограничения

- В per-peer `updateNotifySettings` категория выводится по тегу `PeerId`, который не отличает
  мегагруппу от broadcast-канала. Промах возможен только у диалога с ПОЛНОСТЬЮ унаследованными
  настройками при разных дефолтах `chats`/`broadcasts`; ближайший листинг перезапишет запись
  точным значением через `remember_dialogs`.
- `NotifyDefaults::for_kind` на неизвестном kind даёт `false`: молчать по ошибке хуже, чем
  показать лишнее.
