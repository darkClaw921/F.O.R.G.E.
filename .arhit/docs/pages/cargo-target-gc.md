Контроль размера target/ (кэша сборки Rust)

## Проблема
Cargo никогда не удаляет артефакты сам. Каждая смена версии зависимости, ветки
или набора features добавляет в target/debug/deps новый .rlib/.rmeta, а старый
остаётся навсегда. За несколько месяцев работы target/ вырос до 48 ГиБ на диске
(98.6 ГиБ по счётчику cargo clean, 335 798 файлов) и почти забил свободное место.

Второй источник — полная отладочная информация dev-профиля. Основную массу дают
не наши крейты, а зависимости (tokio, axum, grammers, ring), внутрь которых
отладчиком никто не заходит.

## Решение — два уровня

### 1. Профили в корневом Cargo.toml
[profile.dev] debug = "line-tables-only" — наш код сохраняет panic-сообщения и
backtrace с указанием файл:строка. Теряется только пошаговая отладка с чтением
значений переменных в lldb; если она понадобится, временно вернуть debug = true.

[profile.dev.package."*"] debug = false — зависимости собираются вовсе без
debuginfo.

Замер на чистой сборке всего workspace: 2.5 ГиБ вместо ~5 ГиБ; время сборки не
изменилось (~1 мин 10 с).

### 2. scripts/cargo-gc.sh — регулярная уборка
Запуск: scripts/cargo-gc.sh [порог_в_ГиБ] (по умолчанию 20; 0 = безусловный clean).

Порядок действий скрипта:
  1. Всегда удаляет target/*/incremental — кэш инкрементальной компиляции, самый
     объёмный и самый недолговечный, восстанавливается первой же сборкой.
  2. Если после этого target/ всё ещё больше порога — выполняет полный cargo clean.

Точечное удаление старья по mtime сознательно НЕ применяется: cargo не обновляет
mtime у переиспользованных артефактов, поэтому 'старым' по времени выглядит и то,
что нужно текущей сборке.

Скрипт не ставится в cron и не вешается на hook — правила проекта запрещают
CronCreate и ScheduleWakeup; запускать вручную, когда сборка стала занимать место.

## Известная ловушка
Первая сборка сразу после полного cargo clean может однократно упасть с
'error: extern location for <крейт> does not exist: .../lib<крейт>-*.rmeta'.
Артефакта на диске при этом действительно нет. Лечится простым повторным
запуском cargo build — изменений в коде не требуется.
