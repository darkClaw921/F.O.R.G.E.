Фронтенд логина вкладки Telegram (Фаза 2): tmux-web/static/js/telegram/login.js + правки main.js/api.js/state.js/dom.js/index.html/telegram.css.

login.js — 3-этапный терминальный wizard в оверлее #tg-login:
1. creds — api_id / api_hash / phone -> POST /api/telegram/login/start. Пояснение со ссылкой на my.telegram.org (target=_blank rel='noopener noreferrer'), текст 'это НЕ бот-токен: подключается ваш личный аккаунт' и путь ~/.config/forge/telegram.toml (права 0600). api_hash — input type=password; в localStorage не пишется ничего.
2. code — код из Telegram + подпись 'код отправлен на <phone>' + кнопка BACK -> POST /login/code.
3. password — пароль 2FA + подсказка hint от сервера + BACK -> POST /login/password.

ГЛАВНЫЙ ИНВАРИАНТ: видимый шаг определяется полем state ответа сервера (STEP_BY_STATE: not_configured|disconnected -> creds, code_sent -> code, password_required -> password), а НЕ локальным счётчиком — сервер хранит токены и только он знает, где мы. Единственное исключение — BACK: local.forcedStep действует до ближайшей смены состояния на сервере (local.forcedForState + lastState), потому что request_code разрешён и из CodeSent, и из PasswordRequired.

UX-детали: Enter в любом поле = сабмит шага; на время запроса поля и кнопки disabled + строка '>> connecting…' (#tg-login-status); поля НЕ очищаются, чтобы после неверного кода/пароля можно было исправить одну цифру; ошибки строкой '>> ERR: <message>' цветом --t-red; всё через textContent (XSS). При state=authorized оверлей скрывается и секреты (api_hash/password/code) вычищаются из DOM.

FLOOD_WAIT (риск №2 плана). handleStepError решает по КОДУ ошибки, а не по тексту: flood_wait -> startCountdown(retry_after_secs) + блокировка кнопок + живая строка '>> FLOOD_WAIT: retry in MM:SS' (formatWait даёт HH:MM:SS для многочасовых блокировок); invalid_state -> 'сессия логина устарела, начните заново' + возврат на шаг 1; not_connected -> 'нет соединения с Telegram'. НИКАКИХ авто-ретраев: submit() возвращается сразу, пока local.waitLeft > 0, поэтому даже ручной клик во время countdown ничего не отправляет. setInterval гасится в stopCountdown(), которая вызывается при перезапуске countdown, по истечении, из resetLoginWizard (logout) и из teardownTelegram (beforeunload). unlockButtonsIfIdle() — единственное место снятия блокировки (иначе внешний stopCountdown оставлял бы wizard мёртвым до перезагрузки страницы).

main.js — applyLoginState(dto): ЕДИНАЯ идемпотентная точка, вызываемая и ответом GET /status, и WS-событием login_state. Выставляет tgState.loginState/selfUser, заполняет #tg-self-user через selfUserLabel (@username -> first_name -> phone -> id), показывает/скрывает #tg-logout, делегирует оверлей и шаги в login.js::renderLoginState, обновляет Mode-бейдж (#tg-mode). При переходе authorized -> любое другое состояние (в том числе разлогин с другого устройства) вызывает clearAccountData(): диалоги/сообщения/uploads чистятся, objectURL'ы revoke'аются (state.js::clearTgAccountData — там же, где URL'ы создаются, поэтому утечка не может появиться из расхождения двух копий логики), бейдж сбрасывается. requestLogout(): confirm -> POST /logout -> resetLoginWizard -> applyLoginState; при ошибке состояние переспрашивается через GET /status.

api.js — loginStart/loginCode/loginPassword/logout поверх общего call(), который разбирает {error:{code,message,retry_after_secs}} в Error.status/.code/.retryAfterSecs.

ПРОВЕРЕНО В БРАУЗЕРЕ (playwright из e2e/node_modules, изолированный HOME + свободный порт): кнопка ✈ видна только при включённом плагине (без флага — скрыта, /api/telegram/status -> 404, pageerror нет); оверлей открывается hacker-green; локальная валидация пустого телефона не отправляет запрос; Enter в phone уходит запросом; реальный ответ Telegram API_ID_INVALID показывается как '>> ERR: …' при сохранённом значении поля; переходы creds->code(+телефон)->BACK->creds->code->password(+hint)->authorized на моках; после authorized #tg-self-user='@forge', logout видна, секреты вычищены; countdown 429 retry_after_secs=65 тикает 01:05->01:03 при 0 запросов, а при retry_after_secs=3 через 3.8с кнопка разблокирована и timerActive=false.
