# tmux-web/tests/bitrix_smoke.rs — смоук плагина Битрикс24 ПО ПРОВОДУ

Близнец vk_smoke.rs / telegram_smoke.rs. Поднимает НАСТОЯЩИЙ axum-сервер на свободном порту и ходит в него реальным HTTP/WS-клиентом. Ловит класс дефектов, который unit-тесты с oneshot пропускают: несмонтированный роут, конфликт шаблонов путей, сломанный WS-апгрейд, порядок слоёв, отказ до чтения тела. 27 тестов.

## Стенд

Harness держит РЕЕСТР (Arc<B24Registry>) и отдельно состояние первого слота. Точки входа плагина работают с реестром: init(BitrixRootConfig) -> Arc<B24Registry>, register_routes(app, registry), spawn_workers(&registry), shutdown(&registry). Opts: webhook (один портал), portals (несколько), ws (укороченные heartbeat/idle).

Полная герметичность: cache_dir, config_path, prompts_path и claude_cli_path — во временном каталоге, поэтому живой ~/.config/forge/bitrix.toml разработчика не читается и не перезаписывается, хранилище заметок не уезжает в ~/.forge, а настоящий claude не запускается. base_url_override — https на заведомо закрытый порт 1 (схема именно https: правило Р17 разрешает http://127.0.0.1 только при непустом FORGE_BITRIX_CONFIG_PATH, а подменять переменные процесса в многопоточном тестовом бинаре — гонка).

## Что покрыто

OPT-IN. test_routes_absent_without_the_plugin — главный инвариант фичи: роутер БЕЗ register_routes отдаёт 404 на весь префикс /api/bitrix/* (включая /portals и /portals/:pid) и на /ws/bitrix. Именно на 404 держится гейт кнопки вкладки во фронте.

ГЕЙТ ХОСТА. test_the_host_registers_the_plugin_only_behind_the_flag читает tmux-web/src/main.rs ПО ИСХОДНИКУ (бинарь, функции из интеграционного теста не позвать): регистрация ровно одна и внутри if bitrix_enabled; строго ДО .fallback(static_embed::serve_static) — иначе 404 на роуты плагина; строго ДО auth::bearer_auth и auth::csrf_guard — иначе дыра в авторизации в remote-mode, самая дорогая из трёх ошибок, потому что она не видна ни в одном функциональном тесте. Плюс: init обрабатывается match'ем с warn, а не ?; вызов идёт с BitrixRootConfig::load(); shutdown плагина вызывается. Комментарии из исходника выбрасываются намеренно — иначе тест доказывал бы порядок комментариев.

СЕКРЕТ. assert_no_secret_anywhere проверяет СЫРОЕ тело ответа на: хост портала, слово fingerprint и любой кусок кода вебхука длиной 8+ символов (порог не косметический: код из 16 символов алфавита [A-Za-z0-9], каждый показанный символ убирает из перебора множитель 62). Прогоняется по всем ВОСЬМИ состояниям автомата подключения, по ответам роутов входа/выхода, по GET /api/bitrix/portals и по WS-кадру portals. test_the_secret_guard_actually_catches_a_leak — страж стража: без него assert_no_secret_anywhere мог бы тихо стать no-op и зеленеть на любом теле.

СОСТАВ РОУТОВ. test_only_the_implemented_routes_are_mounted: data-роуты без вебхука дают 409 (ПЕРВАЯ ступень лестницы), POST-роуты на GET дают 405, GET /api/bitrix/portals — 200 с пустым списком (строка вкладок обязана читаться всегда), /api/bitrix/portals/:pid — 405 (PATCH/DELETE-only). Разница 404 vs 405/409 принципиальна: 404 означает «плагина нет» и гасит кнопку вкладки.

ЖИЗНЕННЫЙ ЦИКЛ. init синхронный и без сети — порог 500 мс на реестре ИЗ ДВУХ порталов; spawn_workers возвращается сразу; shutdown идемпотентен (три вызова, третий по пустому реестру воркеров); битый bitrix.toml не роняет init (читается боевым BitrixRootConfig::load_from_file, обе половины падают на дефолты — ни общих настроек, ни [[portals]]).

WS. Снапшот соединения — login_state КАЖДОГО слота, затем кадр portals; у пустого слота portal_id = _vacant, у служебных кадров = _socket. Помощник next_frame_of(ws, тип) читает до кадра нужного типа: разбирать порядок кадров в каждом тесте значило бы прибивать тесты к числу порталов стенда. Дальше: ping/pong переживает несколько idle-окон (тайминги укорочены через B24State::with_ws_timings — с боевыми 15/60 с тест шёл бы больше минуты), молчащий клиент закрывается по idle, битый входящий кадр НЕ рвёт соединение, broadcast доезжает до всех клиентов, shutdown закрывает живые соединения.

ЗАГРУЗКА ФАЙЛА. Отказ приходит НЕ ДОЖИДАЯСЬ ТЕЛА — через oneshot это не увидеть вовсе, там тело уже собрано в памяти. Поэтому запросы шлются вручную по TCP с заведомо ложным Content-Length: ждал бы сервер тело — тест упал бы по таймауту, а не по ассерту. Проверяются 409 (без подключения), 411 (chunked без Content-Length), 413 (сверх лимита, плюс инвариант «каталог staging не создан»), happy path с percent-encoded именем. Плюс страж CSRF-исключения: /api/bitrix/upload обязан стоять в RAW_UPLOAD_PATHS хоста (проверка по исходнику src/auth.rs), а список исключений обязан оставаться точечным.

## Что добавила мультипортальность

test_the_portal_header_picks_the_state_over_the_wire — заголовок X-Forge-Portal выбирает состояние на КАЖДЫЙ запрос: адресный запрос уходит в названный портал, запрос без заголовка — в ПЕРВЫЙ слот, неизвестный id — 404 (а не молчаливое сползание на первый портал, которое означало бы чужую переписку под своим именем). Состояния двух порталов разведены намеренно: одинаковые не отличили бы «выбрали тот портал» от «выбрали любой».

test_ws_carries_every_portal_with_its_id — ОДИН сокет несёт кадры обоих порталов, каждый со своим portal_id; переход состояния одного портала приезжает под ЕГО адресом.

test_the_portals_list_never_leaks_a_webhook — GET /api/bitrix/portals собирается из PortalConfig, где вебхук лежит рядом с id и title, то есть ровно там, где новое поле утекает легче всего.

test_two_portals_share_no_files_on_disk — два портала не делят ни кэш, ни файл разборов, и каталог одного не лежит внутри другого.
