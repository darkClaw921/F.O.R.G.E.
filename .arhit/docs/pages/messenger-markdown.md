Архитектурное решение: собственный парсер Markdown в общем слое мессенджеров (эпик forge-vkmd-b-4fyj).

ЗАДАЧА. Ответы Claude в панели VK (разбор чата и тред вопросов) приходят с Markdown-разметкой и показывались сырым текстом: «**жирный**», «|таблица|».

РЕШЕНИЕ 1: свой парсер, а не библиотека.
 - devforge обязан работать офлайн и не ходить в сеть за ассетами; CDN запрещён, значит библиотеку пришлось бы вендорить в бинарь через rust-embed вместе с её обновлениями и CVE.
 - marked/markdown-it отдают СТРОКУ HTML, то есть требуют ещё и санитайзер (DOMPurify) — два чужих компонента в цепочке, каждый со своей поверхностью XSS, ради шести видов разметки.
 - Инвариант панели VK «в DOM только через textContent» (js/vk/main.js:44-45) с такой цепочкой пришлось бы нарушить: innerHTML — обязательный шаг любой HTML-строковой библиотеки. Текст же порождён моделью ИЗ ПЕРЕПИСКИ С ПОСТОРОННИМИ, то есть недоверен ровно как тело сообщения.
 - Свой рендерер строит узлы через createElement/createTextNode, и тогда весь риск фичи сосредоточен в ОДНОЙ функции safeHref, которую можно доказать и покрыть поимённым списком векторов.

РЕШЕНИЕ 2: модуль в js/messenger/, а не в js/vk/. Разбор Markdown — не свойство ВКонтакте: те же ответы модели будут показывать панели Telegram и Битрикс24. Общий слой (follow-core.js, hotkeys-core.js, http-envelope.js, theme-core.js, ws-core.js) — сложившееся место для такого кода. Следствие: классы узлов нейтральные (md-*), а не vk-*; красит их панель у себя (css/vk.css, только токены --v-*, ограничено .vk-analysis-out и .vk-analysis-thread), поэтому инвариант «панели не красят друг друга» цел.

РЕШЕНИЕ 3: парсер отдельно от рендерера.
  parseMarkdown(text) -> AST      — чистая функция, без DOM
  renderMarkdown(ast, doc) -> DocumentFragment — doc параметром, не глобальный document
Это не эстетика: чистый парсер покрывается тестами сравнением структур без фейкового DOM, а рендерер с инжектируемым документом проверяется в Node. Пять секций теста messenger_markdown.test.mjs (251 проверка) существуют именно благодаря этому разделению.

РЕШЕНИЕ 4: политика ссылок. Только http: и https:, проверка через new URL и сравнение url.protocol, НЕ регекспом по началу строки (регексп обходится пробелами, \\n, табами и регистром — new URL нормализует всё это сам, ровно как браузер). Относительные ссылки запрещены явно: без базы new URL бросает, а подстановка location.href дала бы ответу модели кликабельную ссылку на собственный API devforge с куками пользователя. Запрещённая ссылка рендерится обычным текстом — пустой href выглядел бы рабочей ссылкой.

РЕШЕНИЕ 5: деградация вместо потери. Непонятная разметка становится абзацем, незакрытый блок кода дочитывается до конца, рваная таблица добивается пустыми ячейками. Потерять кусок ответа модели нельзя: пользователь не узнает, что чего-то не увидел.

ГРАНИЦЫ. Подсветки синтаксиса нет (язык сохранён в data-lang на будущее). Изображений нет намеренно: внешний запрос из панели с перепиской — это утечка Referer и трекинг-пиксель. HTML-вставок нет по инварианту. Вложенность ограничена 12 уровнями.

ПОДКЛЮЧЕНИЕ К ПОПАПУ — отдельный эпик (forge-vkmd-c-tju5): во время стрима панель показывает сырой текст (pre-wrap), а по кадру analysis_done перерисовывает блок как Markdown; разбор и тред из GET /api/vk/dialogs/:id/analysis рендерятся Markdown сразу.

Файлы: tmux-web/static/js/messenger/markdown.js, tmux-web/static/css/vk.css (секция «Отрисованный Markdown»), tmux-web/tests/frontend/messenger_markdown.test.mjs.
