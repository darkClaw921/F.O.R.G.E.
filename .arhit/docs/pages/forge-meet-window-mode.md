# Режим окна бота: почему дефолт — `minimized`

Решение принято ИЗМЕРЕНИЕМ, а не рассуждением (задача `forge-meet-f3-uz8j.14`).
Стенд — `plugins/meet/tests/window_mode.rs`, живые проверки механизма —
`plugins/forge-cdp/tests/live_chrome.rs`. Машина: macOS 15, Google Chrome
151.0.7922.138.

## Требование

Пользователь потребовал, чтобы браузер бота НЕ МЕШАЛ работать. Требование «не
отбирать фокус» закрыто ещё в Ф1 (`--no-startup-window` +
`Target.createTarget{background:true}`); здесь речь о втором его смысле — окно
не должно висеть на экране всю встречу.

## Что показал оконный сервер macOS

Снято `CGWindowListCopyWindowInfo(.optionOnScreenOnly)` по pid браузера бота.
Проба проверена контрольным опытом: чужие приложения она видит, и наш браузер
она тоже видит — но только когда окно действительно показано.

| момент | окон бота на экране |
|---|---|
| бот работает сам, режим `minimized` | **0** |
| бот работает сам, режим `offscreen` | **0** |
| человек нажал «показать окно бота» | 1, 1280×800 в (80, 80) |
| окно убрано, режим `minimized` | **0** |
| окно убрано, режим `offscreen` | **1, 1280×800 в (−930, 30)** |

Два вывода, и оба меняют картину, которая была у плана.

**Первое.** Пока окно не показывали человеку, его нет на экране НИ В ОДНОМ
режиме. Фоновая цель (`background: true`) при `--no-startup-window` создаёт
окно, которое оконный сервер не выводит вовсе. «Полоса в 350 пикселей» из Ф1
была ВЫВОДОМ ИЗ КООРДИНАТ, а не наблюдением: подрезанные `left: -930` при
ширине 1280 действительно дают 350 видимых пикселей — но только если окно
показано.

**Второе.** А вот ПОСЛЕ показа человеком разница решающая. Убрать окно «за
экран» на macOS нельзя: координаты подрезаются, и окно остаётся на виду до
конца встречи. Свернуть — можно. Один клик «покажи, что там у бота» в режиме
`offscreen` испортил бы весь оставшийся час.

## Троттлинг: риска нет, и это тоже измерено

Свёрнутое окно occluded, а Chrome троттлит таймеры рендерера occluded-окна до
секунды. Пять минут записи на свёрнутом окне (три дорожки, кадр раз в 20 мс,
то есть 150 кадров в секунду теоретических):

| величина | свёрнутое, 5 мин | за экраном, 1 мин | свёрнутое, 1 мин |
|---|---|---|---|
| кадров в секунду | **149,9** | 148,8 | 149,2 |
| максимальный разрыв между кадрами | **79 мс** | 44 мс | 62 мс |
| разрывов сэмпловых смещений (дырок в WAV) | **0** | 0 | 0 |
| `Page.captureScreenshot` | работает | работает | работает |

Троттлинг дал бы разрывы около 1000 мс и частоту в разы ниже. Его нет, потому
что нарезка кадров и VAD живут в `AudioWorkletProcessor`, то есть в
аудиопотоке, который троттлингу не подвержен в принципе; три флага
`--disable-*-throttling` остаются вторым эшелоном.

## Ловушка: Chrome ВРЁТ про состояние свёрнутого окна

`Browser.getWindowBounds` на macOS отвечает `windowState: "normal"` для окна,
которое реально свёрнуто и физически исчезло с экрана. Проверено, что дело
именно в отчёте, а не в команде:

- `maximized` и `fullscreen` тот же вызов отражает верно;
- попытка свернуть окно из полноэкранного даёт внятную ошибку протокола
  «To minimize a fullscreen window, restore it to normal state first» — то есть
  обработчик существует и проверяет состояние;
- оконный сервер подтверждает: после `minimize` окон на экране ноль.

**Следствие для тестов:** проверять сворачивание через `getWindowBounds`
нельзя — такой тест был бы заведомо красным на исправном коде. За поведением
следит модульный тест на состав CDP-вызовов
(`a_minimized_bot_returns_to_minimized_after_being_shown`), за фактом —
таблица выше, снятая один раз.

## Вторая ловушка: снимок сразу после сворачивания отказывает

`Page.captureScreenshot` в первые секунду-полторы после сворачивания отвечает
`Not attached to an active page`, дальше работает. Ассистированный вход
опрашивает снимок раз в несколько секунд, поэтому на нём это не сказывается, но
тест, снимающий кадр сразу после `prepare_and_navigate`, падал бы «через раз».
Живые тесты ждут появления первого снимка циклом.

## Что появилось в коде

- `PageSetup::window_mode` — режим применяется при подготовке страницы, ДО
  навигации (до создания вкладки окна нет вовсе, сворачивать нечего) и
  запоминается страницей;
- `CdpPage::set_hidden_mode` / `hidden_mode` — куда возвращать окно после
  показа человеку;
- `CdpPage::set_window_visible(false)` в режиме `minimized` СВОРАЧИВАЕТ окно
  вместо переноса за экран;
- `CdpPage::window_state` — чтение состояния (с оговоркой выше);
- `MeetConfig::window_mode` по умолчанию `minimized`; `offscreen` остаётся
  опцией для систем, где координаты не подрезаются.

`e2e_mock` идёт в дефолтном режиме окна, а не в удобном для теста: любая
регрессия сворачивания сразу видна на всех живых прогонах.

## Как повторить измерение

```bash
FORGE_MEET_E2E=1 FORGE_MEET_WINDOW_BENCH=1 \
  cargo test -p forge-meet --test window_mode -- --nocapture --test-threads=1
FORGE_CDP_LIVE=1 cargo test -p forge-cdp --test live_chrome a_minimized_window -- --nocapture
```

Проба оконного сервера — двадцать строк на Swift поверх
`CGWindowListCopyWindowInfo` с фильтром по pid, слою 0 и размеру больше
200×200. Разрешений не требует; `System Events` с атрибутом `AXMinimized`
требует «Функции Упрощённого доступа» и в этом окружении недоступен.
