# forge-meet, фаза 0: живая проба Яндекс Телемоста

Дата: 2026-08-14. Проба снята на реальной встрече (4 участника) через Chrome-расширение,
только чтение DOM и медиаэлементов, без патчинга WebRTC.

## Итог одной строкой

Телемост **НЕ отдаёт трек на участника**. Аудио приходит в фиксированный пул m-линий
(режим `Slots`), поэтому идентичность говорящего берётся ТОЛЬКО из DOM-индикатора.
Пер-трековая расшифровка как «почти идеальная диаризация» для Телемоста недоступна.

## Что измерено

### 1. CSP блокирует инъекцию инлайн-скрипта — CDP обязателен

Прямой тест: создание `<script>` с `textContent` и запись атрибута в `documentElement`.
Результат `cspBlocksInlineScript: true` — скрипт не выполнился.

Следствие: подход «расширение Chrome / контент-скрипт» для перехвата WebRTC
**нежизнеспособен**. Контент-скрипт живёт в изолированном мире и не видит
`window.RTCPeerConnection` страницы, а инъекция в главный мир режется политикой.
Остаётся только CDP с `Page.setBypassCSP(true)` ДО навигации — как и заложено в плане.

### 2. Аудио: пул слотов, а не трек на человека

На встрече 4 участника (Алексей Пруцков, Максим К., Игорь Г., Гость=бот).
Удалённых участников трое. Удалённых аудиоэлементов — **два**:

```
<audio class="goloom_mid_audio">  stream e236784a…  трек 0c0e603a  label "remote audio"  muted:false
<audio class="goloom_mid_audio">  stream 2d774802…  трек 4400fd01  label "remote audio"  muted:true
```

За 20 секунд наблюдения индикатор «говорит» загорался у ТРЁХ разных участников
(Максим К., Игорь Г., Алексей Пруцков), а `track.muted` обоих треков **не изменился ни разу**:
timeline `0c0e:~ 4400:M` постоянен на всех 20 отсчётах.

Вывод: речь всех участников идёт через один и тот же активный трек. Класс `goloom_mid_audio`
(`mid` = идентификатор m-линии в SDP) подтверждает: это пул m-линий, а не поток на участника.

Практические следствия для плана:
- атрибуция спикера строится на DOM-индикаторе, корреляция — основной путь, а не фолбэк;
- пер-трековая нарезка по VAD для Телемоста бессмысленна (трек один);
- в `label` треков имён нет — там буквально `"remote audio"`;
- захват остаётся пер-трековым механически (что дадут, то и пишем), но обоснование
  «трек = человек» для Телемоста не работает.

### 3. Индикатор активного спикера — найден

Внутри плитки участника лежит `div[class*="root"]`, который получает и теряет
дополнительный класс `[class*="rootStroke"]` — это обводка «сейчас говорит».
Ловится `MutationObserver` по `attributeFilter: ['class']`.

За 20 с — 11 переключений у трёх участников, что совпало с реальным разговором.

### 4. Селекторы (для `meet.probes.toml`)

Телемост использует CSS-модули с хешами (`item_NZ2DW`, `TextName_BOaIg`, `root_ypmDo`),
которые меняются при каждой пересборке фронта. Поэтому селекторы обязаны быть
**подстрочными**, а не точными — что и подтверждает решение держать их данными в TOML.

| Что | Селектор |
|---|---|
| Интерстишал «Продолжить в браузере» | `button.continueInBrowserButton_-wew`, надёжнее — по тексту |
| Кнопка входа | `[data-testid="enter-conference-button"]` |
| Микрофон выключен / включён | `[data-testid="turn-on-mic-button"]` / `[data-testid="turn-off-mic-button"]` |
| Камера | `[data-testid="turn-on-camera-button"]` / `turn-off-camera-button` |
| Панель участников | `[data-testid="participants-button"]` (текст содержит счётчик) |
| Завершить звонок | `[data-testid="end-call-alt-button"]` |
| Чат / демонстрация / рука | `chat-alt-button`, `start-demonstration-button`, `hand-up-button` |
| Сетка | `[class*="newGridContainer"]` |
| Плитка участника | `[class*="newGridItem"]`; модификаторы `selfView`, `itemDevices`, `itemDisplay` |
| Имя на плитке | `[class*="participantName"]`, внутри `[class*="TextName"]` |
| Статусы участника | `.participantStatuses` — **не хешируется**, стабилен |
| Обводка «говорит» | `[class*="rootStroke"]` на `[class*="root"]` внутри плитки |
| Удалённое аудио | `audio.goloom_mid_audio` — **не хешируется**, стабилен |

`data-testid` у кнопок панели не хешируются — это лучший вид селектора здесь.

### 5. Две ловушки входа

**Микрофон включается при подключении.** На пре-join экране микрофон был выключен
(кнопка предлагала «Включить микрофон»), после клика «Подключиться» в панели встречи
оказалась кнопка `turn-off-mic-button`, то есть микрофон стал включён.
Адаптер обязан гасить микрофон ПОВТОРНО после входа, а не только на пре-join.

**Залогиненный профиль меняет пре-join экран.** В профиле с активным Яндекс-аккаунтом
поля гостевого имени нет вовсе — показывается карточка аккаунта. При этом на плитке
самого себя имя оказалось «Гость». Адаптеру нужны ДВЕ ветки pre-join: гостевая (с полем
имени) и залогиненная. Продовый бот работает на чистом `--user-data-dir`, то есть по
гостевой ветке, но тестировать будут и на залогиненном профиле.

### 6. Прочее

- Интерстишал «Продолжить в браузере» показывается всегда; капчи на профиле не было.
- Координаты со скриншота не совпадают с координатами DOM (скриншот отмасштабирован):
  клик по координатам промахнулся, клик по элементу сработал. Для адаптера это довод
  в пользу `Input.dispatchMouseEvent` по вычисленному `getBoundingClientRect`, а не по
  координатам с картинки.
- `<audio>`/`<video>` со `srcObject` читаются даже из изолированного мира расширения —
  дешёвый путь для диагностики и e2e-тестов, но не для продового захвата.

## Что осталось непроверенным

- `getSynchronizationSources().audioLevel` и `getContributingSources()` — требуют доступа
  к `RTCPeerConnection`, то есть CDP. Проверяется на фазе 3.
- Растёт ли пул m-линий при большем числе одновременно говорящих (на пробе было 2).
- Поведение на чистом профиле без Яндекс-аккаунта (гостевая ветка pre-join).
