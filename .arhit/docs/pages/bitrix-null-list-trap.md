# Битрикс24: явный null на месте структуры обнулял ВЕСЬ список диалогов

Дефект найден живой проверкой Ф9 на двух фиктивных порталах и починен там же. Класс ошибки — из тех, что не ловятся типами и не видны в логе.

## Симптом

`GET /api/bitrix/dialogs` отвечает `200 {"dialogs":[]}`. Панель пустая. В логе НИ ОДНОЙ строки об ошибке. Портал при этом исправен и отдаёт чаты.

## Живое воспроизведение (стенд переключался служебным входом)

    entity_link = null       -> диалогов в панели: 0
    entity_link = false      -> диалогов в панели: 0
    entity_link = []         -> диалогов в панели: 2
    entity_link = {...}      -> диалогов в панели: 2
    entity_link отсутствует  -> диалогов в панели: 2

## Механика в трёх шагах, каждый из которых по отдельности безобиден

1. `plugins/bitrix/src/api/schema.rs`: поле объявлено как `#[serde(default)] pub entity_link: EntityLinkRaw` — НЕ `Option`. `#[serde(default)]` покрывает только ОТСУТСТВУЮЩИЙ ключ; явный `null` даёт `invalid type: null, expected struct`, то есть ошибку разбора ВСЕГО документа, а не одного поля. Пустой PHP-массив `[]` при этом проходит (serde принимает seq-форму структуры) — поэтому ловушка не видна глазами: в живом ответе `[]` и `null` стоят рядом и выглядят одинаково.
2. `plugins/bitrix/src/api/methods.rs`: ошибка глохла в `from_value::<Vec<RecentItemRaw>>(...).ok().unwrap_or_default()` — ни ошибки, ни лога, просто пустой вектор.
3. `plugins/bitrix/src/recent_sync.rs`: воркер пишет строку только при непустом результате, а нулевой проход — это и есть значение по умолчанию. Следа не остаётся вовсе.

Итог: ОДИН чат ронял не себя, а ВЕСЬ список.

## Почему это не поймали тесты

Фикстура `tests/fixtures/recent_get.json` содержит единственный чат — задачный, у него `entity_link` заполнен объектом. `tests/serde_traps.rs` перебирал полиморфные СКАЛЯРЫ (строка/число, строка/false), но вариант `null` для СТРУКТУРНЫХ полей не покрывал ни разу.

## Починка

1. `schema::nullable_default` — терпимый разбор вложенного поля: `null` и булево дают значение по умолчанию, всё остальное разбирается обычным путём и обычным путём краснеет. Ошибки НЕ глотаются целиком намеренно: молчаливое проглатывание любой ошибки вернуло бы ровно тот дефект, ради которого функция написана.
2. Применён ко ВСЕМ структурным полям строки списка, а не к одному `entity_link`: `recent[].chat`, `.message`, `.avatar`, `.user` и `chat.entity_link`, `.restrictions`, `.mute_list`, `.manager_list`. Чинить только найденное поле значило бы ждать следующего отчёта о пустой панели.
3. `methods::decode_part` заменил `from_value(...).ok()`: поведение при отказе то же (часть пакета пропадает, соседние доезжают — падать целиком из-за одного поля это ровно та крайность, от которой место и защищает), но отказ теперь ВИДЕН в логе. Текст ошибки проходит через `api::error::scrub_urls`: сообщение serde цитирует значение, а в сырье портала попадаются поля с кодом вебхука внутри (`downloadUrl`). Отсутствующий ключ отказом не считается и в лог не пишется — часть пакета могли просто не запрашивать (счётчики задач без известного `user_id`).

## Стражи

- `tests/serde_traps.rs::a_null_in_place_of_a_nested_object_must_not_wipe_the_whole_list` — ловушка 12: обе формы «значения нет» (`null` и `false`) на всех структурных полях, и требование, чтобы СОСЕДНЯЯ здоровая строка выжила. Плюс отдельная проверка, что обнулённые `restrictions` читаются как «писать можно», а не запирают поле ввода молча.
- `api::methods::tests::a_part_that_does_not_match_the_schema_is_logged_without_the_secret` — отказ виден в логе И не содержит ни кода вебхука, ни хоста портала.

## Правило на будущее

В этом крейте вложенное поле, объявленное СТРУКТУРОЙ (не `Option`), обязано идти с `deserialize_with = "nullable_default"`. JSON приходит из PHP, где «пусто» выражается то `[]`, то `null`, то `false`, причём соседние ключи одного объекта расходятся между собой.
