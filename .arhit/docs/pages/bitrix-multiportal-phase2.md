# Битрикс: мультипортальность, Фаза 2 — реестр порталов и жизненный цикл

Фаза 2 ввела plugins/bitrix/src/registry.rs и перевела все четыре точки входа плагина с ОДНОГО состояния на РЕЕСТР порталов.

## Что изменилось в публичном API forge-bitrix

Было (однопортально):
    let state = forge_bitrix::init(forge_bitrix::BitrixConfig::load())?;
    let app = forge_bitrix::register_routes(app, state.clone());
    forge_bitrix::spawn_workers(&state).await;
    forge_bitrix::shutdown(&state).await;

Стало:
    let registry = forge_bitrix::init(forge_bitrix::BitrixRootConfig::load())?;
    let app = forge_bitrix::register_routes(app, registry.clone());
    forge_bitrix::spawn_workers(&registry).await;
    forge_bitrix::shutdown(&registry).await;

Порядок регистрации в tmux-web/src/main.rs НЕ изменился: register_routes по-прежнему стоит ДО .fallback(static_embed::serve_static) и ДО .layer(...) — только при таком порядке bearer_auth и csrf_guard автоматически покрывают /api/bitrix/* и /ws/bitrix. Ошибка init для хоста по-прежнему НЕ фатальна: warn и старт без плагина.

Однопортальный graceful-путь остался публичным под именем forge_bitrix::registry::shutdown_portal — им пользуются интеграционные тесты, которые собирают B24State напрямую, без реестра.

## Сохранённые инварианты

- init синхронен и НЕ ходит в сеть (тест init_never_touches_the_network: конфиг с base_url_override на закрытый порт 1 отрабатывает быстрее 500 мс).
- spawn_workers возвращается немедленно — хост зовёт его ДО биндинга порта.
- shutdown идемпотентен и на реестре из нескольких порталов (тест shutdown_stops_every_portal_and_is_idempotent).
- Оба realtime-воркера каждого портала стартуют ВСЕГДА, даже без вебхука: ждут подключения на authorized_notify и до него сети не трогают. Это же свойство сохранено для портала, добавленного в рантайме.
- Удаление портала идёт полным путём: shutdown.cancel() + shutdown_workers() (две секунды на самостоятельный выход — воркер событий персистит курсор) + analysis.shutdown() (иначе процесс claude переживёт devforge).
- WebhookUrl по-прежнему без Serialize, содержимое только через expose(); единственное место сериализации секрета — save_portals_to.

## Ключевое архитектурное решение: список никогда не пуст

Реестр всегда держит минимум один слот. Свежая установка даёт слот с пустым вебхуком и пустым id — состояние not_configured и экран подключения, ровно как до мультипортальности. Пустой слот — не портал, а МЕСТО для портала: get() по пустому id не резолвится, connected() его не считает, add() его занимает, remove() последнего портала возвращает его на место.

Альтернатива (реестр, который бывает пустым) потребовала бы второго, безпортального режима роутов: у панели нет состояния, в котором ей нечего показать.

## Что осталось на Ф3 и дальше

- register_routes пока привязывает роуты к registry.primary(): роуты Ф2 всё ещё однопортальные и получают Arc<B24State> через with_state. Ф3 заменяет это экстрактором Portal поверх Arc<B24Registry>, после чего портал выбирает сам запрос (заголовок X-Forge-Portal), а не момент регистрации. До Ф3 состав реестра меняться не может — единственные точки входа для add/remove это роуты Ф4, которых ещё нет, — поэтому первый портал здесь не устаревает.
- purge_cache в remove() сносит каталог, ОТЛИЧНЫЙ от общего cache_dir и лежащий внутри него. До Ф6 пер-портальных подкаталогов нет, все порталы делят один каталог, и снести его значило бы стереть кэш соседей. Проверка сформулирована так, что после Ф6 (когда cache_dir станет пер-портальным) она заработает сама, без правки этого места.

## Новые примитивы конфига

Ф1 оставила save_webhook_to однопортальной (заменяет весь список одним порталом ради совместимости старого POST /api/bitrix/login/webhook), а clear_webhook_to — снимающей ОБА представления сразу. Ф2 добавила недостающие точечные операции: rename_portal_in (только title) и reorder_portals_in (порядок вкладок). Обе идут через save_portals_to и наследуют все четыре инварианта записи.
