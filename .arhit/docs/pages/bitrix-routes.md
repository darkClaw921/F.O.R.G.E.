# forge-bitrix — HTTP-поверхность и контракт ошибок

Элементная запись Фазы 1 для `plugins/bitrix/src/routes/mod.rs` и
`routes/error.rs` (префикс `bitrix-` обязателен: имя `routes` пересекается с
плагинами vk и telegram).

## Замороженная таблица путей

Полный список путей ВСЕХ фаз перечислен в шапке `routes/mod.rs` сразу — чтобы
имена не расползлись, когда роуты начнут добавляться по одному. Таблица —
источник истины для фронтового `js/bitrix/api.js`: расхождение даёт
молчаливый 404, а не ошибку сборки.

В Фазе 1 смонтированы только `GET /api/bitrix/status` и `GET /ws/bitrix`;
остальные группы подключаются своими фазами через `.merge(...)`, поэтому
сигнатура `build_router(state) -> Router` не изменится.

Решения, зафиксированные навсегда: `bitrix`, а не `bitrix24`; `dialogs`, а не
`chats` (диалог у портала — это и личная переписка, и групповой чат, и чат
задачи); задачи не заводят вторую вкладку (Р2); медиа разделено на
`/media/file/:dialog/:mid/:index` и `/media/avatar/:user_id`, потому что
аватар адресуется пользователем, а вложение — тройкой.

## `GET /api/bitrix/status` — 200 всегда

Единственный роут, отвечающий 200 в любом состоянии: по нему фронт решает,
показывать ли кнопку вкладки. `StatusDto{enabled, login, max_upload_bytes,
rate_limit_rps, capabilities, hint}`.

`capabilities` — честный список того, чего платформа НЕ умеет (входящее
«печатает», realtime-присутствие, realtime-правки, эмодзи-реакции, отражение
`reply_to` при чтении, пересылка) плюс то, чего нет у соседей (`tasks: true`).
Отдаётся с бэкенда, а не зашит во фронт: разметку браузер держит в кэше PWA
неделями, а состав ограничений зависит от редакции портала.

`hint` — подсказка «где взять вебхук» плюс предупреждение Р15 (вебхук
выпускается от имени одного сотрудника; в remote-mode все увидят его
переписку). Тоже с бэкенда и по той же причине.

**Чего здесь нет:** ни кода вебхука, ни его отпечатка, ни хоста портала.
Проверяется тестами `routes::tests::status_never_leaks_the_webhook_in_any_state`
(восемь состояний, `oneshot`) и
`bitrix_smoke::test_status_never_leaks_the_webhook_in_any_state` (то же по
проводу, по СЫРОМУ телу ответа — утечка через новое поле краснеет
автоматически).

## Лестница проверок для data-роутов (Ф4+)

Авторизация (409) → соединение (503) → резолв объекта (404) → разбор
параметров (400). Query разбирается ВРУЧНУЮ внутри хендлера, тело — через
`Option<Json<T>>`: экстракторы axum отработали бы ДО тела хендлера и отдали
400 раньше проверки авторизации, превратив роут в оракул валидности
идентификаторов портала.

## Конверт ошибок

`{"error":{code, message, retry_after_secs?}}` плюс стандартный заголовок
`Retry-After`, когда `retry_after_secs` присутствует. Необязательное поле не
сериализуется вовсе, поэтому старый фронт-разбор (`code` + `message`)
продолжает работать без правок.

Полная таблица (16 конструкторов, тест `the_error_table_is_frozen` ловит
переименование):

| HTTP | code | когда |
|---|---|---|
| 400 | `invalid_input` | `DIALOG_ID_EMPTY`, `MESSAGE_EMPTY`, `PARAMS_ERROR`, `*_ERROR`, текст >20 000 символов (Р12) |
| 404 | `unknown_dialog` / `unknown_message` / `unknown_task` / `no_media` | объекта нет |
| 409 | `not_authorized` | `INVALID_CREDENTIALS`, `NO_AUTH_FOUND` |
| 409 | `scope_missing` | `insufficient_scope` — вебхук исправен, но без прав |
| 409 | `unsupported_auth` | `WRONG_AUTH_TYPE` — метод требует OAuth-приложения |
| 409 | `invalid_state` | `CANT_EDIT_MESSAGE`, действие вне матрицы `action` |
| 409 | `send_forbidden` | `ERROR_NO_ACCESS`, `ACCESS_DENIED` |
| 411 | `length_required` | `POST /upload` без `Content-Length` |
| 413 | `too_large` | файл больше `max_upload_bytes` (тело НЕ читается) |
| 429 | `flood_wait` | `QUERY_LIMIT_EXCEEDED` или `OPERATION_TIME_LIMIT` |
| 501 | `method_unavailable` | `ERROR_METHOD_NOT_FOUND` — фронт прячет функцию, а не показывает сбой |
| 502 | `bitrix_error` | портал ответил ошибкой, которую не исправит ни ввод, ни повтор |
| 503 | `not_connected` | транспортный отказ, **пустое тело при HTTP 200**, обрыв TCP |

Две ловушки платформы, отражённые в таблице:

1. **Пустое тело при HTTP 200 — это троттлинг**, а не битый JSON: портал при
   превышении интенсивности иногда просто обрывает ответ. Такой случай обязан
   стать `not_connected` (503, повторяемо), а не `bitrix_error` (502, «чините
   ввод»).
2. **`OPERATION_TIME_LIMIT` блокирует КОНКРЕТНЫЙ метод**, а не весь портал, и
   автоповтор его только продлевает — ждать обязан пользователь.

Коды `409` бывают пяти разных смыслов, поэтому фронт принимает решения именно
по `code`, а не по HTTP-статусу.
