Login-роуты плагина Telegram (plugins/telegram/src/routes/login.rs, Фаза 2) + persist кредов.

ЭНДПОИНТЫ (все под /api/telegram):
- GET /status — единственный роут, отвечающий 200 в любом состоянии; по нему фронт решает, показывать ли кнопку ✈ (роут существует => плагин включён флагом --telegram). Тело: {enabled:true} + flatten LoginStateDto {state, phone, hint, error, user}. api_hash НИКОГДА не появляется в ответе (тест status_never_leaks_api_hash).
- POST /login/start {api_id?, api_hash?, phone}: валидация телефона (400 invalid_input) -> если переданы оба креда: save_credentials (atomic, 0600) + state.set_credentials + переход NotConfigured->Disconnected + clear_runtime (старый api_id больше не годится, а его lock мешает поднять новое соединение) -> ensure_runtime -> login::request_code. Половина формы (только api_id или только api_hash) -> 400 с подсказкой про my.telegram.org; api_id<=0 -> 400.
- POST /login/code {code} и POST /login/password {password}: валидация ввода -> backend_for -> переходы автомата. Пароль НЕ триммится (пробелы могут быть его частью), код триммится.
- POST /logout: best-effort auth.logOut (пока соединение живо) -> clear_runtime (освобождает lock сессии) -> удаление файла сессии и спутников (-wal/-shm/-journal; иначе следующий старт 'восстановит' отозванную авторизацию и будет получать AUTH_KEY_UNREGISTERED) -> Disconnected/NotConfigured. Успешен и идемпотентен из ЛЮБОГО состояния: пользователь нажал 'выйти', и UI обязан это отразить даже если Telegram не ответил.

ХЕЛПЕРЫ. backend_for(state) -> MtBackend: 409 invalid_state без кредов, 503 not_connected без живого рантайма. ensure_runtime(state): поднимает соединение, если его нет; при неудаче переводит автомат в Disconnected{error} (иначе UI показывал бы 'всё хорошо' без соединения) и отдаёт 503 с текстом причины.

КОНТРАКТ ОШИБОК в состоянии not_configured (обновлён в Фазе 2 — безусловной 409 больше нет): пустое тело шага логина -> 400 invalid_input; заполненное тело без кредов -> 409 invalid_state; data-роуты -> 409 not_authorized; logout -> 200. FLOOD_WAIT -> 429 {error:{code:'flood_wait', retry_after_secs}} + заголовок Retry-After, НИКОГДА не ретраится сервером (риск №2 плана).

save_credentials / save_credentials_to (config.rs). Инварианты: (1) read-modify-write — остальные поля пользовательского telegram.toml, включая незнакомые ключи, сохраняются; (2) права 0600 выставляются в момент создания файла ДО записи содержимого, поэтому секрет ни на мгновение не лежит с более широкими правами; (3) атомарность — tmp в том же каталоге + fsync + rename, читатель видит либо старый файл, либо новый, но никогда обрезанный; (4) при любой ошибке tmp удаляется, целевой файл не меняется. api_hash никогда не логируется — в лог идёт только api_id. Примитивы write_secret_file/set_owner_only/tmp_path_for переиспользует session::FileSession, чтобы 'атомарная запись секрета' существовала в одной реализации.

state.rs. AppCredentials{api_id, api_hash} + credentials: RwLock<Option<AppCredentials>> — ЕДИНСТВЕННАЯ изменяемая во время работы часть конфигурации (пользователь вводит креды в UI). config остаётся неизменяемым (пути, лимиты). effective_config() отдаёт снапшот 'конфиг + актуальные креды' для build_runtime; has_credentials()/credentials()/set_credentials() — источник истины для автомата логина. Плюс client()/has_runtime()/set_runtime()/clear_runtime() поверх runtime: RwLock<Option<TgRuntime>> (клиент дешёво клонируется, поэтому хендлеры берут копию и отпускают RwLock до похода в сеть).

РАНТАЙМ-ПРОВЕРКА (изолированный HOME + порт 17431): пустое тело -> 400 phone is required; только телефон -> 409 invalid_state; половина кредов -> 400; фальшивые креды -> реальный ответ Telegram API_ID_INVALID -> 400 invalid_input (никаких 500/паник), telegram.toml с правами -rw-------, api_hash в логах отсутствует; после рестарта сессия читается с диска (5 DC) и статус честно становится disconnected; второй процесс с той же сессией сообщает про занятый lock, первый жив.
