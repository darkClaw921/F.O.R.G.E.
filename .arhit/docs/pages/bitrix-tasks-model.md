# forge-bitrix — модель задач (Ф10)

Вторая ключевая часть плагина после переписки: директория `~/tasks`,
карточка-шапка над лентой, ряд кнопок действий и два независимых семейства
счётчиков.

## ГЛАВНЫЙ АРХИТЕКТУРНЫЙ ФАКТ

**Чат задачи Bitrix24 — обычный IM-чат** с `entity_type = "TASKS_TASK"` и
`entity_id = <task_id>`. Комментарии задачи и сообщения её чата — ОДИН И ТОТ
ЖЕ поток. Доказано живьём двумя способами записи в задачу 1:

```
im.message.add       {DIALOG_ID:"chat7", MESSAGE:"PROBE-B"}          -> 63
task.commentitem.add {TASKID:1, FIELDS:{POST_MESSAGE:"PROBE-C"}}     -> 65
im.dialog.messages.get {DIALOG_ID:"chat7"}  -> обе строки, 65 и 63
```

`task.commentitem.add` возвращает идентификатор СООБЩЕНИЯ ЧАТА, а не отдельной
сущности комментария: дублирования нет, потому что сущность одна.

**`task.commentitem.getlist` МЁРТВ**: возвращает `[]` и до, и после добавления
комментария, при четырёх сообщениях в чате. Он читает форумную таблицу, а на
портале с «новыми задачами» форума нет вовсе — у задачи `forumTopicId: null` и
`forumId: null`. Единственный путь к комментариям — `im.dialog.messages.get`.

Отсюда всё устройство фазы:

* «Задачи» — НЕ второй мессенджер, а директория ОДНОГО списка диалогов (Р2)
  плюс обогащённая ШАПКА над той же лентой;
* второй вкладки в `#settings-bar` нет намеренно;
* ленту рисует тот же движок (`routes/dialogs.rs`, `js/bitrix/chat.js`), что и
  обычный чат.

## Цепочка связи task_id ↔ chat_id ↔ dialog_id

```
tasks.task.get              → поле chatId          (task 1 → 7, task 3 → 9)
im.chat.get{TASKS_TASK, id} → {"ID": 7}            (обратный/запасной путь)
DIALOG_ID                   = "chat" + chatId      (правило платформы)
im.dialog.get{"chat7"}      → entity_type/entity_id (проверка в обратную сторону)
```

Индекс живёт в `plugins/bitrix/src/tasks.rs::TaskIndex` (поле
`B24State::task_index`). Он держит по задаче её чат и её матрицу прав и
существует ради ОДНОГО требования: **действие, запрещённое матрицей, обязано
отвергаться БЕЗ обращения к порталу**. Карточка уже на экране в момент нажатия
кнопки — значит матрица прочитана, и спрашивать её второй раз, чтобы ответить
«нельзя», означало бы тратить один из двух запросов в секунду впустую.

Обратное направление (`chat_id → task_id`) нужно ленте: по открытому `chatN`
панель понимает, какую карточку показывать над ним.

Индекс — НЕ кэш ответов: карточка всегда читается у портала заново (статус мог
измениться в чужом браузере). Ёмкость 512 записей, вытеснение самой старой.

## ТРИ ЛОВУШКИ ПЛАТФОРМЫ

Все три опасны одинаково: они дают не ошибку, а **МОЛЧАЛИВУЮ ПУСТОТУ** —
успешный HTTP 200, внутри которого ничего нет. Снаружи это неотличимо от
честного «данных нет», поэтому такая ошибка живёт месяцами.

| № | ошибка | что видит пользователь | что отвечает портал | страж |
|---|---|---|---|---|
| 1 | `ENTITY_TYPE = "TASKS"` | у задач никогда не открывается лента | `{"result":null}`, HTTP 200 | `the_entity_type_is_never_the_bare_tasks`, `no_source_line_passes_the_bare_tasks_entity` |
| 2 | camelCase в `select` | у задач нет чатов, сроков, статусов | поле `null` — как настоящий `null` | `the_select_never_carries_a_camel_case_name`, `the_frozen_select_table_is_uppercase_only` |
| 3 | ключ `STATUS` в фильтре | директория задач пуста | `total: 0`, HTTP 200 | `the_task_filter_never_carries_the_bare_status_key`, `a_poisoned_filter_is_refused_before_the_network` |

Все стражи — в `plugins/bitrix/tests/tasks_traps.rs`. Каждый проверен на
умышленном возврате к неверному варианту: шесть из десяти тестов краснеют.

### Ловушка 1 — `ENTITY_TYPE`

Живой замер на `test-work-2.bitrix24.ru`:

```
im.chat.get {ENTITY_TYPE:"TASKS",      ENTITY_ID:"1"} -> {"result":null}
im.chat.get {ENTITY_TYPE:"TASKS_TASK", ENTITY_ID:"1"} -> {"result":{"ID":7}}
```

Ответ на неверную сущность — успешный HTTP 200 с `null`, то есть ровно то же,
что портал отвечает на «у задачи нет чата». Защита двойная:

1. значение НЕ ПАРАМЕТР обёртки — `B24Client::task_chat_id(task_id)` не
   принимает сущность вовсе, единственный источник — `dto::ENTITY_TASK`;
2. страж по исходникам запрещает литерал `"TASKS"` в боевом коде (тесты
   отсечены: там `TASKS` — законное имя ПРАВА вебхука, `scope`).

`null` разбирается как `Ok(None)` — «чата нет», а не «чат с номером 0». Иначе
задача получила бы `dialog_id = "chat0"`, по которому портал отвечает отказом.

### Ловушка 2 — `select`

Имена полей в `select` — это имена v1 в UPPER_SNAKE (`CHAT_ID`,
`RESPONSIBLE_ID`), а в ОТВЕТЕ те же поля приезжают camelCase (`chatId`,
`responsibleId`). camelCase в `select` портал МОЛЧА игнорирует:

```
select:["ID","chatId","status"] -> {'chatId': None, 'status': None}
select:["ID","CHAT_ID","STATUS"] -> {'chatId': 7, 'status': '2'}
```

Пустое значение неотличимо от настоящего `null`. Поэтому:

* **карточка (`tasks.task.get`) зовётся БЕЗ `select` вовсе** — без него портал
  отдаёт всё (71 поле), и угадывать регистр не нужно;
* **список (`tasks.task.list`) зовётся со `select`** из замороженной таблицы
  `tasks::LIST_SELECT` — все имена UPPERCASE, `CHAT_ID` обязателен (без него
  лента задачи не открылась бы из директории).

### Ловушка 3 — фильтр

`STATUS` у задач — псевдополе: оно пересекается с виртуальными состояниями
(`subStatus`). Живой замер:

| фильтр | результат |
|---|---|
| `{"RESPONSIBLE_ID":1}` | 2 задачи |
| `{"REAL_STATUS":2}` | 2 задачи |
| `{"<REAL_STATUS":5}` | 2 задачи |
| `{"<STATUS":5}` | 2 задачи |
| `{"STATUS":2}` | **0 задач** |
| `{"RESPONSIBLE_ID":1,"STATUS":2,"GROUP_ID":0}` | **0 задач** |

Ключ `STATUS` отвергается `api::methods::task_list_params` ДО СЕТИ
(`B24Error::Decode` с подсказкой про `REAL_STATUS`): молча подменить ключ
нельзя — запрос вернул бы не то, что просили, — а отправить заведомо пустой
ответ тем более.

## Таблицы статусов и приоритетов

Статусы — числовые коды v1, приходят СТРОКОЙ (`"2"`):

| код | подпись | ключ CSS |
|---|---|---|
| 1 | Новая (служебный) | `new` |
| 2 | Ждёт выполнения | `pending` |
| 3 | Выполняется | `in_progress` |
| 4 | Ожидает контроля | `review` |
| 5 | Завершена | `completed` |
| 6 | Отложена | `deferred` |
| 7 | Отклонена | `declined` |

Проверено живьём: `2 → tasks.task.start → 3 → tasks.task.pause → 2`. Подпись
«Ждёт выполнения» для `status:"2"` подтверждена гридом системного сообщения в
чате задачи.

`is_closed(status)` = `status >= 5`. Ровно по этому признаку считается
**просрочка**: отдельного поля у портала НЕТ, признак вычисляется как
`deadline < now && status < 5`. Правило живёт ТОЛЬКО на сервере
(`tasks::task_from_raw`), фронт читает готовый `overdue` — второй экземпляр
правила разъехался бы с первым.

Приоритеты: `0` низкий, `1` средний (дефолт портала), `2` высокий.
Отсутствующее значение — «средний», а не «неизвестный».

`subStatus` (`"-1"` = «нет») приходит только в СПИСКЕ, в карточке его нет.

## Матрица `action` — её нельзя захардкодить

Портал присылает в карточке готовый набор булевых флагов (26 ключей живьём):

```json
"action": {"complete":true,"start":true,"pause":false,"delegate":true,
           "defer":true,"renew":false,"edit":true,"remove":true,
           "changeDeadline":true,"rate":true,"take":false,"approve":false,
           "accept":false,"decline":false,"checklist.add":true, …}
```

Матрица **ДИНАМИЧНА**: после `tasks.task.start` становится
`start:false, pause:true, defer:false`, после `pause` возвращается обратно.
Именно поэтому при разведке `tasks.task.defer` на выполняющейся задаче оказался
no-op — портал молча ничего не сделал.

Отсюда три правила:

1. кнопки рисуются СТРОГО по флагам `true` (`TaskDto::actions`);
2. действие с флагом `false` отвергается `409 invalid_state` **до** обращения
   к порталу — решение принимается по `TaskIndex`;
3. набор действий не перечисляется во фронте, он приезжает с карточкой.

Ключи бывают составными (`edit.originator`, `checklist.reorder`,
`dayplan.timer.toggle`) — точка в них законна, и валидатор `:action` это
учитывает.

### «Умеет ли панель» ≠ «можно ли сейчас»

`tasks::ACTION_METHODS` — таблица «действие → семантический метод портала».
Она отвечает на ПЕРВЫЙ вопрос, матрица — на второй. Разные ответы дают разные
коды и ведут пользователя в разные места:

| ситуация | ответ | смысл для пользователя |
|---|---|---|
| действия нет в `ACTION_METHODS` | `501 method_unavailable` | «откройте задачу в Битриксе» |
| действие есть, но флаг `false` | `409 invalid_state` | «сделайте сначала что-то другое» |
| имя действия — мусор | `400 invalid_input` | ошибка клиента |

Панель выполняет семь действий: `start`, `pause`, `complete`, `defer`,
`renew`, `approve`, `disapprove`. Намеренно НЕ выполняет: `edit` и
`changeDeadline` (нужна форма редактирования), `delegate` (нужен выбор
сотрудника, а scope `user` вебхуку не выдают), `remove` (безвозвратен),
`rate` / `checklist.*` / `favorite.*` (сущностей нет в панели). Всё это
остаётся доступным по ссылке «открыть в Битриксе»: панель — мессенджер с
шапкой задачи, а не второй интерфейс задач.

Семантические методы предпочтительнее `tasks.task.update {STATUS: …}`: они
проводят бизнес-логику портала (контроль, оценка) и пишут в чат ПРАВИЛЬНОЕ
системное сообщение.

## После действия карточка и лента ПЕРЕЗАПРАШИВАЮТСЯ

Смена статуса пишет в чат задачи системное сообщение (`author_id: 0`):

```
87 | author 0 | '[USER=1]Игорь Герасимов[/USER] начал выполнять задачу'
```

Поэтому ответ `POST /api/bitrix/tasks/:id/:action` несёт:

* `task` — СВЕЖУЮ карточку, перечитанную у портала (матрица уже другая;
  собрать её локально невозможно — правила знает только портал);
* `dialog_id` — диалог, чью ленту фронт обязан перезапросить.

Ждать realtime нельзя: событий задач вебхуку не приходит вовсе, а
фолбэк-синхронизация приедет через минуту. Дополнительно рассылается WS-кадр
`task_update` — им перерисовываются ОСТАЛЬНЫЕ открытые вкладки.

## Р20 — ветка «задача без чата»

`chatId` приходит нулём, `null` либо строкой `"0"`. Это ОБЯЗАТЕЛЬНАЯ ветка:

* карточка отдаётся ЦЕЛИКОМ, `chat_id` и `dialog_id` остаются `null`;
* `im.chat.get` НЕ вызывается — у задачи без обсуждения спрашивать нечего;
* фронт рисует карточку без ленты с подписью «Обсуждение задачи ещё не
  начато», поле ввода и кнопка отправки блокируются;
* действия при этом ДОСТУПНЫ — они не требуют переписки.

Единственное исключение: ПОСЛЕ успешного действия портал пишет системное
сообщение, то есть создаёт чат. Если карточка о нём ещё не знает, чат
добирается вторым путём (`im.chat.get {ENTITY_TYPE:"TASKS_TASK"}`) — без этого
первое же действие над свежей задачей оставило бы пользователя без ленты до
перезагрузки.

**ЖИВАЯ ПРОВЕРКА (2026-08-06).** На `test-work-2.bitrix24.ru` создана задача 5
(`tasks.task.add`). Портал выдал `chatId: 31` СРАЗУ при создании, а в чате уже
лежало системное сообщение «создал задачу» с богатым `params.ATTACH` (грид
Статус / Постановщик / Исполнитель / Крайний срок). **Вывод: на этом портале
ветка «задача без чата» естественным путём не наступает — она защитная.**
Проверяется на стенде тремя тестами (`a_task_without_a_chat_never_asks_the_
portal_for_one`, `a_chat_that_appears_later_is_picked_up_after_an_action`,
`a_chatless_task_still_shows_up_in_the_list`).

**ПОДТВЕРЖДЕНО НА ПРИЁМКЕ Ф12 (2026-08-06).** Повторно, на свежесозданной
задаче 7: `tasks.task.add` снова вернул `chatId: 35` в том же ответе. Ветка
остаётся защитной и живьём на этом портале не воспроизводится — её единственное
покрытие тестами стенда, и это осознанное состояние, а не пробел приёмки.

## Пагинация

`tasks.task.list` отвечает `{"result":{"tasks":[…]}, "total": N}` — **`total`
лежит РЯДОМ с `result`**, а не внутри, и берётся из конверта
(`B24Response::total`). Параметра `LIMIT` у метода нет вовсе: страница
ФИКСИРОВАНА пятьюдесятью записями, листается смещением `start = (N-1)*50`.
Произвольный `start` защёлкивается на границу страницы — иначе вторая страница
содержала бы строки, уже показанные на первой.

`start: -1` отключает подсчёт `total` (ответ приезжает без него) — поэтому
`total` в DTO это `Option`, и выдавать за него ноль нельзя.

Матрицы `action` в списке НЕТ вовсе — только в карточке. Поэтому пустая
матрица из списка НЕ затирает матрицу, прочитанную карточкой
(`TaskIndex::remember`), иначе после обновления списка все действия оказались
бы запрещены.

## ДВА семейства счётчиков, которые нельзя складывать

| что считает | метод | обнуляется | поле DTO |
|---|---|---|---|
| непрочитанные СООБЩЕНИЯ чатов задач | `im.counters.get` → `TYPE.TASKS_TASK` | чтением ленты | `CountersDto::tasks` |
| СОСТОЯНИЕ задач: просрочена, новые комментарии, упоминания | `tasks.task.counters.get {userId}` | действием над задачей | `TaskCountersDto` |

Живые ответы:

```json
tasks.task.counters.get -> {"expired":{"counter":2},"new_comments":{"counter":0},
                            "mentioned":{"counter":0}}
im.counters.get         -> {"TYPE":{"ALL":9,"NOTIFY":5,"CHAT":0,"DIALOG":4,
                                    "MESSENGER":4,"TASKS_TASK":0}}
```

Просроченная задача может не иметь ни одного непрочитанного комментария, а чат
задачи — светиться непрочитанным без всякой просрочки. Сложенный бейдж нельзя
обнулить ни чтением, ни закрытием задачи — то есть он «горит» навсегда, и
пользователь перестаёт на него смотреть. Поэтому в состоянии две РАЗНЫЕ ячейки
(`B24State::counters` и `B24State::task_counters`).

Директория `~/tasks` светится числом `TYPE.TASKS_TASK` — она показывает
непрочитанные СООБЩЕНИЯ. Состояние задач показывается в карточке и в строке
списка (метка просрочки, бейдж `newCommentsCount`).

Р13: `NOTIFY` (уведомления портала) входит в общий бейдж вкладки, но отдельной
директории под него в v1 нет.

Оба семейства тянет фолбэк-воркер `recent_sync` ОДНИМ пакетом — третьей
командой того же `batch`. Внешний пакет стоит один хит лимита интенсивности
независимо от числа команд внутри, поэтому счётчики задач достаются бесплатно;
отдельный запрос стоил бы половины бюджета в 2 rps каждую минуту.

## HTTP-поверхность

| метод | путь | что делает |
|---|---|---|
| GET | `/api/bitrix/tasks?filter&start&responsible&group` | страница задач |
| GET | `/api/bitrix/tasks/counters` | оба семейства счётчиков |
| GET | `/api/bitrix/tasks/:id` | карточка (БЕЗ `select`) |
| POST | `/api/bitrix/tasks/:id/:action` | действие по матрице |

`/tasks/counters` — СТАТИЧЕСКИЙ сегмент рядом с `/:id`. У `matchit` статика
приоритетнее параметра, но полагаться на это молча нельзя: перепутанный
приоритет увёл бы счётчики в разбор идентификатора задачи, а тот ответил бы
`404 unknown_task` — бейдж просто перестал бы обновляться, без единой ошибки.
Есть тест `the_counters_route_is_not_shadowed_by_the_id_route`.

Пресеты фильтра (`all | mine | active | expired | closed`) собираются на
сервере: подпускать фронт к сборке фильтра портала означало бы однажды
получить пустую директорию из-за ключа `STATUS`. Открытость выражается
операторной формой `<REAL_STATUS: 5`, закрытость — прямым `REAL_STATUS: 5`.

Лестница проверок та же, что у диалогов: `409` (не подключён) → `503` (нет
связи) → `404` (нет такой задачи) → `400` (разбор параметров). Query
разбирается ВРУЧНУЮ: типизированный экстрактор отработал бы ДО тела хендлера
и вернул бы `400` раньше `409`, превратив роут в оракул валидности
идентификаторов портала.

**«Задачи нет» — это НЕ ошибка портала.** На `taskId: 999999` он отвечает
`{"result": []}` — успехом с пустым PHP-массивом (проверено живьём). Поэтому
`B24Client::task_get` возвращает `Option`, а роут превращает пустоту в
`404 unknown_task`, а не в `502 bitrix_error`.

## Ссылка «открыть в Битриксе»

`TaskDto::url` — АБСОЛЮТНЫЙ адрес задачи в интерфейсе портала:

```
https://<хост>/company/personal/user/<responsible_id>/tasks/task/view/<id>/
```

Форма подтверждена живьём (`entity_link.url` чата задачи). Хост берётся из
`WebhookUrl::portal_origin()` — это единственная часть вебхука, которую можно
показывать пользователю (он и так видит её в адресной строке Bitrix24).
**Кода вебхука в адресе нет и быть не может**; страж —

## Фронт

| файл | что делает |
|---|---|
| `js/bitrix/tasks.js` | карточка-шапка `#b24-task-card`, кнопки, действия, Р20 |
| `js/bitrix/format.js` | чистые функции: `taskActionLabel`, `taskDeadlineLabel`, `taskOfDialog`, `taskNoChatNote` |
| `js/bitrix/dialogs.js` | статус-точка, метка просрочки и бейдж `newCommentsCount` в строке задачи |
| `js/bitrix/api.js` | `getTasks`, `getTask`, `getTaskCounters`, `taskAction` |
| `js/bitrix/main.js` | связка: `showTaskFor` при выборе диалога, `applyTaskUpdate` из WS, перезапрос ленты после действия |
| `css/bitrix.css` | карточка, статус-точки по семи статусам, ряд кнопок, заблокированный prompt |

Карточка ПРЯЧЕТСЯ для обычного чата: оставленная шапка чужой задачи над чужой
лентой — самая дорогая ошибка модуля, потому что кнопки в ней рабочие.

Статус-точка в строке колонки берётся из `b24State.tasks` (карточки,
загруженные при входе в `~/tasks`), а не из строки списка: `im.recent.get`
про статусы задач не знает ничего. Пока карточки нет, точка нейтральна — это
честнее, чем угадать статус.

`409 invalid_state` во фронте — не сбой, а признак устаревшей кнопки (статус
мог поменяться в чужом браузере): карточка тут же перечитывается, и
пользователь видит актуальный набор.
