ТРИ ВЛАДЕЛЬЦА КЛАВИАТУРЫ: как vim-навигация devforge уживается с панелями мессенджеров.

## Проблема

static/hotkeys.js занимает j/k/h/l/g/1/2/3/? ГЛОБАЛЬНО (сессии в сайдбаре, переключение вкладок). Панели Telegram, VK и Битрикс24 используют ровно те же клавиши для своих чатов и сообщений. Без арбитража одно нажатие 'j' и листало бы беседы, и уводило фокус на сессию в сайдбаре.

## Контракт

Каждая панель публикует в своём initKeynav():

  window.ForgeApp.telegramKeys = {owns, enabled, invalidate}   // js/telegram/keynav.js
  window.ForgeApp.vkKeys       = {owns, enabled, invalidate}   // js/vk/keynav.js
  window.ForgeApp.b24Keys      = {owns, enabled, invalidate}   // js/bitrix/keynav.js

hotkeys.js спрашивает owns() у каждой панели в panelOwnsKeys(). Единственная точка вызова — третья строка vimAction().

## РЕЕСТР (введён на третьей панели)

До Битрикс24 имена контрактов были захардкожены списком PANEL_KEY_CONTRACTS, и комментарий рядом обещал реестр «когда появится третья панель». Она появилась, и реестр введён:

  window.ForgeApp.keyboardOwners = ['b24Keys', ...]   // МАССИВ имён контрактов

Панель дописывает себя сама (js/bitrix/keynav.js::registerKeyboardOwner), а hotkeys.js::panelKeyContracts(app) читает массив ЛЕНИВО в момент нажатия и объединяет с засевом LEGACY_PANEL_KEY_CONTRACTS = ['telegramKeys','vkKeys']. Четвёртая панель этот файл уже не тронет вовсе.

Почему МАССИВ в ForgeApp, а не объект с register(), живущий в hotkeys.js: этот файл — классический скрипт, он исполняется РАНЬШЕ модулей, а js/public-api.js затем ЗАМЕНЯЕТ window.ForgeApp целиком. Всё, что hotkeys.js положил бы туда на старте, было бы стёрто. Массив, читаемый лениво, от порядка загрузки не зависит: кто первым дошёл — тот его и создал, а регистрация происходит при входе на вкладку, то есть заведомо позже public-api.js.

Почему две прежние панели остались ЗАСЕЯННЫМИ, а не регистрируются сами: регистрация потребовала бы правки работающих js/telegram/keynav.js и js/vk/keynav.js — чужого кода, менять который ради нуля пользовательской выгоды правило проекта запрещает. Реестр их ДОПОЛНЯЕТ, а не заменяет.

Деградация реестра: не-массив игнорируется целиком (поведение как до фичи), не-строки/пустые строки/повторы пропускаются, имя без контракта пропускается молча (панель ещё грузится).

## Кто отвечает true

owns() каждой панели = её пейн видим И её оверлеи закрыты (логин; у VK ещё и CAPTCHA) И её тумблер включён И (фокус внутри её пейна ИЛИ фокус нигде). Одновременно ответить true панели не могут: switchTab держит непогашенным ровно один пейн. Кликнув в сайдбар сессий, пользователь ВОЗВРАЩАЕТ СЕБЕ vim — это осознанное правило, а не побочный эффект.

## Деградация

Контракты появляются только после загрузки ES-модулей, а hotkeys.js выполняется раньше них. До тех пор panelOwnsKeys() отвечает false — поведение совпадает с тем, что было до фичи. Так же обрабатываются: отсутствие window.ForgeApp, контракт без owns(), исключение внутри owns() (перебор ПРОДОЛЖАЕТСЯ — сломанная панель не повод отнимать навигацию у остального интерфейса) и любой не-true ответ (сравнение строгое: случайный truthy не должен молча съедать клавиши).

## Гейты настроек (легко перепутать)

  cmd_hints_enabled        === true   (дефолт ВЫКЛ, сам hotkeys.js)
  telegram_hotkeys_enabled !== false  (дефолт ВКЛ)
  vk_hotkeys_enabled       !== false  (дефолт ВКЛ)
  bitrix_hotkeys_enabled   !== false  (дефолт ВКЛ)

## Service worker

hotkeys.js раздаётся стратегией stale-while-revalidate (sw.js::isStaticAsset), поэтому любая его правка ТРЕБУЕТ бампа CACHE_VERSION: без бампа первый reload после обновления выполнит СТАРУЮ копию, и она будет молча воровать j/k у новой панели. История бампов: v2 — гейт cmd_hints_enabled, v3 — гейт telegram, v4 — гейт vk, v10 — РЕЕСТР keyboardOwners (v5-v9 бампались по другим причинам, см. комментарии в sw.js). Вторая независимая причина бампа в v4 и v5: index.html отдаётся через navigationStrategy из SHELL_CACHE под ключом '/', то есть разметка новой панели тоже приехала бы старая.

## Тесты

tmux-web/tests/frontend/hotkeys_panel_owner.test.mjs (27 ассертов) — единственное автоматическое покрытие арбитража: vim уступает, когда владеет ЛЮБАЯ панель; забирает клавиши обратно, когда не владеет ни одна; деградирует на сломанном контракте; и отдельная секция на РЕЕСТР — панель вне реестра невидима для vim, зарегистрированная видна, засеянные имена продолжают работать, мусор в реестре пропускается.
