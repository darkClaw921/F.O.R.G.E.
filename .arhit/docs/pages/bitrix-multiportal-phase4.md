# Мультипортальность Битрикс24 — Фаза 4: роуты управления порталами

CRUD состава порталов поверх B24Registry плюс перевод старых роутов подключения на адресуемый портал.

## Что появилось

Новый модуль plugins/bitrix/src/routes/portals.rs, смонтированный в build_router через .merge(portals::router()):

| метод | путь | что делает |
|---|---|---|
| GET | /api/bitrix/portals | список вкладок {id,title,connected,login,unread} в порядке реестра |
| POST | /api/bitrix/portals | подключить портал по вебхуку (тело {webhook, title?}) |
| PATCH | /api/bitrix/portals/:pid | {title?, order?} — переименовать и/или переставить |
| DELETE | /api/bitrix/portals/:pid?purge_cache=1 | отвязать портал |

Новый примитив записи config::replace_portal_webhook_in.

## Пять решений фазы

1. **Хост портала в ответах НЕ отдаётся.** Задача Ф4.1 разрешала отдавать host, но GET /api/bitrix/status намеренно не отдаёт его ни в одном состоянии автомата и охраняет это замороженным тестом status_never_leaks_the_webhook_in_any_state. Два соседних по смыслу роута с противоположными правилами про одно и то же поле разъедутся при первой правке, поэтому правило единое: хост вебхука не пересекает границу HTTP. Вкладке он не нужен — узнаваемое имя несёт id, поверх него пользователь ставит title, а разница между id и хостом это доменный суффикс, у коробочного портала как раз внутреннее имя инфраструктуры. Следствие для фронта Ф8: пустой title показывается как id, а НЕ как хост (доккомментарий PortalIdentity::title поправлен).

2. **Фильтр пустых слотов — по portal_id, а не по registry.connected().** connected() смотрит на КОНФИГОВЫЙ вебхук, а он у только что занятого пустого слота ещё пуст (вебхук туда кладёт set_webhook, рантаймовое поле). Взяв готовую connected(), мы получили бы панель, которая уже работает с порталом, но не показывает его вкладку до перезапуска devforge. portal_id реестр присваивает вместе с секретом, им же вкладка адресуется заголовком — «слот, который нельзя назвать» это ровно «слот, которого во вкладках быть не должно».

3. **logout отвязывает ОДИН портал.** clear_webhook_to снимает и legacy-ключ, и весь массив [[portals]] — при одном портале разницы не было, со строкой вкладок «выйти» на одной вкладке отключало бы все. logout переведён на B24Registry::remove(id, purge_cache=false), то есть на тот же путь, что DELETE /portals/:pid. clear_webhook_to остаётся в config для миграции и тестов. Полного «выйти отовсюду» отдельным жестом нет: фронт зовёт logout по каждой вкладке, а один необратимый жест, снимающий всё разом, стоит ровно один промах мимо кнопки.

4. **login/webhook больше не переписывает список целиком.** Симметричная дыра: save_webhook_to ЗАМЕНЯЕТ весь список одной записью, то есть подключение на одной вкладке стирало бы секреты остальных. Развилка по ХОСТУ: тот же хост и другой код это перевыпуск вебхука, то есть та же вкладка (replace_portal_webhook_in сохраняет id, title и позицию); пустой слот или другой хост это подключение нового портала (registry.add), причём старая вкладка остаётся — вставить чужой вебхук в чужую вкладку не значит потребовать удалить её портал.

5. **Автоповторов нет ни при каких условиях.** Портал душит интенсивность состоянием throttled (Р16), автоповтор его только продлевает. Повтор всегда инициирует пользователь, он видит retry_after_secs.

## Две попутные починки

- **registry.add больше не выставляет занятому пустому слоту disconnected.** set_login рассылает кадр login_state, и на живом экране подключения пользователь видел вспышку «нет связи» между вставкой вебхука и первым checking. Автомат двигает проверка, которую делает вызывающий роут и которая начинается с checking.
- **registry.remove восстанавливает пустой слот безусловно.** Раньше он поднимался через build_state, а тот валидирует общие настройки: провались валидация — реестр остаётся ПУСТЫМ, и экстрактор портала отвечает 503 на каждый запрос, включая /status, то есть панель не может показать даже экран подключения, чтобы пользователь исправил положение. Теперь при неудаче слот поднимается напрямую через B24State::new: валидность ему не нужна, пока в него не вставили вебхук.

## Что осталось следующим фазам

- Ф5: кадр portals и поле portal_id во всех кадрах WS — сейчас список вкладок обновляется только ответом роутов.
- Ф6: пер-портальные подкаталоги кэша. До них purge_cache осознанно НЕ сносит общий каталог (тест purge_cache_refuses_to_wipe_the_shared_cache_directory фиксирует границу).
- Ф7: unread с учётом фильтра видимости портала — сейчас это dialogs_unread() из снимка счётчиков.
- Ф8.2: обёртки CRUD и заголовок X-Forge-Portal в static/js/bitrix/api.js. Сами ПУТИ в таблице замороженного контракта routes/mod.rs уже есть (пометка МП), контрактный тест bitrix_contract.test.mjs 28/28 зелёный.

## Тесты

plugins/bitrix/tests/portals_crud.rs — 23 HTTP-теста на герметичном стенде (127.0.0.1:0 + base_url_override): пустой список свежей установки при непустом реестре, отсутствие секрета и хоста в ответах, порядок вкладок, добавление и его откат при мусоре, идемпотентность по URL, суффикс при коллизии id, переименование, перестановка, 404 на неизвестный pid для PATCH и DELETE, адресность отвязки, 404 по заголовку удалённого портала, выживание процесса после отвязки последнего, перевыпуск вебхука, чужой хост в чужой вкладке, обе формы логаута.
