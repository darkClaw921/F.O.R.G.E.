# bitrix-throttle — два независимых лимита Bitrix24 (`plugins/bitrix/src/api/throttle.rs`)

Портал ограничивает работу по двум осям сразу. Это НЕ одна настройка с двумя
порогами, а два разных механизма с разной реакцией — путать их нельзя.

| | 1. Интенсивность | 2. Ресурсоёмкость (`operating`) |
|---|---|---|
| Считается на | портал + IP | **метод + вебхук** |
| Модель | leaky bucket: 2 req/s, ёмкость 50 | окно из 10 минутных корзин, лимит ~420–480 с |
| Превышение выглядит как | HTTP 503 `QUERY_LIMIT_EXCEEDED`, а живьём — **зависание или обрыв TCP без JSON** | HTTP 429 `OPERATION_TIME_LIMIT` |
| Что блокируется | всё | **только этот метод**, остальные работают |
| Наша реакция | превентивный token bucket + один повтор | пауза метода до `operating_reset_at` |
| Источник данных | известен заранее | `time.operating` / `time.operating_reset_at` КАЖДОГО успешного ответа |

Заголовков `X-RateLimit-*` и `Retry-After` портал НЕ присылает — других
источников, кроме тела ответа, не существует.

## Лимит 1: token bucket

`Bucket{tokens, capacity, refill_per_sec, last}` — чистое ядро без асинхронности
и без `Instant::now()` внутри: всё время приходит параметром, поэтому арифметика
проверяется мгновенными тестами. `take(now)` возвращает `Ok(())` (токен списан)
либо `Err(duration)` (сколько ждать).

Настройка из конфига: `rate_limit_rps = 2`, `burst = 5`. Ёмкость 5, а не
портальные 50, — сознательно: девять десятых бюджета остаются живому
пользователю, который в это же время работает в браузере.

Почему ведро, а не «спать 500 мс между вызовами»:
- залп холодного старта (batch + counters + добор имён) проходит мгновенно;
- непрерывное пополнение — ближайшая аппроксимация скользящей секунды;
- фиксированное окно даёт пограничный залп (5 в конце окна + 5 в начале
  следующего = 10 за 20 мс), то есть гарантированный отказ.

Честная оговорка: bucket с ёмкостью `C` и пополнением `r` формально допускает
`C + r·W` запросов в окне `W`. «Не больше двух в любую скользящую секунду» и
«залп из пяти проходит мгновенно» — взаимоисключающие требования; выбрано
второе, потому что портальное ведро вмещает 50. В установившемся режиме
интервал ровно `1/rps`. Тест: `throttle_spaces_calls_evenly`.

Lock ведра УДЕРЖИВАЕТСЯ ЧЕРЕЗ `sleep` намеренно: `tokio::sync::Mutex` справедлив
(FIFO), поэтому очередь обслуживается в порядке прихода; отпусти мы lock на
время сна — все ожидающие проснулись бы одновременно.

## Лимит 2: operating time на метод

`MethodBudget{operating, reset_at, paused_until}` в `HashMap<method, …>`.
Заполняется из `time` каждого успешного ответа (`note_success`). Портал уже
отдаёт `operating` НАКОПЛЕННЫМ по текущему окну, поэтому хранится последнее
присланное значение, а не наша сумма: своя арифметика окна разъехалась бы с
портальной на первом же перезапуске процесса. При `operating ≥ 336 с` (80 % от
420) пишется предупреждение: пора звать метод через `batch`.

`note_operating_limit(method, reset_at)` ставит паузу. Момент разблокировки
берётся в порядке: из тела ошибки → `operating_reset_at` последнего успешного
ответа этого метода → фолбэк 60 с (одна минутная корзина). Первые два — точные,
а не угаданные.

`acquire(method)` сначала ждёт снятия паузы МЕТОДА и только потом берёт токен
интенсивности. Порядок не косметика: ожидание паузы под общим lock'ом
остановило бы ВСЕ методы — ровно то, чего платформа не делает. Два мьютекса
никогда не удерживаются одновременно, поэтому взаимной блокировки нет.

Паузу длиннее `MAX_METHOD_PAUSE_WAIT` (5 с) `acquire` не пересиживает, а
возвращает вызывающему: держать HTTP-запрос пользователя до десяти минут
нельзя, а заведомо отказной запрос портал засчитал бы в тот же лимит. Клиент
превращает это в `429 flood_wait` с обратным отсчётом БЕЗ обращения в сеть.

Тест: `operating_limit_blocks_only_one_method_until_reset_at` — отказ метода A
не мешает методу B, A возобновляется после `reset_at`, в сеть ушло ровно два
вызова A.

## Что НЕ расходует operating

Внешний `batch` стоит ОДИН хит лимита интенсивности и не учитывается в
`operating` вложенных методов — поэтому он и объявлен главным инструментом
экономии (см. `bitrix-batch`).

## Инъекция времени

`trait Clock` даёт и монотонные часы (`now() -> Instant`, для ведра), и
календарные (`unix() -> i64`, для сравнения с `operating_reset_at`). В тестах
время двигается вручную — ни одного `sleep` ради проверки арифметики.

## Один троттлер на секрет

`Arc<Throttle>` живёт внутри `B24Client`, который кэшируется на вебхук. Лимит —
свойство пары портал+вебхук, а не отдельного вызова; дробить его между
REST-хендлерами и воркером событий нельзя. Документация портала прямо запрещает
«несколько параллельных серий запросов с одного IP».
