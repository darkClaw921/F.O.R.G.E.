# forge-bitrix — модель медиа: скачивание, кэш, аватары (Фаза 8)

Байты вложений и аватаров попадают в браузер ТОЛЬКО через прокси плагина.
Внешних адресов портала в разметке панели не бывает ни одного — ни в `src`,
ни в `href`, ни в заголовке `Location`.

## 1. Почему `urlDownload`, `urlShow` и `unifiedLink` не работают

Портал кладёт эти три адреса прямо в дескриптор файла (`files[]` ответа
`im.dialog.messages.get`), и выглядят они как готовые ссылки на скачивание.
Живая проверка на тестовом портале показала обратное:

| поле | что отдаёт без сессионной куки |
|---|---|
| `urlDownload` | HTTP 200, 52 382 байта, `text/html` — страница логина |
| `urlShow` | то же самое |
| `viewerAttrs.unifiedLink` | HTTP 403 |

Все три требуют куки браузерной сессии портала, которой у входящего вебхука
нет и быть не может. Самое опасное здесь — форма отказа: HTTP 200 с HTML
внутри. Клиент, доверившийся статусу, сохранил бы страницу логина под именем
`отчёт.pdf`.

Поэтому этих полей **нет ни в одной структуре плагина** — ни в
`api::schema::FileRaw`, ни в `attach::MediaDto`. Не объявить проще, чем не
отдать: невозможно случайно передать наружу то, чего не существует в типе.

## 2. Единственный рабочий путь

```
страница истории ──► params.FILE_ID[index] ──► im.v2.File.download {fileId}
                                                        │
                                                  downloadUrl (СЕКРЕТ)
                                                        │
                                          стрим в staging ──► rename в кэш
                                                        │
                                                 БАЙТЫ браузеру
```

`im.v2.File.download` доступен вебхуку по scope `im` (scope `disk` не нужен и
не выдан) и отвечает `{"downloadUrl": "…"}`.

## 3. `downloadUrl` НИКОГДА не покидает процесс

Адрес имеет вид

```
https://<портал>/rest/<uid>/<КОД ВЕБХУКА>/download/?token=im%7C…
```

то есть цитирует секрет плагина ЦЕЛИКОМ. Секрет у Bitrix24 — это весь URL
вебхука, а не отдельный токен: `user_id` криптографически связан с кодом.
Попади эта строка в браузер, и любой, кто увидел devtools, HAR-файл поддержки
или расширение браузера, получает полный доступ к порталу: чтение всей
переписки, отправку от чужого имени, задачи. Это компрометация учётки, а не
утечка одного файла.

Отсюда четыре рубежа:

1. **Тип.** `api::schema::FileDownloadRaw` не реализует `Serialize` — положить
   адрес в JSON-ответ не компилируется.
2. **Редирект запрещён.** Заголовка `Location` в ответах `routes::media` не
   бывает вовсе, ни на успехе, ни на отказе. Ответить `302` было бы вдвое
   дешевле по трафику и означало бы отдать браузеру ключи от портала.
3. **Лог.** Адрес не логируется ни на каком уровне, включая `trace`;
   построчный греп по `src/` — тест `no_source_line_logs_a_download_url`.
4. **Диск.** В `meta.json` вместо адреса ложится отпечаток
   (`media_cache::source_tag`, FNV-1a, 16 hex-символов) — он не
   восстанавливается в URL.

Тест-страж `download_urls_never_leak_to_the_client`
(`plugins/bitrix/tests/media_leak.rs`) перебирает ВСЕ DTO, которые плагин
отдаёт наружу, сериализует их и ищет подстроки `downloadUrl`, `download_url`,
`urlDownload`, `urlShow`, `unifiedLink`, `unified_link`, хост портала и код
вебхука. Он перебирает DTO, а не один роут, потому что регрессия случится не в
`routes/media.rs` (там правило написано в шапке), а в момент, когда кто-нибудь
добавит «полезное» поле в `MediaDto`.

## 4. Роуты

| метод | путь | что отдаёт |
|---|---|---|
| GET | `/api/bitrix/media/file/:dialog/:mid/:index` | байты вложения |
| GET | `/api/bitrix/media/:dialog/:mid/:index` | синоним предыдущего |
| GET | `/api/bitrix/media/avatar/:user_id` | байты аватара (Р6) |

Путей у вложения два и они полные синонимы: длинная форма записана в
замороженной таблице `routes/mod.rs`, короткая — та, которой адресуются панели
VK и Telegram. Коллизии нет (разное число сегментов), а построчный дифф трёх
фронтов — главный инструмент их сопровождения.

**Лестница проверок:** авторизация (409) → объект (404) → параметр (400) →
кэш → связь (503) → портал.

Авторизация первой — общее правило data-роутов: иначе неподключённый клиент
прощупывал бы валидность идентификаторов портала по разнице кодов ответа.
А `503` стоит ПОСЛЕ кэша сознательно: уже скачанная картинка обязана
открываться и при оборванной сети.

## 5. Аватары идут через прокси (Р6), хотя CDN публичен

CDN-адреса аватаров портала работают без всякой авторизации — прямой
`<img src>` показал бы лицо и без прокси. Решение всё равно обратное, и
причин две:

- **Инвариант проверяем.** «Внешних URL в DOM панели нет» проверяется одним
  грепом по разметке. Единственное исключение превращает эту проверку в разбор
  каждого поля каждого DTO.
- **Referer.** Прямая ссылка утекала бы адресом девфоржа на хост портала при
  каждом рендере списка диалогов.

Адрес фото живёт в `peers::PeerInfo::avatar` — ВНУТРИ процесса. В DTO уезжает
только путь прокси (`dto::AVATAR_PATH_PREFIX` + id) — и в `DialogDto::avatar_url`,
и в `SenderDto::avatar_url` строки ленты.

**Источник адреса бесплатный.** Блок `user` приезжает в каждом событии
`ONIMV2MESSAGEADD` и в каждой строке `im.recent.get`; `PeerCache::absorb_users`
забирает его за ноль запросов. Добор `im.user.list.get` делается, только если о
сотруднике не известно вообще ничего.

**«Нет фото» портал пишет тремя способами** — `false`, пустой строкой и
заглушкой `blank.gif` (иногда абсолютным адресом, иногда относительным).
Правило одно на весь плагин: `peers::real_avatar_url`. «Показать картинку» и
«есть что скачать» обязаны отвечать одинаково, иначе кружок аватара покажет
пустой квадрат вместо инициалов.

## 6. Ключ кэша: path traversal невозможен СТРУКТУРНО

Раскладка на диске:

```
<cache_dir>/media/<dialog>/<message_id>.<index>.file.bin
<cache_dir>/media/<dialog>/<message_id>.<index>.file.meta.json
<cache_dir>/media/<dialog>/<message_id>.<index>.file.tmp.<uuid>
<cache_dir>/media/avatars/<user_id>.avatar.bin
<cache_dir>/media/avatars/<user_id>.avatar.meta.json
```

Собрать `media_cache::CacheKey` можно только разбором, и разбор даёт ЧИСЛА:

| часть | тип | правило |
|---|---|---|
| `:dialog` | `DialogKey { prefix: DialogPrefix, number: i64 }` | префикс — перечисление из ТРЁХ вариантов (`User`, `Chat`, `Group`), число > 0 из ASCII-цифр |
| `:mid` | `i64 > 0` | только ASCII-цифры |
| `:index` | `u32 <= MAX_ATTACH_INDEX` (19) | граница модели: столько вложений разбирает `attach::MAX_MEDIA` |
| `:user_id` | `i64 > 0` | только ASCII-цифры |

Имя каталога собирается `format!`-ом из варианта перечисления и числа —
строка из URL в путь не конкатенируется ВООБЩЕ. `../../etc` не парсится в
число и отбрасывается до единого обращения к файловой системе. Это структурная
гарантия, а не проверка строки: убрать её можно только переписав тип ключа,
что видно в диффе.

Отвергаются также: ведущий `+`, ведущие знаки, не-ASCII-цифры (`٤٢`),
null-байты, нулевые и отрицательные значения. Ведущие нули нормализуются:
`0027` и `27` — один путь, а не два файла.

Каталог `avatars` с каталогом диалога столкнуться не может по построению: имя
диалога либо состоит из одних цифр, либо начинается с `chat`/`sg`.

## 7. Целостность записи

Порядок «сначала `bin`, потом `meta`» — контракт: попаданием считается ТОЛЬКО
пара «непустой `bin` + разбираемая `meta`». Оборванная запись (остался `.tmp`,
или появился `bin` без меты, или мета битая, или `bin` пуст) попаданием не
является — иначе клиент получил бы обрезанный файл, да ещё с
`Cache-Control: immutable`, то есть навсегда.

Оба файла пишутся во временный файл В ТОМ ЖЕ каталоге и переносятся `rename`,
атомарным в пределах одной ФС (`/tmp` вполне может оказаться другой ФС — там
`rename` падает с `EXDEV`).

## 8. `Cache-Control` и инвалидация

| ресурс | заголовок | почему |
|---|---|---|
| вложение | `private, max-age=31536000, immutable` | содержимое ключа `(dialog, message_id, index)` неизменно |
| аватар | `private, max-age=3600` (БЕЗ `immutable`) | фото меняют когда угодно, событий об этом платформа не присылает |

`immutable` у вложения законен ТОЛЬКО вместе с работающей инвалидацией. Она
живёт в двух местах:

| что случилось | кто зовёт `media_cache::invalidate` |
|---|---|
| `ONIMV2MESSAGEDELETE` | `events::invalidate_media` |
| правка последнего сообщения замечена диффом | `recent_sync::sync_once` |

Правка приезжает медленным воркером (до `recent_sync_secs`), потому что
события `ONIMV2MESSAGEUPDATE` портал документирует, но живьём не присылает ни
разу. Убери любую из двух строк — и `immutable` из корректного заголовка
превращается в «показывать вложение удалённого сообщения вечно».

У аватара роль инвалидации играет отпечаток источника: если `PeerCache` знает
адрес и он не совпадает с `MediaMeta::source_tag` записи, кэш стирается и
байты качаются заново. Если адрес сейчас неизвестен — отдаётся кэш: лишний
поход в портал на каждый показ аватара дороже, чем день устаревшего фото.

## 9. Удалённое сообщение — 404 БЕЗ СЕТИ

Портал удаление не стирает: он заменяет текст заглушкой и ставит
`params.IS_DELETED: "Y"`. Байты вложения после этого не отдаются вовсе.

`B24State::note_deleted` (кольцевой буфер на 512 записей, отдельный от
дедупа событий) запоминает такие сообщения. Зовут двое: воркер событий на
`ONIMV2MESSAGEDELETE` и сам роут медиа, когда увидел `deleted: true` в свежей
странице истории. После этого запрос той же карточки стоит НУЛЯ вызовов
портала — иначе каждый показ старой ленты обходился бы в два обращения и всё
равно заканчивался тем же 404.

## 10. Дедуп inflight

Открытие ленты с десятком вложений даёт десяток параллельных запросов, а
бюджет портала — два вызова в секунду. Первый запросивший становится владельцем
ключа (`B24State::media_inflight`), остальные ждут его `Notify` и
перечитывают кэш (`routes::media::fetch_cached`).

Гонка «владелец закончил, пока мы шли к `await`» закрыта тем же приёмом, что в
`events::wait_authorized`: `notified()` включается ДО повторной проверки кэша —
`Notify::notify_waiters` не оставляет permit'ов. Ожидание ограничено
`INFLIGHT_WAIT` (300 с), число круговых попыток — `MAX_INFLIGHT_ATTEMPTS` (2):
если владелец упал, второй запрос обязан взяться сам, а не висеть до таймаута
клиента.

`InflightGuard` снимает запись и при панике, и при раннем `return`: без него
любой `?` в середине загрузки оставил бы ключ в реестре навсегда.

## 11. LRU-подчистка

Бюджет — `BitrixConfig::max_cache_bytes` (512 MiB по умолчанию, `0` = не
подрезать, env `FORGE_BITRIX_MAX_CACHE_BYTES`). `media_cache::sweep_once`
удаляет записи по `mtime` от старых к новым, пока размер не опустится ниже
90 % лимита (гистерезис: без него подчистка запускалась бы каждый тик).

`mtime` — приближение «последнего использования»: на попадании роут дёргает
`touch`, поэтому часто открываемые файлы всплывают наверх. Записи, которые
сейчас качаются, пропускаются — удалить файл живой загрузки значит отдать
клиенту пустоту.

Брошенный staging старше `STAGING_TTL` (1 час) удаляется как мусор упавшего
процесса. Возраст «из будущего» (часы прыгнули назад после NTP-коррекции)
считается нулевым — иначе sweeper убил бы файл живой загрузки.

Воркер `media_cache::spawn_sweeper` запускается ВСЕГДА, даже без вебхука:
скачанные медиа переживают logout, и привязка воркера к подключению означала
бы, что после выхода кэш растёт до упора и подмести его некому.

## 12. Стриминг и прогресс

Байты идут потоком в обе стороны: из портала в staging
(`routes::media::stream_to_file`) и из кэша клиенту (`ReaderStream` с буфером
64 КиБ). Пиковая память не зависит от размера файла.

`Accept-Ranges` НЕ анонсируется намеренно: `<video>`, увидев его, шлёт `Range`
и ждёт `206`; получив `200` с полным телом, часть браузеров ломает
воспроизведение. Фронт грузит медиа через `fetch` + `blob:`, поэтому Range ему
не нужен.

Прогресс двуногий:

- кадр WS `download_progress` (`{key, received, total}`) — «сервер тянет из
  портала», подпись `B24`;
- чтение `response.body` в браузере — «сервер отдаёт вкладке», подпись `NET`.

Ключ кадра — тот же `<dialog>/<message>/<index>`, что и `CacheKey::id`, и
`format.js::mediaKey`. Без индекса прогресс второго файла сообщения прилетал бы
в карточку первого.

Троттлинг (`progress::Throttle`) подавляет кадры по ДВУМ условиям сразу
(100 мс ИЛИ 256 КиБ). Без него стомегабайтный файл дал бы десятки тысяч кадров
в broadcast-канал ёмкостью 1024: все подписчики получили бы `Lagged` и ушли в
`resync` — то есть индикатор прогресса сломал бы realtime. **Финальный кадр
проходит всегда**, иначе полоса навсегда замерла бы на 97 %.

## 13. Почему `waveform` и `player_url` всегда пусты

`MediaDto::waveform` (огибающая голосового) и `MediaDto::player_url`
(страница-плеер) объявлены и ВСЕГДА пусты: у Битрикс24 нет ни того, ни другого.
Огибающую платформа не отдаёт вовсе; воспроизводимый файл голосового и видео
приходит обычным вложением, отдельной страницы плеера (как у VK) не существует.

Поля сохранены ради ИДЕНТИЧНОСТИ ФОРМЫ с панелями VK и Telegram — их фронты
рисуют карточку одним и тем же кодом, и каждое удалённое поле превратилось бы
в `if`.

По той же причине нет отдельного вида кэша `thumb`: `im.v2.File.download`
отдаёт ОРИГИНАЛ, а `mediaUrl.preview["250"]` без сессионной куки не работает.
Признак `has_thumb` остаётся — он значит «портал считает файл картинкой», а не
«есть отдельный маленький файл». Превью картинки в ленте — это и есть её полный
файл, и именно поэтому оно грузится лениво.

## 14. Фронт

`static/js/bitrix/media.js` — поведение; разметку карточки строит
`attachments.js` (чистые узлы, ни одного обработчика, поэтому проверяется в
голом Node).

- **Ленивая загрузка** через `IntersectionObserver` с запасом 200 px: на
  истории в сотню медиа иначе улетела бы сотня запросов при первом рендере.
- **`fetch` → `blob` → `objectURL`.** Атрибут `src` не несёт заголовков, а в
  remote-mode `/api/*` требует `Authorization: Bearer`: прямой
  `src="/api/bitrix/media/…"` работал бы локально и молча ломался бы у
  пользователя с токеном.
- **`revoke` при смене диалога** (`revokeDialogMedia`): браузер не собирает
  блоб, пока жив его URL. Аватары при этом ПЕРЕЖИВАЮТ смену диалога — они
  общие для всей панели.
- **`dropMessageMedia`** на кадрах `message_update` и `message_delete`: сервер
  в этот момент стирает свой кэш, а его ответ помечен `immutable`.
- **Лайтбокс-галерея** по картиночным вложениям ОДНОГО сообщения: Esc,
  стрелки, клик по фону, ловушка фокуса. Границы не зациклены — «следующее» за
  последним фото это ничего, а прыжок в начало читается как сбой.
- **Плеер в карточке** для аудио, голосовых, видео и кружков; играет ровно
  один, повторный клик по той же карточке переключает play/pause без потери
  позиции.
- **SAVE** через `<a download>` с санитизацией имени: `download` браузеры
  трактуют как подсказку ПУТИ.

## 16. Обратное направление: отправка файла (Фаза 9)

Скачивание и отправка симметричны только на первый взгляд — у платформы это
принципиально разные механизмы, и знать их различие полезно ровно здесь.

| | скачивание (Ф8) | отправка (Ф9) |
|---|---|---|
| метод | `im.v2.File.download` → `downloadUrl` → отдельный GET | `im.v2.File.upload`, ОДИН POST |
| тело | поток байтов, RSS не двигает | base64 целиком в памяти (~1.33 размера) |
| прогресс | точный в обе ноги (сервер знает `Content-Length`) | точный на приёме, НЕТ на заливке |
| результат | файл в кэше `<cache_dir>/media/` | СООБЩЕНИЕ в чате (метод отправляет его сам) |
| повтор | безопасен и делается | ЗАПРЕЩЁН (Р9): дал бы второй файл и вторую строку |

Главное, что стоит держать в голове при правках медиа: **`im.v2.File.upload`
не «заливает файл», а «заливает файл и отправляет сообщение»**. Поэтому у
отправки нет своего роута — она живёт в `POST /api/bitrix/dialogs/:id/messages`
рядом с текстом, а `POST /api/bitrix/upload` только принимает байты в staging и
выдаёт одноразовый `upload_id`.

Кэш скачивания и staging отправки соседствуют внутри `cache_dir`, но общего у
них ничего: `media/` — это кэш с ключом и метаданными, `uploads/` — каталог
полуфабрикатов, каждый из которых расходуется первой же отправкой либо
подбирается GC по TTL 30 минут. Общий у них только приём `StagingGuard` —
guard, снимающий недописанный файл на `Drop`.

Подробности — страница `bitrix-upload` и записи `bitrix-upload-routes`,
`bitrix-upload-staging`, `bitrix-upload-progress`.
