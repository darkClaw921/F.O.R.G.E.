# Аналитика использования Claude Code (analytics-dashboard)

Фича: вкладка «Аналитика» в настройках devforge + полноэкранный дашборд с чартами по всем проектам, с фильтром по проекту и периоду. Источник данных — транскрипты Claude Code ~/.claude/projects/**/*.jsonl (на машине пользователя ~2.7 ГБ, 1341 файл). Codex НЕ поддерживается.

Эпики в br (база корня, префикс forge-*): forge-an-f1-ucdfw … forge-an-f7-*.

## Правила вычисления (выведены из ЖИВЫХ данных — обязательны)

- Один .jsonl = одна сессия, имя файла = sessionId, файл append-only.
- СООБЩЕНИЕ ЧЕЛОВЕКА, шаг 1 (структура): type==user И isMeta!=true И isSidechain==false И message.content — строка ЛИБО массив БЕЗ блоков tool_result. Без фильтра по tool_result метрика завышена примерно в 10 раз (в живой сессии 19 настоящих против 664 tool_result).
- СООБЩЕНИЕ ЧЕЛОВЕКА, шаг 2 (роль текста, Фаза 7): структурный фильтр пропускает ещё ТРИ вида записей, и все три сообщениями НЕ являются — прерывание `[Request interrupted by user…]` (считается прерыванием), вывод слэш-команды `<local-command-stdout>…` (не считается ничем) и слэш-команда `<command-name>/clear</command-name>…` (сообщение, но слэш-команда, и в словарь TTR идёт только имя команды). Разбор — analytics::text::classify_user_text. Подробности и числа — в разделе Фазы 7.
- КОНЕЦ ХОДА АССИСТЕНТА: type==system && subtype==turn_duration (ровно одна запись на ход). Fallback: timestamp последней assistant-записи перед следующим сообщением человека.
- ПАУЗА «читает ли код» = timestamp следующего сообщения человека − конец хода. Паузы > 30 мин — «отошёл»: отдельный счётчик away_count, в медиану/перцентили/гистограмму не входят.
- ДЛИТЕЛЬНОСТЬ ХОДА = конец хода − предшествующее сообщение человека.
- ТОКЕНЫ: assistant.message.usage.{input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens, output_tokens_details.thinking_tokens}.
- СТОИМОСТЬ И ИТОГИ СЕССИИ: ТОЛЬКО из ПОСЛЕДНЕЙ записи type==cost-state (totalCostUSD, modelUsage[model].costUSD, totalAPIDuration, totalToolDuration, totalLinesAdded/Removed, startTime). Промежуточные кумулятивны — СУММИРОВАТЬ НЕЛЬЗЯ.
- ИНСТРУМЕНТЫ: assistant.message.content[].type==tool_use → .name. ПРЕРЫВАНИЕ — НЕ toolUseResult.interrupted: этого поля в живом архиве нет ни разу, CLI пишет прерывание записью user с текстом `[Request interrupted by user]` (91 запись на 498 файлов). Старый маркер оставлен только для транскриптов прежних версий CLI.
- КОМПАКТЫ: system/compact_boundary. СУБАГЕНТЫ: isSidechain==true и записи agent-name (у agent-name таймстемпа НЕТ).
- ПРОЕКТ: cwd записи; имя каталога — claude_memory::encode_project_dir (не дублировать).
- Заголовок сессии — в записях ai-title; записей summary в файлах нет. durationMs использовать не следует.

## Фаза 1 «Ядро разбора» — ЗАКРЫТА

Реализовано:
- tmux-web/src/analytics/mod.rs — точка входа (mod analytics в main.rs:10).
- tmux-web/src/analytics/parse.rs — построчный разбор, префильтр, устойчивость к битым строкам, parse_offset для инкрементальности.
- tmux-web/src/analytics/rollup.rs — DayBucket / SessionRollup / AnalyticsIndex, merge, Samples (точный вектор до 20k + логарифмическая гистограмма 128 бинов), идемпотентное redistribute_totals, Query (from/to/project/day|week).
- tmux-web/tests/analytics_parse.rs — 22 теста на синтетических фикстурах.

Принятые архитектурные решения Фазы 1:
1. Перцентили — по хранимым сэмплам, пока их < 20000 на день; дальше оценка по логарифмической гистограмме (погрешность ≤ ~13 %, закреплена тестом). Гистограмма складывается при merge без потерь.
2. Дни считаются в ЛОКАЛЬНОЙ зоне машины (иначе «ночная активность» и heatmap теряют смысл).
3. Пауза относится ко дню, в который ход ЗАВЕРШИЛСЯ — тогда человек начал читать.
4. cost-state даёт итог на всю сессию без разбивки по дням; redistribute_totals раскладывает cost/lines/api_ms/tool_ms по дням пропорционально числу записей ассистента. Метод идемпотентен (сначала обнуляет распределённые поля), поэтому безопасен после каждого дочитывания.
5. gen_ms — измеренная сумма длительностей ходов, api_ms/tool_ms — распределённые доли cost-state: обе величины хранятся отдельно, чарт «куда уходит время» выбирает нужную.
6. Состояние автомата ходов (TurnState) хранится в SessionRollup, а не в локальных переменных, — чтобы ход, разрезанный границей инкрементального дочитывания, не потерялся и не задвоился.
7. Последний открытый ход НЕ закрывается автоматически в конце разбора (файл может дорасти); для заведомо законченной сессии есть явный close_open_turn().
8. Тесты подключают модули через #[path] (devforge — бинарный крейт без [lib]) и обёрнуты в mod analytics_parse, чтобы фильтры cargo по имени теста работали.

Верификация Фазы 1: cargo build -p devforge (без предупреждений), cargo test -p devforge analytics → 22 passed. Числа сверены с jq на живом транскрипте: 23 сообщения человека и 178 tool_use — совпало точно.

## Фаза 2 — индексатор и кэш (закрыта)

Файлы: tmux-web/src/analytics/scan.rs, tmux-web/src/analytics/cache.rs, tmux-web/tests/analytics_cache.rs. В tmux-web/Cargo.toml добавлена зависимость forge-atomic. Роутов и AppState здесь ещё нет — это Фаза 3.

Инкрементальность по ключу (len, mtime, parse_offset), решение принимается БЕЗ чтения содержимого (scan::decide_action):
* len и mtime те же → Unchanged, файл не открывается вовсе;
* len вырос, mtime не уехал назад → Append, seek(parse_offset) + append_session;
* len уменьшился, ИЛИ mtime назад, ИЛИ len тот же при новом mtime, ИЛИ parse_offset > len → Full, роллап выбрасывается;
* нового файла не было в индексе → Full; исчезнувший файл выпадает из индекса.

Ветка «тот же len, новый mtime» — перезапись «в размер»: не рост и не усадка, содержимое могло измениться где угодно, поэтому единственный безопасный ответ полный пересбор. Ветка parse_offset > len — рассинхрон с диском: seek за конец молча дал бы пустой хвост и замороженные числа.

Параллелизм: каждый файл в tokio::task::spawn_blocking, одновременность ограничена Semaphore на available_parallelism (фолбэк 4); пермит берётся ДО spawn_blocking, иначе семафор не ограничивал бы ничего. Паника в задаче (JoinError) и ошибка отдельного файла считаются как errors и скан не отменяют. Прогресс — атомарные total/done/errors/files_read/bytes_read/running в ScanProgress; повторный скан во время идущего невозможен (try_begin + ScanGuard, снимающий running на Drop даже при панике).

Кэш: CacheSnapshot{version, updated_at_ms, files: путь → SessionRollup} в ~/.forge/analytics-cache.json, запись через forge_atomic::write_bytes_atomic (temp+fsync+rename+0600, своей копии tmp+rename не заводить). CACHE_VERSION = 1 — версия СХЕМЫ: любое изменение полей роллапа или правил разбора обязано её поднимать. Несовпадение версии, битый/пустой/отсутствующий JSON → load() возвращает None, то есть полный пересбор, без паники. Загруженный снимок сразу годится как аргумент prev для scan_incremental — после рестарта неизменившиеся файлы не читаются.

Размер снимка: наборы точных сэмплов длиннее CACHE_MAX_KEPT (4096) отбрасываются ЦЕЛИКОМ, перцентили после загрузки считаются по гистограмме. Отбрасывать частично нельзя: Samples::quantile переходит на гистограмму по признаку kept.len() != count, и усечённый наполовину набор дал бы неверный ответ вместо приближённого. Режется копия — живой индекс в памяти сохраняет точность.

Развилки Фазы 2, которые легко сломать:
9. close_open_turn() в скане НЕ вызывается: файл живой сессии может дорасти в любой момент, а закрытие хода необратимо испортило бы равенство «инкремент == полный пересбор». Закрывать ход можно только для заведомо законченной сессии.
10. redistribute_totals() уже вызывается в конце append_session и идемпотентен, поэтому дочитывание хвоста не требует отдельного пересчёта итогов.
11. project_dir роллапа берётся из cwd записей, но у сессии без единой записи с cwd его нет — тогда scan_file подставляет имя каталога с диска, иначе сессия ушла бы в проект «unknown».
12. Каталог memory/ внутри проекта принадлежит claude_memory.rs; фильтр по расширению .jsonl отсекает его сам.

Верификация Фазы 2: cargo build -p devforge и cargo clippy --all-targets — чисто; cargo test -p devforge — 878 тестов зелёные (из них 15 новых в analytics_cache). Замер полного скана на живом архиве (ignore-тест measure_full_scan_of_live_archive): 498 файлов, 1406 МБ, 4.5 с в debug-сборке, ошибок 0, done == total.

## Фаза 3 — API аналитики (закрыта)

Файлы: tmux-web/src/analytics/mod.rs (хранилище + DTO), правки tmux-web/src/main.rs (поле AppState, четыре роута, четыре хендлера), новый клиент tmux-web/static/js/analytics/api.js, страж tmux-web/tests/analytics_routes_contract.rs. Плюс Samples::bucket_counts в rollup.rs — раскладка распределения по произвольным границам для чартов-гистограмм.

### AnalyticsStore

Cheap-clonable Arc-обёртка (клон = Arc::clone, ни индекс, ни роллапы не копируются). Внутри: tokio RwLock<Data> и Arc<ScanProgress>. Data = {index: AnalyticsIndex, files: путь → SessionRollup, updated_at_ms, scanning, ready, last_error}. Пути (~/.claude/projects и ~/.forge/analytics-cache.json) хранятся Option — отсутствие $HOME делает аналитику пустой, но не роняет процесс; юнит-тесты main.rs создают store с обоими None, чтобы не трогать домашний каталог.

Счётчики прогресса живут в ScanProgress, а НЕ в Data: хендлер status читает их атомарно, не вставая в очередь за пишущим локом скана — иначе прогресс переставал бы обновляться ровно тогда, когда он нужен.

Методы:
* init_lazy() — вызывается один раз при сборке AppState; читает ТОЛЬКО снимок кэша (spawn_blocking), каталог транскриптов не открывает. Снимка нет / битый / другой версии — состояние остаётся Idle, это не ошибка.
* ensure_scan(full) — запускает фоновый проход, если нужно; хендлер не ждёт его конца.
* rescan() — удаляет снимок, сбрасывает индекс, ensure_scan(true), сразу возвращает StatusDto.
* status() / projects() / summary(&SummaryParams) — построение ответов ЦЕЛИКОМ по индексу в памяти, без обращений к диску.

### Развилки Фазы 3, которые легко сломать

13. ЛЕНИВАЯ ИНДЕКСАЦИЯ. На старте devforge вызывается только init_lazy(): читается один файл ~/.forge/analytics-cache.json. Каталог ~/.claude/projects при старте не открывается ни разу — иначе каждый запуск платил бы обходом 2.7 ГБ за вкладку, которую могут не открыть. Первый скан запускает ПЕРВЫЙ ЗАПРОС к любому роуту аналитики (все четыре хендлера зовут ensure_scan).
14. ПОРОГ REFRESH_MIN_INTERVAL_MS = 60 000. Инкрементальный проход НЕ начинается, если индекс готов и последний проход был меньше минуты назад. Это не оптимизация, а условие работоспособности: каждый роут зовёт ensure_scan, и поллинг status раз в полсекунды без порога перезапускал бы обход бесконечно — состояние никогда не доходило бы до ready, прогресс-бар не исчезал бы с экрана. Дефект найден живым прогоном Фазы 3 и исправлен там же. rescan() порог обходит намеренно: это явное действие человека.
15. ГОТОВЫЙ ИНДЕКС ОСТАЁТСЯ ready ВО ВРЕМЯ ОСВЕЖАЮЩЕГО ПРОХОДА (state_of сначала проверяет ready, потом scanning). state=scanning означает ровно одно: «показывать нечего, идёт первая сборка». Откат в scanning из-за фонового обновления спрятал бы за прогресс-баром рабочий дашборд; что проход идёт, клиент видит по progress.running.
16. ЗАПРОС ДО ГОТОВНОСТИ ИНДЕКСА — 200, А НЕ ОШИБКА. summary отвечает state:"scanning" с заполненным progress и пустыми сериями. Ни 202, ни 503: иначе каждый клиент лечил бы это состояние отдельной веткой, и первая же забытая ветка дала бы пустой экран без объяснения.
17. НЕВАЛИДНЫЕ ПАРАМЕТРЫ МОЛЧА ЗАМЕНЯЮТСЯ УМОЛЧАНИЯМИ. bucket=quarter → day, from=nonsense → начало диапазона индекса, project=ghost → пустые серии (не 404). Дашборд не должен уметь получить 400 из-за опечатки в адресной строке.
18. ПРЕДЫДУЩИЙ ПЕРИОД — ТОЙ ЖЕ ДЛИНЫ, вплотную перед from (previous_range), а не «предыдущий календарный месяц»: семь дней сравниваются с семью, даже если период начался в середине недели. Границы отдаются клиенту в range.previousFrom/previousTo — фронт не гадает, что сервер понял.
19. МЕДИАНА ПАУЗЫ НЕ ФИЛЬТРУЕТСЯ ПОВТОРНО. Паузы «отошёл» (> 30 мин) не попадают в Samples по построению ещё в Фазе 1; вторая фильтрация «на всякий случай» отрезала бы честные длинные паузы.
20. ТОП ПРОЕКТОВ СЧИТАЕТСЯ ОТДЕЛЬНЫМИ ЗАПРОСАМИ ПО КАЖДОМУ ПРОЕКТУ, а не из суммарного бакета: бакет уже сложен по всем проектам и разложить его обратно нельзя.
21. РОУТЫ РЕГИСТРИРУЮТСЯ РЯДОМ С /api/user-settings, внутри того же Router с .with_state — bearer-auth и CSRF навешиваются слоями автоматически, руками к analytics-роутам ничего добавлять не нужно.

### Семь типов чартов — единый API

Все функции имеют одну сигнатуру `chart(container, data, opts) -> {update(data, opts), redraw(), svg}`; `update()` перерисовывает НА МЕСТЕ (контейнер очищается, канва создаётся заново), `redraw()` нужен после смены темы.

* `barChart(el, {labels, values, overlay?}, opts)` — чарт 1 (сообщения по дням + линия новых сессий).
* `lineChart(el, {labels, series:[{label, values}]}, opts)` — чарты 3, 9, 10 (медиана/p90 пауз, средняя длина, p50/p90 хода).
* `hbars(el, [{label, value, secondary}], opts)` — чарты 6, 8 (топ инструментов с долей прерванных, топ проектов).
* `donut(el, [{label, value}], opts)` — чарт 7 (модели по сообщениям и по стоимости).
* `stackedArea(el, {labels, series}, opts)` — чарты 4, 5 (токены in/out/cache, «куда уходит время»).
* `histogram(el, {labels, values}, opts)` — чарты 3 и 9 (бакеты пауз и длин сообщений).
* `heatmap(el, {matrix, rowLabels?, colLabels?}, opts)` — чарт 2 (час × день недели, 7×24).

Публичные примитивы того же модуля: `node`, `clear`, `tip`, `finite`, `size`, `clamp`, `linearScale`, `niceTicks`, `themeColors`, `foldSeries`, `formatCompact`, `formatCount`, `formatMs`, `formatUsd`, `formatPercent`, `formatDay`, константы `SERIES_MAX` и `SERIES_TOKENS`.

### Принятые решения Фазы 4

1. НИКАКОЙ БИБЛИОТЕКИ. В devforge нет ни одной chart-зависимости, и заводить её нельзя: фронт целиком едет в бинарь через rust-embed, а сторонний рантайм принёс бы собственную палитру, которая не следует за пользовательской темой.
2. ЦВЕТА ТОЛЬКО ИЗ CSS-ПЕРЕМЕННЫХ, БЕЗ ХЕКС-ФОЛБЭКОВ. `js/echo/stats.js` подстраховывается хексом — здесь так нельзя: хардкод пережил бы смену темы ровно у того пользователя, который тему и настроил. Последний рубеж — `currentColor`. Страж в тесте: регулярка `#[0-9a-fA-F]{3,8}` по исходнику файла.
3. ПОРЯДОК СЛОТОВ ПАЛИТРЫ ЗАФИКСИРОВАН: `--accent → --warn → --agent-accent → --success → --danger`. Порядок выбран не на глаз — прогнан валидатором палитры (симуляция протанопии/дейтеранопии Machado 2009, ΔE в OKLab×100) на тёмной подложке `--bg-elev`: худшая СОСЕДНЯЯ пара даёт ΔE 10.9 при дейтеранопии и 33.1 при обычном зрении (пороги 8 и 15), контраст к подложке у всех пяти ≥ 3:1. Другие перестановки тех же пяти токенов дают худшие цифры. Проверка «полоса светлоты» на `--warn`/`--success` формально не проходит (они светлее рекомендованной для тёмного режима полосы), но это значения ПОЛЬЗОВАТЕЛЬСКОЙ темы, и подменять их своими — прямое нарушение решения 2.
4. БОЛЬШЕ ПЯТИ СЕРИЙ КИТ НЕ РАСКРАШИВАЕТ. Шестой оттенок пришлось бы генерировать, а сгенерированная пара рано или поздно оказывается неразличимой при дейтеранопии. Хвост сворачивается в «Другое» приглушённым `--fg-dim` (`foldSeries`). Тема вправе переопределить слоты через `--chart-1…--chart-5` — они имеют приоритет над семантическими токенами.
5. ИДЕНТИЧНОСТЬ НЕ ТОЛЬКО ЦВЕТОМ: у каждой фигуры `<title>` с подписью и значением, от двух серий обязательна легенда; подпись легенды красится ТЕКСТОВЫМ токеном `--fg`, а цвет несёт квадратик рядом.
6. ВТОРАЯ ОСЬ — ТОЛЬКО ЯВНО. Две шкалы Y — приём сомнительный (соотношение кривых задаёт выбор шкал, а не данные), поэтому `overlay` включается вручную и существует ради чарта 1 плана. Шкала наложенной линии считается ТОЛЬКО по своему ряду и с основной не связана — это закреплено тестом.
7. ТРИ ОБЯЗАТЕЛЬНЫХ СОСТОЯНИЯ У КАЖДОГО ЧАРТА: пустой ряд (заглушка «нет данных»), одна точка, все нули. Механика: `niceTicks` на вырожденном диапазоне [0,0] даёт шкалу 0..1 (делений всегда > 1), `linearScale` на вырожденном домене кладёт точку в середину диапазона вместо деления на ноль, `size()` обнуляет отрицательные размеры, `clamp` держит координаты внутри поля, `finite()` ловит NaN на входе. Одна корзина: линия рисуется маркером, стек — столбиками, точка ставится по центру поля, а не в углу.
8. HEATMAP — ОДИН ОТТЕНОК. Последовательная величина кодируется непрозрачностью `--accent` от 0.08 до 1.0, а не радугой; на матрице из нулей `span = 0 → t = 0`, все ячейки в минимуме (деления на ноль нет). Ночные часы 00–06 подчёркнуты скобкой с подписью, рядом легенда шкалы из пяти ступеней.
9. ОТЗЫВЧИВОСТЬ БЕЗ ПИКСЕЛЕЙ: `viewBox` + `preserveAspectRatio="xMidYMid meet"` + `width="100%"`; внутри чарта координаты — «единицы графика» (по умолчанию 720×260), в разметку пиксели не попадают.
10. ТЕСТИРУЕМОСТЬ БЕЗ JSDOM: документ берётся из `container.ownerDocument`, окно — из `ownerDocument.defaultView`, глобальные `document`/`getComputedStyle` — только последний рубеж. Поэтому весь кит рисуется на крошечном фейковом DOM из ~90 строк.

### Принятые решения Фазы 5

1. МЕХАНИКА ПОКАЗА — ТОЧНАЯ КОПИЯ «Сводки дня» (`daily-summary.js::showDailySummary`, строки 436-450): вью занимает `#main` целиком, поэтому при открытии скрывает `#home` и placeholder терминала (`showPlaceholder(false)`), а `closeAnalytics()` зовёт `fetchSessions()` — тот сам решает, показать `#home` или активную сессию. Своей «истории вью» в devforge нет, и заводить её ради одного экрана — лишняя сущность.
2. ВЬЮ `#main` ВЗАИМОИСКЛЮЧАЮЩИЕ. `showAnalytics` гасит «Сводку дня», а `showDailySummary` и `showScreensaver` — дашборд, все три через `window.ForgeApp.*` (тот же приём, что уже был у заставки). Прямые импорты замкнули бы граф модулей. Дело не в косметике: оставленный под соседним вью дашборд продолжал бы поллить `/api/analytics/status`.
3. ЧИСТАЯ ЛОГИКА ВЫНЕСЕНА В `view-core.js`. Импортировать `analytics.js` в Node нельзя — он тянет `core/dom.js`, а тот на первой строке зовёт `document.getElementById`. Всё, что можно посчитать неправильно (границы периода, дельта, подписи бакетов, доля thinking), живёт в файле без единого импорта и покрыто тестом; в модуле вью остаются только узлы и запросы.
4. ГРАНИЦЫ ПЕРИОДА СЧИТАЮТСЯ КАЛЕНДАРЁМ. «7 дней» — сегодня и шесть предыдущих дат, ровно семь колонок (а не «сегодня минус семь», что даёт восемь). `all` НЕ шлёт ни `from`, ни `to`: сервер подставит весь диапазон индекса сам, а подстановка «1970-01-01» уводила бы в бессмыслицу предыдущий период для дельт. Корзина: до 90 дней — `day`, «всё время» — `week` (на полугодовом архиве дневная ось даёт две сотни колонок в пиксель).
5. ДЕЛЬТА К ПУСТОМУ ПЕРИОДУ НЕ РИСУЕТСЯ. `previous == 0` — это первая неделя работы или свежий проект; «+∞%» и «NaN%» в плитке читаются как поломка самих цифр. ЗНАК НЕ РАВЕН СМЫСЛУ: окраска задаётся метрикой (`better: 'up' | 'down' | null`), а не знаком разницы — рост стоимости не «зелёный», а падение медианной паузы это ровно тот сигнал «соглашаюсь не читая», ради которого дашборд и затевался.
6. HERO-ПЛИТКИ. Медианная пауза перед ответом и доля ответов быстрее 10 с идут первыми и вдвое крупнее: это главный вопрос запроса, и он не должен теряться среди двадцати одинаковых прямоугольников. Всего плиток 22 — весь `KpiDto`, включая «строк +/−» одной плиткой и счётчик пауз «отошёл» (>30 мин), которые в медиану не входят по построению.
7. ПОДПИСИ БАКЕТОВ — ОТ ГРАНИЦ СЕРВЕРА. `pauseBucketEdgesMs` и `msgLenEdges` приходят в ответе именно затем, чтобы подписи не разъезжались с расчётом: хардкод «<5 с, 5-15…» на фронте пережил бы правку `PAUSE_BUCKET_EDGES_MS` в `rollup.rs` молча, и график подписывал бы не то, что рисует.
8. ГЛАВНАЯ РАЗВИЛКА — `viewMode()`. `idle`/`scanning` (индекса ещё нет) → только прогресс-бар: рисовать нули было бы враньём. `ready` при `progress.running` → ПОЛНОЦЕННЫЕ ДАННЫЕ плюс тонкая пометка «в фоне дочитываются файлы»: индекс поднят из кэша, добираются лишь хвосты, и подменять готовый дашборд прогресс-баром значило бы прятать его ради технической подробности. Поллинг `/api/analytics/status` (1.5 с) нужен в обоих случаях и гаснет при готовности и при закрытии вью.
9. УСТАРЕВШИЕ ОТВЕТЫ ОТБРАСЫВАЮТСЯ ПО НОМЕРУ ЗАПРОСА. Быстрое переключение периода — гонка: ответ на «7 дней» может прийти после ответа на «90». Счётчик сдвигается и в `hideAnalytics`, поэтому после ухода со страницы не дорисовывается ничего.
10. ВЫБОР ФИЛЬТРОВ — В `localStorage` (`forge.analytics.range`, `forge.analytics.project`), как режим темы панелей мессенджеров. `user_settings` потребовал бы round-trip к серверу и новой ручки ради двух строк, переживать перезагрузку которым достаточно локально; недоступный `localStorage` (private mode) не ошибка — выбор просто не переживёт перезагрузку. Исчезнувший с диска проект молча возвращает «Все проекты».
11. ПУСТОЙ ПЕРИОД ОБЪЯСНЯЕТСЯ СЛОВАМИ. При пустом ответе (`isEmptySummary`) вместо сетки из десяти карточек «нет данных» рисуется одно осмысленное сообщение с подсказкой расширить период или сменить проект. Отдельные заглушки внутри чартов остаются для частичных дыр.
12. СМЕНА ТЕМЫ — `MutationObserver` за `style`/`class` на `<html>` и `redraw()` по каждому хендлу. Глобального события «тема сменилась» в devforge нет: `themes/api.js::applyTheme` просто расставляет CSS-переменные. Тот же приём, что у панелей мессенджеров; обратный импорт замкнул бы граф модулей. Хендлы чартов накапливаются в `_charts` и обнуляются при каждой отрисовке, иначе смена темы перекрашивала бы призраки прошлых отрисовок (частный случай — переключатель метрики в «Топе проектов», где хендл помечен и заменяется адресно).
13. НИКАКОГО `innerHTML`. Подписи проектов, инструментов и моделей приходят из транскриптов, то есть с диска пользователя; путь до `innerHTML` для таких строк не должен существовать в принципе. Страж — регулярка по исходнику (комментарии из проверки вырезаются).
14. СЕТЬ ТОЛЬКО ЧЕРЕЗ `js/analytics/api.js`. Свой `fetch` означал бы 401 в remote-режиме: заголовки авторизации и CSRF подставляет подменённый `window.fetch` из `core/auth.js`, и единственная дверь к нему — `apiFetch`. Второй страж теста.
15. ДИПЛИНК — БЕЛЫЙ СПИСОК. `routeView` теперь обрабатывает два значения явными ветками; динамический импорт по строке из адресной строки был бы дырой.

### Чарты вью (номера по плану)

Порядок карточек в сетке: **3** (пауза перед ответом — гистограмма бакетов + медиана/p90, первой после KPI как главный чарт запроса), **1** (сообщения по дням + линия новых сессий на своей оси), **4** (стек токенов in/out/cache-read/cache-create + отдельная линия стоимости ПОД стеком, а не второй осью поверх него — пятая кривая на своей шкале сделала бы картинку нечитаемой), **5** (куда уходит время: генерация · инструменты · человек читает), **6** (топ инструментов, прерванные вызовы внутри полосы), **7** (модели: два кольца — по сообщениям и по стоимости), **8** (топ проектов с переключателем метрики сообщения/стоимость/строки), **9** (длина сообщений: гистограмма + средняя по дням), **10** (p50/p90 длительности хода), **12** (доля thinking в выводе — именно ДОЛЯ: абсолютные токены повторяли бы чарт 4). Чарты 2 (тепловая карта), 11 (разнообразие) и 13 (версии CLI) ждут своих метрик в Фазе 7.

Геометрия: широкие карточки рисуются в 1200×300 (4:1 — 90 дневных столбцов остаются читаемыми), обычные — в умолчании кита 720×260; высота `hbars` считается от числа строк.

### Правила метрик разнообразия (чарт 11)

* **Слово** — максимальная последовательность `char::is_alphanumeric`
  (кириллица и цифры наравне с латиницей), в нижнем регистре. Стоп-слова НЕ
  отбрасываются.
* **TTR за день** = оценка числа различных слов / все слова. Числитель —
  HyperLogLog на 512 регистров (`rollup::Distinct`): точное множество слов
  раздуло бы снимок кэша на десятки мегабайт, а HLL занимает 512 байт при
  любом словаре и складывается поэлементным максимумом без потерь. Ошибка
  ~4.6 % на больших словарях, доли процента на малых (линейный счёт). **TTR —
  тренд, а не точное число.** Регистры уезжают в снимок base64-строкой.
* **Повторы промптов** — `prompt_hashes: BTreeMap<хеш, счёт>` за день: повторы
  = сумма значений − число ключей. Карта складывается при слиянии, поэтому
  один и тот же промпт в РАЗНЫХ сессиях одного дня виден как повтор. Потолок
  `MAX_PROMPT_KEYS = 20 000` — страховка, живые дни до него не достают.
* **Энтропия инструментов** — Шеннон по `day.tools` в битах: 0 — весь день
  одним инструментом, `log2(N)` — равномерно по N.
* **Уникальные проекты в день** считаются по проектным дням индекса
  (`unique_projects_per_bucket`), а не по суммарному бакету: бакет уже сложен
  по всем проектам, и разложить его обратно нельзя.
* **Односложное подтверждение** — не длиннее трёх слов, нормализованный текст
  целиком в белом списке `ACK_PHRASES` (46 фраз, рус + англ), либо одни плюсы.
  Слэш-команда никогда не считается подтверждением.
* **Хеш** — свой FNV-1a + финализатор SplitMix64 (`text::hash64`), а не
  `DefaultHasher`: значения уезжают в снимок и обязаны совпадать между
  запусками и версиями компилятора.

Полного текста сообщений нет ни в роллапе, ни в снимке, ни в API — только
счётчики и 64-битные хеши. Закреплено тестом
`analytics_does_not_keep_message_text_anywhere_in_the_rollup`.

### Часовой пояс и ночная активность (чарт 2)

Таймстемпы транскриптов — UTC. Бэкенд раскладывает их по ЛОКАЛЬНОЙ зоне машины
один раз (`SessionRollup::on_human_message` → `local_dt`), фронт повторно
ничего не сдвигает. Матрица `hour_x_weekday` копится как `[час][день недели]`
(день 0 = понедельник), в серии уходит как есть, а разворот в календарные 7×24
делает `view-core::weekdayHourMatrix`. Ночь — первые `NIGHT_HOURS = 6` часов
суток; константа едет в ответ полем `series.nightHours`, чтобы подпись на
фронте и сумма на бэкенде не разошлись.

### Полоса версий CLI (чарт 13)

`chart.js::band`. За квартал в архиве набирается **35** версий, поэтому
палитра из пяти цветов не годится ни в каком виде: «пять цветных плюс серое
остальное» превращает полосу в серую ленту, а пять цветов по кругу — в
конфетти. Решение: ОДИН тон (`--accent`) со ступенями непрозрачности по
хронологии первого появления — читается как движение вперёд, каждая смена
видимая ступень. Крайние версии подписаны по краям, точная версия — в
подсказке, даты смен подписаны снизу с минимальным зазором 44 px. День без
данных о версии — нейтральная заливка `--border` с прозрачностью 0.35.

### Сверка чисел через jq (задача .6)

Эталон — jq-программа с ТЕМ ЖЕ автоматом ходов, что в `rollup.rs`. Сверялись
**10 живых транскриптов** из 5 проектов (22 КБ … 15 МБ), по 13 метрик каждый:
сообщения человека, прерывания, доля слэш-команд, стоимость, токены
in/out/cache-read/cache-create, вызовы инструментов, «отошёл», медианная
пауза, человеко-время, доля ответов быстрее 10 с. **Расхождений нет.**

Сверка шла через НАСТОЯЩИЙ API: devforge поднимался с временным `HOME`, в
котором лежал ровно один живой файл, и ответ `/api/analytics/summary`
сравнивался с выводом jq — так проверяется вся цепочка, а не одна функция.

Ключевые фрагменты jq (полная программа — в отчёте задачи
`forge-an-f7-t9row.6`):

```bash
# Текст записи user: строка целиком либо конкатенация text-блоков
def text_of:
  if (.message.content|type)=="string" then .message.content
  elif (.message.content|type)=="array"
  then ([.message.content[]? | select(.type=="text") | .text] | join("\n"))
  else "" end;

# Структурный фильтр
def is_user_record:
  .type=="user" and (.isMeta != true) and (.isSidechain != true)
  and (((.message.content|type)=="string")
       or (((.message.content|type)=="array")
           and (([.message.content[]? | select(.type=="tool_result")]|length)==0)));

# Роль записи: реплика / прерывание / вывод слэш-команды
def role:
  (text_of | sub("^\\s+";"")) as $s
  | if ($s|startswith("[Request interrupted by user")) then "interrupt"
    elif ($s|startswith("<local-command-stdout>")) then "cli"
    else "msg" end;

def is_human: is_user_record and (role=="msg");

# Настоящих сообщений человека
jq -s '[.[] | select(is_human)] | length' файл.jsonl

# Стоимость: ТОЛЬКО последняя запись cost-state (они кумулятивны)
jq -s '[.[] | select(.type=="cost-state")] | last | .totalCostUSD' файл.jsonl

# Паузы: тот же автомат ходов, что в rollup.rs (pending_end из turn_duration,
# иначе последний assistant), медиана без пауз > 30 мин
```

Контрольные ориентиры, подтверждённые на живых файлах:
* один файл: **19** настоящих сообщений против **664** `tool_result` — если
  аналитика показывает сотни сообщений, фильтр не работает;
* файл с ДВУМЯ записями `cost-state`: последняя = `0.229085`, наивная сумма =
  `0.45817`; API отдаёт `0.229085`;
* `cost-state` есть лишь в 29 файлах из 498 — у остальных сессий стоимость
  неизвестна и равна нулю, это не ошибка индекса.
