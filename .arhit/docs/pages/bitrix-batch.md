# bitrix-batch — пакетный вызов и нарезка по 50 (`plugins/bitrix/src/api/batch.rs`)

## Зачем

Внешний `batch` стоит ОДИН хит лимита интенсивности (2 req/s) и **не расходует
`operating`-время** ни одного из вложенных методов. Холодный старт панели —
`im.recent.get` + `im.recent.list` + `im.counters.get` + добор имён — по
отдельности это четыре хита и две секунды ожидания на боевом лимите, одним
`batch` — один хит и один round-trip. Отсюда правило Р3: холодный старт и добор
имён идут ТОЛЬКО пачкой.

## Формат, который принимает портал

```json
{"halt": 0, "cmd": {"recent": "im.recent.get?SKIP_OPENLINES=Y",
                    "counters": "im.counters.get"}}
```

Каждая команда — СТРОКА `метод?query`, а не объект. Отсюда два требования,
которые легко нарушить:

1. **Значения обязаны быть urlencode.** Ловушка живая: `+` в датах
   (`2026-08-05T20:14:43+03:00`) без кодирования читается порталом как пробел, и
   фильтр по дате молча съезжает на часовой пояс. `percent_encode` кодирует всё,
   кроме `A-Za-z0-9-_.~`; пробел даёт `%20`, а не `+` (иначе сам плюс стал бы
   непередаваем).
2. **Вложенность выражается скобками в ИМЕНИ**: `FILTER[>ID]=10`,
   `SELECT[0]=ID`. `encode_params` разворачивает JSON-объект в такие имена:
   объект → `parent[key]`, массив → `parent[index]`, `null` → пустое значение,
   `true/false` → `1/0`. Структурные скобки остаются литеральными, имена и
   значения кодируются.

`halt: 0` — «не останавливаться на первой ошибке»: панели нужны все результаты,
которые портал в состоянии отдать, а не первый успешный префикс.

## Лимит 50 и молчаливая потеря

Команд в пачке не больше **50**. 51-я и дальше НЕ выполняются, но общей ошибки
при этом НЕТ: они приезжают поключево в `result_error` с кодом
`ERROR_BATCH_LENGTH_EXCEEDED`. Вызывающий, который смотрит только на `Ok`/`Err`,
потеряет их молча — поэтому нарезка автоматическая (`chunks`), а не оставлена на
дисциплину. Пачки идут ПОСЛЕДОВАТЕЛЬНО: параллельный запуск был бы теми самыми
«параллельными сериями запросов с одного IP», которые портал запрещает.

## Разбор ответа

```json
{"result": {"result": {…}, "result_error": [], "result_total": {"k": 2},
            "result_next": [], "result_time": {…}}}
```

`result_error`, `result_next`, `result_total` — PHP-поля: пустыми приезжают как
`[]`, заполненными как объект. `demux` проверяет форму на каждом.
`BatchOutcome{ok, errors, totals, next}` раскладывает всё по ТЕМ ЖЕ ключам, что
были в запросе; отказ одной команды НЕ делает пачку неуспешной. Ошибка команды
приходит объектом `{error, error_description}`, но у части методов — голой
строкой; обе формы дают `BatchError`.

`B24Client::batch(calls)` возвращает `Err` только тогда, когда не выполнилась ни
одна команда (транспорт, лимит, отказ самого `batch`).

## Р9 внутри пачки

`batch`, в `cmd` которого вложена отправка (`im.message.add`,
`im.v2.File.upload`), НЕ повторяется — иначе запрет на повтор обходился бы одной
строкой. Проверка живёт в `api/mod.rs::is_retryable`.

Тест: `batch_splits_at_fifty_and_demuxes_result_error` — 55 команд уезжают
двумя пачками (50 + 5), ни один ключ не потерян, отказавшая команда лежит под
своим ключом, `+` в дате доехал как `%2B`; та же пачка одним куском даёт пять
`ERROR_BATCH_LENGTH_EXCEEDED` и НИ ОДНОЙ общей ошибки.
