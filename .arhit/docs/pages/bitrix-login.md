# forge-bitrix — подключение портала: автомат логина и хранение секрета

Страница Фазы 3 для `plugins/bitrix/src/login.rs`, `src/routes/login.rs`,
записи секрета в `src/config.rs` и фронтовой пары
`static/js/bitrix/{api,login}.js`. Rust-файлы `arhit arch build` в этом
проекте не индексирует (индексируется только JS), поэтому модульная
документация ведётся именованными страницами с префиксом `bitrix-`.

## Что вставляет пользователь

Секрет Bitrix24 — **весь URL входящего вебхука целиком**:
`https://<портал>/rest/<user_id>/<код>/`. `user_id` криптографически связан с
кодом (живая проверка: `/rest/2/<тот же код>/profile.json` →
`INVALID_CREDENTIALS`), поэтому «спрятать только код» бессмысленно: пара
`user_id + code` и есть учётные данные.

## Восемь состояний автомата — ЗАМОРОЖЕННЫЙ КОНТРАКТ

`LoginFlow::kind()` даёт машинное имя, по которому `js/bitrix/login.js`
выбирает экран. Других состояний не заводить.

| состояние | когда | что делает UI |
|---|---|---|
| `not_configured` | вебхука нет (стартовое) | форма ввода без ошибки |
| `checking` | идёт `profile` → `scope` | форма заблокирована, ошибки НЕТ |
| `invalid_url` | строка не разобралась | форма + пояснение, СЕТИ НЕ БЫЛО |
| `invalid_credentials` | `INVALID_CREDENTIALS` / `NO_AUTH_FOUND` | «вставьте другой вебхук» |
| `scope_missing` | `insufficient_scope` либо прав не хватает | перечисление недостающих прав |
| `throttled` (Р16) | `QUERY_LIMIT_EXCEEDED` / `OPERATION_TIME_LIMIT` | обратный отсчёт, автоповтора НЕТ |
| `disconnected` | сеть, DNS, портал ответил непонятно | «повторить» |
| `authorized{user, portal}` | обе проверки прошли | оверлей скрыт, поле ввода ОЧИЩЕНО |

Переходы рассылаются кадром `login_state` ВСЕМ WS-подписчикам под тем же
lock'ом, под которым меняется состояние (`B24State::set_login`): клиент
физически не может увидеть переходы в порядке, обратном реальному. Новый
подписчик получает `login_state` первым кадром, а `GET /api/bitrix/status`
отдаёт тот же DTO снапшотом — три источника ОДНОЙ формы означают одну
функцию отрисовки во фронте вместо трёх ветвлений.

`LoginFlow::Authorized` несёт хост портала, но `LoginStateDto` — НЕТ: см.
раздел «Чего нет в /status».

## Почему порядок `profile` → `scope` неизменен

Сначала выясняется, что вебхук вообще принят порталом, и только потом — что у
него есть нужные права. Обратный порядок дал бы «не хватает прав» на чужом
или опечатанном вебхуке, то есть отправил бы человека чинить не то. Порядок
проверяется по журналу стенда
(`b24_stub::a_rejected_webhook_never_reaches_the_scope_call`:
`scope` после отказа `profile` не вызывается вовсе).

## Нужны ОБА права: `im` и `task`

`REQUIRED_SCOPES = ["im", "task"]`, синоним `tasks` части редакций портала
принимается наравне с `task`. Без `im` панель бесполезна целиком. `task`
технически не смертелен (чаты задач приходят и через `im` — чат задачи это
обычный IM-чат), но директория `~/tasks` и карточка над лентой — половина
смысла вкладки, а пересоздать вебхук с недостающей галочкой это операция на
полминуты. Панель, молча работающая наполовину, диагностируется пользователем
несравнимо дороже.

Пустой `scope` (портал вернул `[]`) — это «прав нет», а не «наверное, есть»:
такой ответ даёт полный список недостающих.

## Три формы ввода → один канонический вебхук

`parse_webhook_input` (чистая функция, `login.rs`) принимает то, что реально
копируют из портала:

1. полный адрес с именем метода — `…/rest/1/код/profile.json`;
2. адрес без метода с хвостовым слэшем — `…/rest/1/код/`;
3. он же без слэша — `…/rest/1/код`.

Дополнительно снимаются `?query`, `#fragment` и пробелы по краям (адресную
строку копируют целиком). Основа — регексп контракта §4
`^(https?://[^/\s]+)/rest/(\d+)/([A-Za-z0-9]+)/?$`, разобранный вручную:
крейт `regex` ради одной строки не нужен.

Каноническая форма ОДНА (`https://хост/rest/uid/код/`), и именно она уходит в
файл — три разных ввода дают побайтово одинаковый конфиг (тест
`all_three_input_forms_connect_and_save_the_same_canonical_webhook`).

**Схема:** `http://` разрешён только на петлевой хост и только в изолированном
окружении (непустой `FORGE_BITRIX_CONFIG_PATH`) — то же правило Р17, что для
`base_url_override`, и по той же причине: секрет едет в ПУТИ запроса.

**Разбор живёт ТОЛЬКО на бэкенде.** Во фронте нет ни `split`, ни `match`, ни
`RegExp` — это проверяет `bitrix_contract.test.mjs`. Второй парсер был бы
вторым местом, где можно ошибиться с секретом, и неизбежно разъехался бы с
первым.

## Где хранится секрет и почему НЕ в user_settings.json

`~/.config/forge/bitrix.toml`, права `0600`. `user_settings.json`
читается фронтом и уезжает в браузер — секрету там не место ни при каких
условиях. С мультипортальностью секретов в файле НЕСКОЛЬКО — по одному в
каждой записи массива `[[portals]]`; верхнеуровневое поле `webhook` осталось
legacy-ключом, и вот у него значение по-прежнему одно, а повторное сохранение
его перезаписывает. Устройство файла — на странице `bitrix-multiportal-config`.

Запись (`config::save_webhook_to`) держит четыре инварианта:

1. **read-modify-write** — чужие ключи пользовательского TOML целы;
2. **`0600` в момент СОЗДАНИЯ файла** (`OpenOptions::mode(0o600)` плюс явный
   `chmod` до первого `write_all`: файл мог остаться от упавшего процесса, и
   тогда `mode()` не применяется вовсе) — секрет ни на мгновение не лежит с
   более широкими правами;
3. **атомарность** — `.bitrix.toml.<pid>.tmp` в ТОМ ЖЕ каталоге → `fsync` →
   `rename`: читатель видит либо старый файл, либо новый, но никогда
   обрезанный. Каталог тот же не случайно: `rename` атомарен только внутри
   одной файловой системы;
4. при любой ошибке tmp удаляется, целевой файл остаётся прежним.

Плюс `tighten_perms_if_needed` на КАЖДОЙ загрузке: файл могли создать руками
через `echo >`, скопировать с другой машины или достать из бэкапа — тогда
`0644` чинится на `0600` с warn'ом.

## Что делает logout

Стирает вебхук ЛОКАЛЬНО и больше ничего. **Отозвать входящий вебхук через
REST невозможно** — он остаётся действующим, пока владелец не удалит его в
интерфейсе портала (Разработчикам → Другое → Входящий вебхук). Делать вид,
что мы что-то отозвали на той стороне, было бы враньём в интерфейсе, поэтому
текст `routes::login::LOGOUT_HINT` едет в `/status` полем `logout_hint` и
показывается на экране подключения.

Порядок обратный подключению: сначала диск, потом память. Иначе неудачная
запись оставила бы пользователя «отключённым» до перезапуска, после которого
вебхук вернулся бы из файла. Вместе с секретом сбрасываются кэш клиента
(а значит, и его троттлер) и курсор потока событий: следующий вебхук может
принадлежать другому порталу, и чужой `offset` дал бы либо пустоту, либо
чужую очередь.

## Ограничение Р15: вебхук = один пользователь портала

Вебхук выпускается от имени ОДНОГО сотрудника, и `profile` возвращает ровно
того, чей `user_id` стоит в URL. Следствие для remote-mode: **все, кто открыл
этот devforge, видят переписку владельца вебхука.** Мультипользовательности в
v1 нет; для многопользовательского сценария каждый заводит свой devforge.

Предупреждение обязано быть на экране подключения — оно живёт в
`routes::WEBHOOK_HINT` (поле `hint` ответа `/status`), а не в разметке:
интерфейс портала меняется, а `index.html` браузер держит в кэше PWA
неделями.

## Чего НЕТ в `/status` ни в одном состоянии

Ни кода вебхука, ни любого его куска, ни хоста портала, ни слова
`fingerprint`. Код невозможен по типам (`WebhookUrl` не реализует
`Serialize`), хост исключён решением: `/status` уходит в браузер, в devtools и
в HAR-файл, который человек прикладывает к обращению в поддержку, а хост
сужает перебор кода до одного портала.

Страж: `bitrix_smoke::test_status_never_leaks_the_webhook_in_any_state` +
`assert_no_secret_anywhere`, который ищет ЛЮБУЮ подстроку кода длиной от
восьми символов, и само-тест стража
`test_the_secret_guard_actually_catches_a_leak` (страж обязан падать на целом
коде, на его половине и на хосте — иначе он мог бы тихо превратиться в no-op).
Тот же набор проверок применён к ответам обоих роутов подключения на стенде
(`no_login_response_ever_contains_the_webhook_or_a_piece_of_it`).

Единственное законное место отпечатка (`portal#uid…хвост6`) — логи сервера, и
только из `config::save_webhook_to`.

## `trait LoginBackend` — почему автомат отделён от сети

Две операции, `profile` и `scope`. Благодаря трейту вся матрица переходов
(включая троттлинг и потерю прав) тестируется без портала, без вебхука и без
единого сетевого вызова. Боевая реализация `HttpBackend` поверх `B24Client` не
содержит ни одной ветки логики — только перевод `B24Error` в `LoginError`.

Своей таблицы кодов в `LoginError` НЕТ: перевод идёт через `to_api_error`, то
есть через ту же замороженную таблицу §4, что обслуживает все REST-роуты.
Второй список кодов неизбежно разъехался бы с первым, и «неверный вебхук»
однажды показался бы как «портал недоступен».

## Роуты

| метод | путь | что делает |
|---|---|---|
| POST | `/api/bitrix/login/webhook` | тело `{"webhook": "…"}` — СОДЕРЖИТ СЕКРЕТ |
| POST | `/api/bitrix/logout` | стирает локально, на портал не ходит |

Порядок действий при подключении обратным быть не может: **разобрать** (мусор
→ `400 invalid_input` и состояние `invalid_url` ДО диска и сети, счётчик
вызовов стенда остаётся нулевым) → **сохранить** 0600 атомарно →
**применить** к состоянию (`set_webhook` заодно сбрасывает кэш клиента, иначе
проверка пошла бы со старым секретом) → **проверить** сетью.

Сохранение ПЕРЕД проверкой намеренно: проверка строит клиент из состояния, а
пользователь, закрывший вкладку на середине, всё равно останется с введённым
вебхуком и увидит результат после перезапуска. Обратный порядок потребовал бы
второго пути «проверить, не сохраняя» — то есть второго места, где секрет
живёт в памяти.

Оба роута отвечают `LoginStateDto` — той же формы, что снапшот `/status` и
WS-кадр.

## Стартовая проверка (`spawn_workers`)

Если вебхук есть в конфиге, `spawn_workers` поднимает РОВНО ОДИН фоновый
воркер — однократную проверку `verify_saved_webhook`. Без неё после
перезапуска процесса панель показывала бы `disconnected` до первого нажатия
«подключить», хотя вебхук лежит в файле и совершенно исправен.

Повторов нет намеренно: упавшая сеть не должна превращаться в бесконечный
опрос портала, а кнопка на экране подключения решает ту же задачу по
требованию пользователя. Воркер снимается по `shutdown`-токену, поэтому
остановка сервера не ждёт connect-таймаута портала.

## Фронт

`js/bitrix/api.js` — тонкие обёртки поверх `apiFetch` через общий разборщик
конверта `messenger/http-envelope.js`; таблица путей дословно совпадает с
шапкой `routes/mod.rs` (сверяет `bitrix_contract.test.mjs`).

`js/bitrix/login.js` — оверлей `#b24-login`:

- **идемпотентен**: `renderLoginState` зовут из снапшота `/status`, из
  WS-кадра и из ответа POST'а; повторный вызов не сбрасывает поле, не
  перезапускает обратный отсчёт и не навешивает вторых слушателей
  (`initB24Login` защищён флагом);
- **очищает поле сразу после успеха** — секрет не задерживается в DOM, где он
  доступен любому расширению браузера и попадает в скриншот devtools;
- **ничего не пишет в localStorage/sessionStorage** (проверяется стражем);
- показывает подсказку Р15 и инструкцию «Разработчикам → Другое → Входящий
  вебхук» со ссылкой на документацию;
- при `throttled` ведёт обратный отсчёт и НЕ уходит в автоповтор: повтор
  продлевал бы троттлинг портала.

`_debugLogin()` отдаёт ФАКТ наличия значения в поле (`webhookInDom`), а не
само значение: снимок уезжает в e2e-логи.

## Тесты фазы

Юнит (`login.rs`, без сети): три формы ввода → один канон; мусор отвергается
двенадцатью видами; текст ошибки не цитирует ввод; правило схемы обеими
ветками; `missing_scopes`; вся матрица переходов через подменённый бэкенд;
таблица кодов; заморозка машинных имён; DTO без секрета.

Конфиг (`config.rs`): `0600` при создании И при перезаписи; чинка прав на
загрузке; отсутствие tmp-хвостов; целость файла при падении между записью и
`rename`; чужие ключи; перезапись вместо дописывания; битый TOML; no-op
`clear` по несуществующему файлу; отказ на пустом вебхуке.

Стенд (`b24_stub.rs`, настоящий транспорт): три формы по проводу; порядок
`profile` → `scope`; мусор без единого сетевого вызова; `INVALID_CREDENTIALS`
/ `insufficient_scope` / пустой scope / `QUERY_LIMIT_EXCEEDED` / зависание —
каждый в своё состояние; `0600` по настоящему пути роута; logout без похода
на портал; вставка в рантайме доезжает до подписчиков и будит
`authorized_notify`; смена секрета даёт НОВЫЙ клиент; секрет не в логах.

Фронт: `bitrix_login.test.mjs` (58 проверок на фейковом DOM) и расширенный
`bitrix_contract.test.mjs`.
