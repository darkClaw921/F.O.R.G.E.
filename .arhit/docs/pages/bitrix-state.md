# forge-bitrix — разделяемое состояние `B24State`

Элементная запись Фазы 1 для `plugins/bitrix/src/state.rs` (префикс
`bitrix-` обязателен: имя `state` пересекается с плагинами vk и telegram).

Создаётся один раз в `init`, живёт под `Arc`, раздаётся роутам,
WS-соединениям и фоновым воркерам.

## Поля

| поле | зачем |
|---|---|
| `config` | неизменяемая часть настроек |
| `webhook: RwLock<WebhookUrl>` | ЕДИНСТВЕННАЯ меняющаяся в рантайме часть конфига |
| `broadcast: Sender<B24ServerEvent>` | ёмкость 1024, **без фильтрации** |
| `login: Mutex<LoginFlow>` | переходы автомата строго сериализованы |
| `client: RwLock<Option<(WebhookUrl, Arc<CachedApiClient>)>>` | ОДИН клиент на секрет ⇒ ОДИН троттлер |
| `event_cursor: RwLock<Option<EventCursor>>` | ack-курсор `im.v2.Event.get` (Ф7) |
| `uploads: Mutex<HashMap<String, UploadEntry>>` | TTL 30 минут (Ф9) |
| `health: Arc<RwLock<ConnHealth>>` | **под Arc** — ту же ячейку получит `B24Client` |
| `workers` + `shutdown` | graceful shutdown с грейсом 2 с |
| `authorized_notify: Notify` | вставка вебхука поднимает realtime БЕЗ рестарта |
| `ws_heartbeat`, `ws_idle_timeout` | тайминги — ДАННЫЕ, а не константы |

`CachedApiClient` в Фазе 1 — алиас на `()`: транспорта ещё нет, но поле и его
инвариант объявлены сразу, а Фаза 2 меняет ОДНУ строку.

Тайминги WS лежат в состоянии ровно затем, чтобы интеграционный тест
проверял НАСТОЯЩИЙ цикл на сотнях миллисекунд, а не ждал боевую минуту
(`with_ws_timings`).

## Автомат подключения `LoginFlow`

Восемь состояний, `kind()` даёт машинное имя — КОНТРАКТ с фронтом
(`js/bitrix/login.js` выбирает по нему экран):

`not_configured` · `checking` · `invalid_url` · `invalid_credentials` ·
`scope_missing` · `throttled` · `disconnected` · `authorized`

`from_config` выводит стартовое состояние ИСКЛЮЧИТЕЛЬНО из наличия вебхука —
именно поэтому `init` синхронный и сети не касается.

`set_login` — единая точка перехода: broadcast делается под тем же lock'ом,
что и запись, поэтому клиенты не увидят события в порядке, обратном реальным
переходам. При `Authorized` дополнительно бьёт `authorized_notify`.

## `LoginStateDto` — чего в нём НЕТ

Ни кода вебхука (невозможно по типам), ни хоста портала (исключён решением).
Хост живёт внутри `LoginFlow::Authorized` и нужен серверу для ссылок на
карточку задачи (Ф10) и осмысленного лога, но наружу не выходит: `/status`
уезжает в браузер, в devtools и в HAR-файл поддержки, а хост сужает перебор
кода до одного портала.

## `ConnHealth`

`Ok{at}` / `Down{since, reason}`. `connected(now)` = `false` только ВНУТРИ
окна `HEALTH_GRACE_SECS = 3` после отказа, дальше снова `true`. Окно
намеренно короткое: оно нужно, чтобы пачка запросов сразу после обрыва
получила честный 503 вместо повторного ожидания таймаута, а не чтобы
«запомнить» отказ. `note_down` НЕ сдвигает `since` при повторном отказе —
иначе окно 503 продлевалось бы вечно и здоровье не чинилось бы никогда.

## `EventCursor`

`{offset, saved_at}`, персистится в `<cache_dir>/events.json` (Ф7). `offset` у
портала — это ПОДТВЕРЖДЕНИЕ, а не позиция чтения: неподтверждённые события
переотдаются, поэтому курсор обязан пережить рестарт процесса. `saved_at`
нужен правилу Р18: курсор старше шести часов не заслуживает доверия.

## Реестр загрузок

`take_upload` ПОТРЕБЛЯЕТ запись — именно поэтому повторная отправка с тем же
`upload_id` невозможна: второй запрос получит `409 invalid_state` вместо дубля
сообщения. `evict_stale_uploads(ttl, now)` принимает `now` параметром, чтобы
тест «через 30 минут» не спал полчаса, и НЕ делает файлового ввода-вывода —
удаление staging-файлов забота вызывающего.

## `ws_subscribers()`

Число живых WS-подписчиков — не статистика: воркер событий (Ф7) выбирает по
нему каденс опроса портала (ноль подписчиков ⇒ idle-интервал, Р4).

## Кэш API-клиента (Фаза 2)

`pub type CachedApiClient = crate::api::B24Client` — алиас, объявленный ещё в
Фазе 1 отдельной строкой; Фаза 2 подставила настоящий тип, не тронув ни одного
использования.

`B24State::api_client()` собирает клиент при первом обращении и кэширует его,
ключуя САМИМ СЕКРЕТОМ (double-check под write-lock). Причина не в экономии
аллокаций: вместе с клиентом создаётся троттлер, а троттлер и есть соблюдение
лимита. Два клиента — это два ведра по 2 rps, то есть 4 rps в портал, который
считает бюджет на пару портал+IP и отвечает на превышение не ошибкой, а
обрывами соединений.

Ключ кэша — секрет, потому что смена вебхука обязана дать НОВЫЙ клиент: иначе
после переподключения плагин продолжил бы ходить в портал со старым (а после
logout — со стёртым) кодом. Сброс делает `set_webhook()`, проверка ключа в
`api_client()` — вторая линия.

Ячейка `health: Arc<RwLock<ConnHealth>>` отдаётся клиенту через
`health_handle()`: клиент и состояние обязаны смотреть в ОДНУ ячейку, иначе
data-роуты отдавали бы `503` по собственной копии, ничего не знающей о реальных
вызовах.
