# ws/mod.rs — WebSocket-handler /ws/telegram

## Жизненный цикл соединения

1. `telegram_ws` апгрейдит HTTP в WebSocket. Bearer-auth (в remote-mode) уже
   выполнен middleware'ом хоста; query-параметр `token` существует только
   потому, что браузерный WebSocket не умеет слать заголовок Authorization.
2. `handle_socket` подписывается на broadcast ДО отправки снапшота (событие
   между снапшотом и подпиской иначе потерялось бы навсегда) и ПЕРВЫМ кадром
   отправляет текущий `login_state`.
3. Дальше один `tokio::select!` с `biased`: shutdown-токен -> idle-таймаут ->
   heartbeat -> событие из broadcast -> входящий кадр.
4. `RecvError::Lagged(n)` НЕ рвёт соединение: клиенту уходит `Resync`, он
   перечитывает состояние по REST.
5. Малформленный клиентский кадр НЕ рвёт соединение (может прийти от более
   новой версии фронта) — только warn в лог.

## Тайминги

`HEARTBEAT_INTERVAL` = 15с, `IDLE_TIMEOUT` = 60с (четыре пропущенных пинга).
Инвариант «heartbeat * 2 < idle» закреплён тестом.

С Фазы 6 цикл читает тайминги из `TelegramState::ws_heartbeat` /
`ws_idle_timeout`, а не из констант напрямую. Смысл: интеграционный тест
поднимает состояние через `TelegramState::with_ws_timings` со значениями в
сотни миллисекунд и проверяет НАСТОЯЩИЙ цикл (закрытие молчащего клиента и
выживание отвечающего), не превращаясь в минутный. Продовый путь
`TelegramState::new` всегда подставляет боевые константы — это закреплено
тестом `default_state_uses_production_timings`.

## Почему нет фильтрации по активному диалогу

Echo фильтрует события по conversation_id, потому что чужой чат клиенту не
нужен. Здесь наоборот: unread-бейдж на кнопке ✈ и тосты о новых сообщениях
должны работать, когда открыта ЛЮБАЯ вкладка. Поэтому сервер вещает все
события, а решает, что показать, фронтенд.
