# plugins/tracker/src/ws.rs

WebSocket /ws/tracker — realtime-поток изменений трекера, дословный аналог /ws/todos хоста (tmux-web/src/ws_todos.rs). enum TrackerEvent (serde tag=kind, snake_case): TaskUpsert{task}, TaskRemoved{id}, EntryUpsert{entry}, EntryRemoved{id}, Reload. Точечные кадры есть только у задач и отрезков — у сущностей, которые меняются часто (перетаскивание в канбане, тикающие таймеры); списки, пункты чек-листа и вехи публикуют reload, а пункт вдобавок шлёт task_upsert родителя, потому что от него зависит прогресс n/m. tracker_ws(WebSocketUpgrade, State<Arc<TrackerState>>) — upgrade без единого query-параметра: задачи ГЛОБАЛЬНЫЕ, фильтровать поток по корню проекта (как делает /ws/todos) здесь нечем. handle_socket: подписка на broadcast идёт ПЕРВОЙ, до снимка (обратный порядок терял бы мутации в окне между снимком и подпиской; при этом порядке худшее — дубль, который клиент идемпотентно применит по id); дальше select-цикл на четырёх ветках — сигнал shutdown, событие канала, heartbeat Ping каждые 30 секунд (HEARTBEAT_INTERVAL, первый мгновенный tick съедается), входящие кадры. Отставший клиент (RecvError::Lagged) получает НОВЫЙ СНИМОК, а не разрыв и не просьбу сходить самому: пропущенные события означают, что его состояние разошлось с сервером незаметно для него. snapshot_frame(&TrackerState) -> Value — кадр {kind:snapshot, ...StateDto}; публична ради теста протокола без сетевого соединения. Клиент серверу не шлёт ничего, кроме Pong/Close: все мутации идут через REST, иначе проверку тел пришлось бы дублировать в сокете.
