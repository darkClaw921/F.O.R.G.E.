# tmux-web/static/js/bitrix/state.js

Клиентское состояние вкладки «Битрикс24» (плагин forge-bitrix). Единственный мутируемый объект b24State — импортируется остальными модулями панели и правится ими напрямую, реактивности нет: перерисовку инициирует тот, кто поменял поле.

Поля: dialogs (ЕДИНСТВЕННЫЙ список — он же источник бейджа и белого списка), activeDir ('all'|'chats'|'tasks'|'unread'), messages (Map dialog_id -> MessageDto[] по возрастанию id), activeDialogId, tasks (Map task_id -> карточка; отдельная карта, потому что у задачи может не быть чата вовсе — Р20), uploads, mediaCache (ключ -> objectURL), counters {total, chat, dialog, tasks, notify}, themeMode, enabled, loginState, selfUser, ws, lat, throttled.

Ключевое отличие от js/vk/state.js: директорий ЛОКАЛЬНЫЕ. У VK all/unread/important/unanswered — серверный параметр filter, то есть отдельный запрос и отдельный список dirDialogs. Здесь портал отдаёт ОДИН список im.recent.get, а разделение чаты/задачи/непрочитанные выводится из полей строки (entity_type, unread_count), поэтому второго массива нет и не будет — он был бы копией того же.

Все id — СТРОКИ: dialog_id полиморфен у самого портала (число для личных диалогов, строка 'chat7' для групповых), и единая строковая форма — единственный способ не разветвлять фронт.

Экспорт: b24State, clearB24AccountData() (полный сброс данных аккаунта с ОБЯЗАТЕЛЬНЫМ URL.revokeObjectURL по всему mediaCache — иначе 'разлогинился и снова вошёл' медленно съедает сотни мегабайт), _debugB24State() (снимок для e2e).

В шапке файла заморожен контракт лексики: структурные имена UI остаются телеграмными (dialog/dialogId/dir/media), лексика портала живёт только на границе API — иначе построчный дифф js/vk/chat.js и js/bitrix/chat.js перестал бы быть осмысленным.

ЧТО ДОБАВИЛА ФАЗА 4. currentVisibilityFilter() — действующий белый список диалогов: настройки читаются ЛЕНИВО через window.ForgeApp.state.userSettings (модули панели грузятся раньше, чем приходит ответ /api/user-settings, и снимок со старта застыл бы навсегда), результат кэшируется по СОДЕРЖИМОМУ настроек, а не по ссылке — форма пересобирает объект при каждом сохранении, и ключ по содержимому даёт нужное свойство: сохранённые настройки действуют СРАЗУ, без перезагрузки вкладки. invalidateVisibilityFilter() сбрасывает кэш и зовётся из window.ForgeApp.b24Filter.refresh(). Сам разбор живёт в js/bitrix/visibility.js (normalizeFilter): у него нет ни состояния, ни зависимостей, и его обязаны уметь позвать напрямую и тест, и форма настроек.

Поле dialogs наполняется страницами GET /api/bitrix/dialogs через format.js::mergeDialogs (обновление совпавших строк, сортировка «пины сверху, затем дата»), counters — из GET /api/bitrix/filters и WS-кадра counters.

ФАЗА 5. Поле messages (Map dialog_id -> MessageDto[] по ВОЗРАСТАНИЮ id) перестало быть объявлением и стало рабочим кэшем ленты: js/bitrix/chat.js держит в нём историю каждого открытого диалога, поэтому возврат в диалог рисует прочитанное мгновенно, ещё до ответа сети. Кэш живёт до clearB24AccountData() (logout, падение из authorized, teardown) — там же revoke'аются objectURL медиа-кэша.


Ф9 (отправка файлов): добавлено поле maxUploadBytes — потолок размера
отправляемого файла (Р7). Приходит из GET /api/bitrix/status, а не зашит во
фронт: значение живёт в bitrix.toml, а скрипты браузер держит в кэше PWA
неделями. Ноль означает «сервер ещё не ответил»: клиентская проверка тогда
ничего не отсекает, и решение принимает сервер (413).

Ф10 (задачи): b24State.tasks — Map task_id -> TaskDto. ОТДЕЛЬНАЯ карта, а не поле диалога: у задачи бывает НЕ быть чата вовсе (Р20), и вешать карточку на строку списка означало бы терять такие задачи целиком. b24State.counters получил ВТОРОЕ семейство — expired/new_comments/mentioned (состояние самих задач, tasks.task.counters.get). Складывать его с полем tasks НЕЛЬЗЯ: то считает непрочитанные СООБЩЕНИЯ чатов задач и обнуляется чтением ленты, а эти три числа обнуляются действием над задачей. clearB24AccountData() чистит обе структуры.
