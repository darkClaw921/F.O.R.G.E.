# tmux-web/static/js/bitrix/main.js

Точка сборки вкладки «Битрикс24»: гейт кнопки, постоянный WS, обработчики кадров, бейдж и тосты.

ДВА ВХОДА. initB24Gate() — один раз на загрузке страницы (GET /api/bitrix/status; 404 = плагин выключен, кнопка скрыта, в консоль ничего); поднимает ПОСТОЯННЫЙ WS, поэтому бейдж и тосты работают из любой вкладки devforge. initB24() — на каждом входе на вкладку, идемпотентна.

buildHandlers() (Ф7) — таблица обработчиков всех кадров протокола:
- message_new: вставка в открытую ленту (stick-to-bottom), локальный подъём строки колонки (bumpDialog) БЕЗ запроса к порталу, +1 к бейджу для чужого сообщения в неоткрытой ленте, maybeToast; строки нет в загруженной странице → loadDialogs();
- message_update: appendMessage (замена строки по id);
- message_delete: markDeleted — строка ОСТАЁТСЯ помеченной, а не исчезает (портал удаление не стирает);
- reaction: applyLikes (итоговый список, не дельта);
- dialogs_patch: applyDialogsPatch + recomputeUnread;
- counters: единственный серверный источник бейджа;
- presence: онлайн живёт в строке списка;
- resync: resyncPanel();
- open: при ПЕРЕоткрытии сокета (wsOpens > 1) — полный resyncPanel;
- typing/read/task_update/upload_progress/download_progress: заглушки (кадры объявлены, но не приходят или ждут своих фаз).

recomputeUnread() — ЕДИНСТВЕННЫЙ путь обновления #b24-unread-badge. При ДЕЙСТВУЮЩЕМ белом списке серверный total игнорируется целиком (расщепить готовое число нечем) и считается по видимым строкам.

maybeToast(frame) — пять обязательных гейтов: своё исходящее, системное, muted ИЗ КАДРА (сервер знает chat.mute_list, фронт — только загруженную страницу), белый список, открытая лента при активной вкладке, окно тишины TOAST_THROTTLE_MS=20с на диалог. Канал общий — #echo-toasts.

resyncPanel() — полное перечитывание: список, счётчики, открытая лента. Зовётся по кадру resync (Lagged Р19 либо протухший курсор Р18) и после каждого реконнекта: «догрузка снизу» не приносит ни удалений, ни правок.

applyLoginState(dto) — одна точка на три источника состояния (/status, ответы POST подключения, кадр login_state).

Тест: tmux-web/tests/frontend/bitrix_realtime.test.mjs.


Ф9 (отправка файлов): initB24() зовёт initUpload() (порядок навески: колонка ->
лента -> медиа -> ЗАГРУЗКИ -> хоткеи); buildHandlers().upload_progress ведёт в
upload.onUploadProgress (применяется только фаза portal — свой прогресс приёма
вкладка знает из XHR точнее, а кадры фазы client нужны второй открытой
вкладке); teardownB24() зовёт teardownUpload() ПОСЛЕ teardownMedia (очередь
держит летящие XHR и objectURL миниатюр); initB24Gate() кладёт
status.max_upload_bytes в b24State.maxUploadBytes; _debugState() включает
upload: _debugUploadState().

Ф10 (задачи): initTasks({onReloadFeed,onTasksLoaded}) навешивается ДО initDialogs — выбор строки сразу зовёт showTaskFor, и слушатель кнопок карточки к этому моменту обязан быть. onSelect дополнительно зовёт showTaskFor(dialog): для обычного чата карточка ПРЯЧЕТСЯ (оставленная шапка чужой задачи опасна — кнопки в ней рабочие). onDir('tasks') тянет карточки задач: статусы и сроки живут в tasks.task.list, а не в списке диалогов. Обработчик кадра task_update применяет карточку целиком (матрица в ней уже новая). Обработчик counters читает три новых поля второго семейства. resetTasks() зовётся при logout, при падении из authorized и в teardownB24. _debugState() включает tasks.

Ф11 (обвязка UX). initB24() навешивает мобильную раскладку ПЕРВОЙ (initB24Mobile: её слушатель Escape обязан оказаться в очереди раньше Escape ленты и лайтбокса — иначе первый Esc на узком экране снимал бы курсор клавиатуры, оставляя колонку висеть поверх ленты) и хоткеи ПОСЛЕДНИМИ (initB24Keynav: capture-слушатель обязан встать поверх уже навешенных построчных обработчиков). onSelect дополнительно зовёт resetB24Keynav() (курсор адресовал строку ПРОШЛОЙ ленты) и closeB24ContactsAfterSelect() (колонку открывали ради выбора — после него она уезжает).

showNotice(text) — канал коротких уведомлений клавиатуры («Скопировано», «У этого сообщения нет вложений»). Общий стек #echo-toasts, но БЕЗ префикса «Б24 · »: это ответ на собственное нажатие пользователя, а не событие портала.

initDialogs получает четвёртый колбэк onCounters: счётчики портала приезжают ответом GET /api/bitrix/filters (в dialogs.js), а бейдж вкладки живёт здесь. Обратный импорт dialogs.js -> main.js замкнул бы граф модулей, поэтому связь колбэком. Без него бейдж обновлялся бы ТОЛЬКО кадром counters из WS и на свежей загрузке оставался бы пустым, хотя число уже получено по REST. Писатель у бейджа по-прежнему ровно один — recomputeUnread().

teardownB24() зовёт teardownB24Keynav(): capture-слушатель стоит на document и панель переживает.

_debugState() — агрегат ВСЕХ модулей панели и контракт для e2e (e2e/tests/ui/bitrix-ui.spec.ts читает его через import('/js/bitrix/main.js')). Ф11 добавила разделы mobile (_debugB24Mobile), theme (_debugB24Theme), keys (_debugKeynavState) и filter (разобранный белый список тем же currentVisibilityFilter, которым пользуются колонка, бейдж и тосты). СЕКРЕТА В СНИМКЕ НЕТ: вебхук во фронт не приезжает вовсе, а login отдаёт лишь факт заполнения поля (webhookInDom). Сторож — tests/frontend/bitrix_keys.test.mjs: сериализует снимок целиком при заполненном поле и ищет в нём код вебхука, '/rest/' и адрес портала.

## МУЛЬТИПОРТАЛЬНОСТЬ (Ф5/Ф8)

Точка сборки вкладки «Битрикс24».

ДВА ВХОДА: initB24Gate() — один раз на загрузке страницы (GET /api/bitrix/status; 404 = плагин выключен, это НЕ ошибка и в консоль ничего не пишется; 200 ⇒ кнопка Ⓑ, строка вкладок порталов, ПОСТОЯННЫЙ WS). initB24() — на каждом входе на вкладку, идемпотентна по local.inited.

ЕДИНСТВЕННЫЙ ПУТЬ ОБНОВЛЕНИЯ БЕЙДЖА — recomputeUnread(); setUnreadBadge приватна.

МУЛЬТИПОРТАЛЬНОСТЬ (Ф8):
- initB24Portals поднимается в ГЕЙТЕ (активный портал обязан быть выбран до первого запроса данных), затем await loadPortals() и только потом connectB24Ws;
- switchPanelToPortal(portalId, rememberedDialogId) — колбэк onSwitch строки вкладок: ПОЛНЫЙ reset панели в значимом порядке (teardownUpload -> clearB24AccountData -> resetDialogs -> resetChat -> resetTasks -> resetB24Keynav -> recomputeUnread), затем refreshPortalStatus: перечитывание /status уже с новым заголовком, applyLoginState, await loadPanelData() и возврат в последний открытый диалог этого портала;
- ПОЛНОГО КЭША СОСТОЯНИЯ НА ПОРТАЛ НЕТ И НЕ БУДЕТ — осознанное ограничение: кэш означал бы правку всех фронтовых модулей и разъезд с построчным диффом js/vk ↔ js/telegram ↔ js/bitrix, который здесь главный инструмент сопровождения. Запоминается только последний открытый диалог (portals.js);
- НЕЗАВЕРШЁННАЯ ЗАГРУЗКА ФАЙЛА ПРИ ПЕРЕКЛЮЧЕНИИ ОТМЕНЯЕТСЯ: upload_id выдаёт staging КОНКРЕТНОГО портала, а второй этап уезжает в диалог, которого в новом портале нет;
- обработчик кадра portals -> applyPortalsFrame (строка вкладок обновляется без перезагрузки);
- обработчик foreign -> onForeignFrame(msg): counters ставит ТОЧНОЕ число бейджу вкладки, message_new двигает бейдж на 1 и даёт тост. В ленту, список, карточку задачи и кэш медиа кадр соседа не попадает НИКОГДА;
- loadPanelData() возвращает промис загрузки СПИСКА — дождаться его нужно ровно переключению портала.

maybeToast(frame, portalId): гейты — сообщение чужое, диалог не заглушён (источник истины поле muted КАДРА), проходит белый список, это не открытая лента при открытой вкладке (гейт применим только к СВОЕМУ порталу), окно тишины TOAST_THROTTLE_MS с ключом (портал, диалог) — dialog_id полиморфен и одно значение у двух порталов означает разные чаты. Префикс: 'Б24 · ' плюс название портала (усечённое TOAST_PORTAL_MAX), когда порталов больше одного. Клик по тосту соседнего портала запоминает диалог и переключает вкладку — selectDialog сразу нельзя, списка того портала ещё нет.
ОГРАНИЧЕНИЕ ДО Ф7.4: белый список один на все порталы, поэтому при действующем фильтре тост чужого портала подавляется (fail-closed).
