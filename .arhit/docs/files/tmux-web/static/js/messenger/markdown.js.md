# tmux-web/static/js/messenger/markdown.js

Общий слой мессенджеров: разбор и БЕЗОПАСНЫЙ рендер Markdown (эпик forge-vkmd-b-4fyj).

ЗАЧЕМ. Ответы Claude (разбор чата и тред вопросов в панели VK) приходят с Markdown-разметкой и до этого показывались сырым текстом: пользователь читал «**жирный**» и «|таблица|» буквально.

ПОЧЕМУ В messenger/, А НЕ В vk/. Разбор Markdown не является свойством ВКонтакте: те же ответы модели будут показывать панели Telegram и Битрикс24. Модуль написан по правилам общего слоя (follow-core.js, hotkeys-core.js, http-envelope.js, theme-core.js, ws-core.js): никаких импортов панелей, никакого обращения к глобальному document. Классы разметки нейтральные (md-*), красит их панель — в css/vk.css под .vk-analysis-out и .vk-analysis-thread.

ГЛАВНЫЙ ИНВАРИАНТ. Ни одного innerHTML / insertAdjacentHTML / outerHTML / document.write. Текст порождён моделью ИЗ ПЕРЕПИСКИ С ПОСТОРОННИМИ ЛЮДЬМИ, то есть это недоверенный ввод ровно в том же смысле, что и тело сообщения; инвариант панели VK «в DOM только через textContent» (js/vk/main.js:44-45) распространяется и сюда. Структурно инвариант держит секция 4 теста tmux-web/tests/frontend/messenger_markdown.test.mjs: она читает файл как текст и падает, если запрещённая строка вернётся.

ПОЧЕМУ НЕ БИБЛИОТЕКА. devforge обязан работать офлайн и не тянуть внешние ассеты; вендорить marked/markdown-it + DOMPurify с их собственной поверхностью XSS ради шести видов разметки — плохой размен. Весь риск здесь сосредоточен в ОДНОЙ функции safeHref, которую проще доказать, чем аудировать чужой санитайзер.

ЭКСПОРТЫ:
  parseMarkdown(text) -> Block[]            — чистая функция, без DOM
  parseInline(src, depth) -> Inline[]       — инлайн-разбор одной логической строки
  safeHref(raw) -> string|null              — белый список схем ссылок
  renderMarkdown(ast, doc) -> DocumentFragment — только createElement/createTextNode/setAttribute
  renderMarkdownText(text, doc)             — parse + render одним вызовом

ОБЪЁМ ПОДДЕРЖКИ. Блоки: заголовки #..###### (7 решёток = абзац), маркированные (-,*,+) и нумерованные (N. / N)) списки с вложенностью по отступу и сохранением стартового номера, ограждённые блоки кода ``` и ~~~ (язык сохраняется, подсветки НЕТ), цитаты > (вложенные, с блоками внутри), горизонтальная линия (---, ***, ___), GFM-таблицы с выравниванием, абзацы. Инлайн: **жирный**, *курсив* и _курсив_ (не внутри слова), `код` (наивысший приоритет — внутри разметка не разбирается), ~~зачёркнутый~~, [текст](url). Намеренно НЕТ: изображений (внешний запрос из панели с перепиской — утечка Referer и трекинг-пиксель), HTML-вставок, сносок, автоссылок, заголовков setext.

ПРАВИЛО ДЕГРАДАЦИИ: непонятная или битая разметка становится обычным текстом, а не пропадает — терять кусок ответа модели нельзя, пользователь не узнает, что чего-то не увидел. Незакрытый блок кода дочитывается до конца текста (модель регулярно обрывает вывод).

ФОРМА AST (JSDoc-typedef в шапке файла). Блоки: paragraph{text,inline}, heading{level,text,inline}, hr, code{lang,text}, blockquote{blocks}, list{ordered,start,marker,items[{text,inline,children}]}, table{align,header,rows}. Инлайн: text{value}, code{value}, strong/em/strike{children}, link{href,children}. У блоков с инлайном СОХРАНЯЕТСЯ и исходный text — по нему тесты проверяют границы блоков, а вызывающий код может показать сырьё (стриминг разбора до кадра analysis_done рисует сырой текст).

ОГРАНИЧЕНИЯ: MAX_NESTING = 12 (глубже цитаты и списки остаются текстом — защита от рекурсии на тысячу кадров), TAB_WIDTH = 4.

Тест: tmux-web/tests/frontend/messenger_markdown.test.mjs (251 проверка, пять секций).
