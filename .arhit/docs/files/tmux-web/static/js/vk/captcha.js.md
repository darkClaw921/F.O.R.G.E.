# tmux-web/static/js/vk/captcha.js

Оверлей captcha панели VK (#vk-captcha, Ф3). Аналога в Telegram нет.

Почему оверлей ОТДЕЛЬНЫЙ, а не шаг логина: VK возвращает код 14 на ЛЮБОЙ метод — он может прилететь посреди отправки сообщения, при пометке прочитанным, при загрузке истории. Шаг внутри #vk-login означал бы, что ради символов с картинки пользователю показывают экран входа, будто его разлогинило. Слой z-index 7, поверх всего включая #vk-login.

Экспорт: initCaptcha(), requestCaptcha(source) -> Promise<{sid,key}|null>, withCaptcha(fn), closeCaptcha(), isCaptchaOpen(), _debugCaptcha().

Четыре правила (каждое — отдельная проверка в tests/frontend/vk_captcha.test.mjs):
1. картинка грузится ЧЕРЕЗ ПРОКСИ GET /api/vk/captcha/:sid (captchaImageUrl), а не по прямому captcha_img — прямой адрес отправил бы браузер пользователя на серверы VK со всеми его cookie;
2. повтор ровно ОДИН: второй captcha_required подряд показывает новую картинку (состояние не остаётся протухшим), но автоповтор не зацикливается — ошибка уходит вызывающему;
3. пока оверлей открыт, isCaptchaOpen() = true, и планировщик js/vk/ratelimit.js (Ф4) не выпускает фоновые запросы: иначе они сгенерируют вторую captcha, пока пользователь разбирает первую;
4. отмена (Esc / CANCEL / клик по подложке) резолвит null — вызывающий ОБЯЗАН показать системную строку, молчание после закрытия выглядит как зависшая панель.

Повторный requestCaptcha с тем же sid возвращает то же ожидание (login_state приходит и снапшотом, и кадром WS — второй оверлей на ту же задачу был бы гонкой); новый sid заменяет картинку, а прошлое ожидание честно резолвится null.

Честно о покрытии: на пользовательском токене captcha возникает почти исключительно при массовых рассылках, то есть в разработке этот путь скорее всего ни разу не сработает вживую. Покрытие — стенд plugins/vk/tests/vk_stub.rs, юнит-маппинг кода 14 и node-тест; живого срабатывания не ждём.
