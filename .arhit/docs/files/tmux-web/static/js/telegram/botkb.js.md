# tmux-web/static/js/telegram/botkb.js

Клавиатуры ботов Telegram: inline + reply (дефект D2 — «нету поддержки ботов, ни кнопок которые
появляются»). Новый модуль, ~1000 строк.

ДВЕ РАЗНЫЕ СУЩНОСТИ, ПУТАТЬ НЕЛЬЗЯ (контракт dto.rs::ReplyMarkupDto.kind):
- inline — клавиатура ПОД КОНКРЕТНЫМ сообщением, живёт ровно столько, сколько живёт сообщение;
  нажатие уходит в Telegram как messages.getBotCallbackAnswer(peer, msg_id, data);
- keyboard / hide / force_reply — СОСТОЯНИЕ ДИАЛОГА, а не свойство сообщения. Официальные
  клиенты держат такую клавиатуру над полем ввода, пока бот не пришлёт другую (или hide).
  Поэтому она рисуется ПОЛОСОЙ над #tg-prompt, а не под строкой лога: иначе после десяти
  сообщений в ленте висело бы десять одинаковых клавиатур и ни одна не была бы «текущей».
  Узел полосы создаётся в JS и вставляется перед #tg-prompt — index.html не тронут.

СТРУКТУРА ФАЙЛА. Первая половина — ЧИСТАЯ логика без DOM (нормализация разметки, классификация
кнопки, разбор ответа бота, белый список схем URL, выбор актуальной reply-клавиатуры), покрыта
node-тестом tmux-web/tests/frontend/telegram_botkb.test.mjs (137 ассертов). Вторая половина —
рисование и жизненный цикл.

КОНСТАНТЫ: BUTTON_TEXT_MAX=48 (code points подписи), PLACEHOLDER_MAX=64, MAX_ROWS=32,
MAX_ROW_BUTTONS=12, ANSWER_TEXT_MAX=400. Потолки размера нужны потому, что разметка пришла от
ЧУЖОГО бота через WS: «клавиатура» из десяти тысяч рядов подвесила бы вкладку на рендере.

БЕЗОПАСНОСТЬ (обе меры критичны — контент чужой):
- подпись кнопки ставится ТОЛЬКО через textContent, никакого innerHTML; скобки [ … ] рисует CSS
  (::before/::after), поэтому в текстовом узле лежит ровно подпись бота;
- URL проверяется белым списком схем (http/https/tg) ПОСЛЕ вычистки управляющих символов:
  браузер трактует "java\0script:" как javascript:, а наивная регулярка — как «схемы нет».
  Отвергаются также //evil.com и https:evil.
- из подписи вырезаются управляющие символы и bidi-override (U+202E переворачивает строку —
  спуфинг «удалить»/«оставить»); ZWJ сохраняется (эмодзи), обрезка по code points.

АНТИ-FLOOD: повторные нажатия callback-кнопки блокируются на время запроса (кнопка disabled) —
Telegram считает каждое нажатие обращением к боту, дребезг мыши это прямой путь к FLOOD_WAIT на
аккаунте пользователя. 429 flood_wait НИКОГДА не ретраится сам: кнопка гаснет с обратным
отсчётом, повтор только явным кликом (тот же класс риска, что у login/start в api.js).

ЗАВИСИМОСТИ: ../core/dom.js ($tgInput, $tgPrompt), ../echo/notifications.js (notify),
./api.js (sendCallback), ./state.js (tgState). Отправка текста НЕ дублируется — chat.js::send
передаётся колбэком в initBotKeyboards.

CSS: .tg-kb / .tg-kb-row / .tg-kb-btn (+ модификаторы -url/-unsupported/-pending/-wait),
.tg-kb-bar / -head / -title / -close / -rows / -hint / -show / -collapsed. Только токены темы,
поэтому обе темы работают без отдельных правил.

АВТОПРОКРУТКА ПОСЛЕ НАЖАТИЯ (дефект «нажал кнопку — сообщение выросло и уехало за экран»). У initBotKeyboards появился второй колбэк — `onButtonPress(dialogId, messageId)`; в продакшене это chat.js::noteButtonPress, включающий «следование» ленты за парой (диалог, message_id) на 12 секунд (см. js/telegram/follow.js).

Зовётся из runAction ПЕРВЫМ делом, ДО отправки запроса: правка сообщения приезжает отдельным WS-кадром `message_edited` и вполне может опередить ответ на callback, так что регистрация «после ответа» не срабатывала бы в самом частом случае — у быстрого бота.

Только для действий 'callback' и 'send-text' — они реально меняют ленту. 'open-url' уводит в другую вкладку, 'inline-query' лишь заполняет поле ввода; включать для них следование значило бы 12 секунд дёргать прокрутку на постороннем событии.

Вызов обёрнут в try/catch с console.debug: автопрокрутка — удобство ПОВЕРХ нажатия, её падение не должно отменять сам callback боту.

Аргументы нормализуются здесь же: dialogId → строка (null ⇒ ''), messageId → число (`Number(...) || 0`). Ноль означает «кнопка reply-клавиатуры, конкретного сообщения нет» — follow.js трактует его как следование за диалогом целиком, и доскролл идёт через chat.js::onNewMessage.

Граница модулей не нарушена: botkb.js по-прежнему не знает ни про #tg-log, ни про ResizeObserver, ни про prefers-reduced-motion — он только сообщает факт нажатия, ровно как с onSendText.
