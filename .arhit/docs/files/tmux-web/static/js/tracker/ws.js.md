# tmux-web/static/js/tracker/ws.js

WebSocket-клиент /ws/tracker панели «Мои задачи».

Образец — js/ws/todos-ws.js: та же лестница реконнекта и тот же polling-фолбэк. Общее ядро js/messenger/ws-core.js НЕ используется намеренно: оно построено вокруг JSON-кадра ping и оценки задержки, а трекер шлёт heartbeat протокольным Ping фрейма WebSocket, на который браузер отвечает сам. Тащить чужой контракт значило бы завести мёртвый код и второй смысл у поля kind.

Контракт кадров (plugins/tracker/src/ws.rs): snapshot (весь StateDto, приходит ПЕРВЫМ кадром при подключении и после Lagged), task_upsert, task_removed, entry_upsert, entry_removed, reload.

Почему снимок приходит кадром, а не запрашивается отдельно: между ответом GET /api/tracker/state и открытием сокета есть окно, где события теряются молча. Один канал закрывает его по построению, и после разрыва панель не дублирует и не теряет строк — новый снимок ЗАМЕЩАЕТ состояние целиком.

Почему сокет закрывается при уходе с вкладки (в отличие от трёх мессенджеров, чьи соединения постоянны ради бейджа непрочитанного): трекеру считать нечего, задачи не приходят извне, их заводит сам пользователь. После disconnectTrackerWs() не остаётся НИ ОДНОГО таймера — ни реконнекта, ни polling'а; это отдельный критерий приёмки фазы 4.

Экспорт: WS_BACKOFFS_MS [1000,2000,5000,10000], POLL_INTERVAL_MS 15000, SERVER_FRAMES, frameToHandler(raw) — ЧИСТАЯ функция разбора кадра в пару {name, arg} (кадр без обязательного поля превращается в reload, чтобы событие не потерялось), connectTrackerWs(handlers) (идемпотентен: при живом сокете только обновляет handlers), disconnectTrackerWs(), isTrackerWsOpen(), _debugWsState() для e2e.
