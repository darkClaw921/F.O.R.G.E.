# tmux-web/static/js/tracker/render-kanban.js

Режим kanban панели трекера: доска задач по колонкам статуса.

Что делает. Строит доску из пяти колонок, совпадающих один в один со значениями TaskStatus модели (plugins/tracker/src/models.rs): inbox · today · doing · waiting · done. Колонка — это не отдельная сущность и не поле задачи: статус и есть колонка, поэтому доска и лента показывают одну и ту же задачу согласованно, а перенос карточки — это обычный PATCH /api/tracker/tasks/:id/status.

Ключевые функции.
- COLUMNS — замороженный список колонок (id + подпись). Число и порядок колонок менять только вместе с TaskStatus.
- groupByStatus(tasks) — раскладка задач по колонкам с сохранением общего порядка order; чистая, покрыта tests/frontend/tracker_kanban.test.mjs.
- renderKanban(container, view) — отрисовка доски и установка обработчиков drag'n'drop (один раз на контейнер, флаг dataset.kbDndInstalled).
- card(task, view) — карточка: приоритет, заголовок, теги, срок, время (узел помечен data-trk-task-time, его раз в секунду обновляет общий тикер js/tracker/timer.js).

Перетаскивание. dragstart/dragover/drop навешены на контейнер доски, а не на карточки: view пересоздаётся каждой отрисовкой, и обработчик из замыкания протух бы после первого же кадра WS. Наружу отдаётся одно событие onMove(movedId, status, targetId, after) — доска не решает, куда именно встала карточка внутри колонки, полный порядок пересобирает main.js (planOrder из render-list.js) и отправляет одним POST /api/tracker/tasks/reorder. Во время активного drag перерисовка откладывается: кадр WS, пришедший в середине переноса, порвал бы сам drag.

Оптимистичный перенос. Карточка визуально уезжает в новую колонку сразу, а при отказе сервера возвращается назад с сообщением; refreshTracker в откате не зовётся, если ответа не было вовсе, иначе снимок затирает текст ошибки.

Ограничения. Доска в директории ~/today пуста по построению — директории сайдбара сами построены на статусах; для полной картины нужен ~/all.
