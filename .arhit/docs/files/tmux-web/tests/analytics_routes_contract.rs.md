# tmux-web/tests/analytics_routes_contract.rs

Страж контракта API аналитики (Фаза 3). Поверхность /api/analytics/* описана дважды — вызовами .route(...) в tmux-web/src/main.rs и таблицей ANALYTICS_ROUTES в tmux-web/static/js/analytics/api.js — и между этими описаниями нет ни компилятора, ни общего типа. Расхождение не ломает сборку и не пишет ни строчки в лог: клиент уходит по несуществующему пути, получает 404 от статик-фолбэка, и дашборд остаётся пустым.

Четыре теста:
1. the_analytics_routes_match_in_both_directions — составы совпадают поимённо в обе стороны. Разбор main.rs идёт по БАЛАНСУ СКОБОК от '.route(', а не построчно: многострочная регистрация (как у соседнего /api/user-settings) при построчном разборе потерялась бы молча. Методы (get/post/put/patch/delete) опознаются на границе идентификатора, иначе get(get_analytics_status) дал бы ложное второе совпадение внутри имени хендлера. Порог «не меньше 4 роутов» с обеих сторон — защита от сломавшегося разбора: два пустых списка совпали бы между собой и сняли бы проверку. Верхней границы нет намеренно.
2. the_analytics_route_handlers_and_clients_exist — каждому роуту соответствует объявленный async fn в main.rs и export function в api.js. Имя в таблице, за которым ничего нет, — та же молчаливая дыра: import вернёт undefined, и вызов упадёт только в момент клика.
3. the_analytics_client_never_calls_fetch_directly — api.js ходит в сеть только через apiFetch. Комментарии пропускаются: в самом api.js слово fetch( стоит в объяснении, почему его нельзя звать.
4. the_analytics_client_is_inside_the_embedded_static_dir — файл лежит в static/, иначе он есть в репозитории и отсутствует в бинаре.

Сравнение текстовое по исходникам: поднимать сервер ради четырёх строк дороже, чем прочитать два файла (тот же приём у meet_contract.test.mjs). Запуск: cargo test -p devforge analytics.
