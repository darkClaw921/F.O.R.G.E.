# js/vk/ratelimit.js

tmux-web/static/js/vk/ratelimit.js — клиентский планировщик запросов под лимит VK 3 rps (Ф4.8, НОВЫЙ). Покрыт tests/frontend/vk_ratelimit.test.mjs (45 проверок на виртуальных часах).

ЗАЧЕМ ОТДЕЛЬНО ОТ СЕРВЕРНОГО ТРОТТЛЕРА: он решает ДРУГУЮ задачу. Bucket на бэкенде укладывается в лимит; этот — не даёт попасть в очередь запросам, которые уже неактуальны. Пользователь, прощёлкавший десять бесед, иначе честно дождётся всех десяти историй.

createLimiter({minIntervalMs, burst, now, schedule, frozen}) — token bucket (MIN_INTERVAL_MS=380 с запасом на дрожание, BURST=3) с ДВУМЯ очередями приоритетов: user обгоняет bg. Тайминги читаются из объекта опций на каждом обращении (тот же приём, что with_retry_delays на бэкенде) — иначе тесты панели ждали бы настоящие 380 мс на запрос.

createCoalescer({controller}) — по ключу живёт ПОСЛЕДНИЙ запрос, предыдущий ОТМЕНЯЕТСЯ через AbortController (брошенный fetch продолжал бы занимать место в серверной очереди). fn вызывается синхронно; завершившийся старый запрос снимает ТОЛЬКО свой контроллер.

dropStale(gen, current) / createGeneration() — отменённый fetch всё равно может доехать до .then, и без поколения история покинутой беседы дорисовалась бы поверх открытой.

ОБЩИЕ НА ВКЛАДКУ: vkLimits (мутируемые тайминги) + vkLimiter + vkCoalescer — по одному экземпляру, потому что бюджет 3 rps выдаётся на ТОКЕН; frozen читает vkState.captcha: пока открыт оверлей captcha, фоновые запросы заморожены — иначе они породят вторую captcha.
