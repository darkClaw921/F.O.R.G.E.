# attach.rs

plugins/vk/src/attach.rs — разбор вложений VK в MediaDto (Ф4.2/Ф7, НОВЫЙ файл; аналога в plugins/telegram нет: там вложение одно на сообщение).

ЧТО ДЕЛАЕТ. Две половины, обе ЧИСТЫЕ (ни сети, ни диска, ни состояния):
  1. Классификация и метаданные: media_list(&[AttachmentRaw]) -> Vec<MediaDto> (по одному DTO на вложение, index = ПОЗИЦИЯ в исходном массиве), media_from_attachment(index, att), first_kind(&[AttachmentRaw]) -> Option<String> (вид первого вложения для превью цитат и пересланных без сборки полного списка).
  2. Выбор файла для скачивания: pick_size, url_for(att, MediaKind) -> Option<String>, http_url(&str) -> Option<String>. Результат живёт ровно на время одного скачивания — URL вложений VK подписанные и протухающие и НЕ КЭШИРУЮТСЯ никогда.

ГЛАВНЫЙ ИНВАРИАНТ (введён при починке дефекта «не работают превью ссылок»):
  has_thumb == url_for(att, Thumb).is_some()
  has_full  == url_for(att, Full ).is_some()
media_from_attachment сначала зовёт приватную describe(index, att) (только метаданные: вид, mime, размер, геометрия, длительность, имя, заголовок, waveform, player_url, link_url), а потом ПЕРЕЗАПИСЫВАЕТ оба флага результатом url_for. Ни одна ветка from_* больше не выставляет их сама. Смысл: раньше обещание («у ссылки есть photo.sizes ⇒ превью есть») и способность его выполнить (url_for) жили в разных функциях и могли разъехаться от правки любой из них — наружу это вылезало как карточка, которая просит превью и получает 404 no_media. Побочный (желанный) эффект: флаги стали строже там, где VK прислал размер без адреса или с адресом нечитаемой схемы. Гейт — тест promises_never_outrun_url_for (таблица по ВСЕМ видам словаря, включая заведомо пустые + проверка, что таблица покрывает весь словарь) и сквозной стенд-тест vk_stub.rs::every_promised_thumb_is_actually_downloadable (флаги из messages.getHistory, байты из messages.getById).

ГРАНИЦЫ. MAX_ATTACHMENTS=10 (документированный предел VK; заодно не даёт испорченному ответу переполнить u8-индекс, который входит в ключ медиа-кэша), MAX_TITLE_CHARS=200 (имя файла приходит от отправителя, то есть это чужой ввод), MAX_WAVEFORM=200, THUMB_MIN_PX=200 (нижняя граница «полезного» превью).

ВЕТКИ ПО ВИДАМ (describe): photo (геометрия по НАИБОЛЬШЕМУ размеру — порядок sizes VK не гарантирует, а превью 75x75 дало бы квадрат вместо панорамы), video (player_url; has_full=false ВСЕГДА, потому что url_for(_, Full) у video возвращает None: вложение video у VK не содержит воспроизводимого файла, video.get отдаёт адрес СТРАНИЦЫ-плеера, а прямые files.* доступны только владельцу), audio (artist — title), audio_message (длительность + waveform), doc (mime по расширению, fallback на числовой doc.type 3/4/5/6; вид карточки остаётся document), sticker (fallback на images_with_background; для Full предпочтителен вариант С ФОНОМ), graffiti, link (заголовок + геометрия превью + link_url).

url_for ПО ВИДАМ (thumb/full): photo sizes[]/sizes[] max; doc preview.photo.sizes[]/doc.url; audio_message нет/link_ogg,link_mp3; audio нет/audio.url; sticker images[]/images_with_background[] max; graffiti url/url; video image[] (иначе first_frame[])/НЕТ; link превью ссылки/НЕТ. Остальные члены группы other (wall, market, article, poll, gift, story, ...) содержимого не разбирают вовсе — url_for честно отдаёт None, значит has_thumb=false, и карточка сразу рисует значок вместо запроса, который вернул бы no_media.

ССЫЛКИ НАРУЖУ — РОВНО ДВА ПОЛЯ, и ни одно не адресует CDN вложений:
  * MediaDto::player_url — страница-плеер VK (файла у video не существует);
  * MediaDto::link_url — адрес вложения link, тот, что прислал СОБЕСЕДНИК. Это содержимое переписки, а не инфраструктура VK: карточка без перехода по такой ссылке не делает того единственного, ради чего ссылку и присылают. Раньше поля не было вовсе, и кнопка перехода на карточке ссылки была бессмысленна.
Оба проходят http_url (белый список схем http/https). http_url применяется ДВАЖДЫ по разным поводам: к адресу файла (иначе подмена ответа VK превращалась бы в чтение локальных файлов сервера через file://) и к link.url (там javascript:/data: — не теория, а то, что отправитель может набрать руками). Фронт проверяет второй раз — js/vk/format.js::webUrl.

ТЕСТ УТЕЧКИ. Бывший no_vk_urls_leak_except_the_video_player переименован в attachment_cdn_urls_never_leak и ОСЛАБЛЕН ОСОЗНАННО: он по-прежнему ловит CDN-адреса вложений (sun.example, psv4.example, vk.com/doc, vk.com/graffiti) и access_key, но допускает player_url и link_url. Разница по существу: CDN-адрес подписан, протухает, ведёт на инфраструктуру VK и заставил бы браузер сходить туда с нашим Referer — а player_url/link_url ведут туда, куда пользователь и собирался, и альтернативы у них нет. Чтобы ослабление не превратилось в «защиту сняли», тест дополнительно требует: обе разрешённые ссылки ПРИСУТСТВУЮТ (иначе «утечки нет» достигалось бы пустым DTO) и полей-URL в сериализованном MediaDto ровно столько, сколько перечислено — ТРЕТЬЕ поле с http-адресом провалит тест, даже если его содержимое не совпало ни с одной запрещённой строкой.

ПРОЧИЕ ИНВАРИАНТЫ. Неизвестный attachment.type -> MediaDto{kind:"unsupported"}, а НЕ ошибка разбора: VK добавляет типы без предупреждения, и падение стоило бы пользователю всей страницы переписки ради одной карточки. Индексы не сдвигаются: неизвестные вложения НЕ выбрасываются из списка — иначе ключ медиа-кэша указывал бы на другой файл.

ЗАВИСИМОСТИ: crate::api::schema (AttachmentRaw и вложенные), crate::dto::MediaDto, crate::media_cache::MediaKind, mime_guess. Потребители: dto::message_from_raw (attachments + media=первое), dto::reply_to_from_nested и flatten_forwards (first_kind), routes::media (url_for перед каждым скачиванием).
