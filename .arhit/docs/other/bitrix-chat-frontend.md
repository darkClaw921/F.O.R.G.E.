# bitrix-chat-frontend

ЛЕНТА ДИАЛОГА И ЦИКЛ ПЕРЕПИСКИ ВО ФРОНТЕ (tmux-web/static/js/bitrix/chat.js + attachments.js + botkb.js, Ф5–Ф6).

СОСТАВ.
- chat.js — лента #b24-log и поле ввода #b24-prompt: открытие диалога, страница истории, догрузка вверх, вставка новых строк, ОТПРАВКА/ПРАВКА/УДАЛЕНИЕ/ЛАЙК/ОТВЕТ (Ф6), счётчик символов, «печатает…», отметка о прочтении, шапка сессии, сброс.
- attachments.js — карточки вложений (заглушка до Ф8) и карточки ATTACH трёх видов блоков.
- botkb.js — inline-клавиатуры сообщений: нормализация нажатия и рендер кнопок.

STICK-TO-BOTTOM — ЗАЩЁЛКА, А НЕ ВЫЧИСЛЕНИЕ. Флаг local.stickBottom переключается ТОЛЬКО в обработчике прокрутки (onScroll → format.js::isAtBottom). Вычислять «пользователь внизу» в момент вставки строки нельзя: высота ленты к тому моменту уже изменилась, и ответ будет про новую ленту, а не про намерение пользователя. Новое сообщение прокручивает ленту вниз ТОЛЬКО при взведённой защёлке. Тот же обработчик, увидев низ ленты, ставит отложенную отметку о прочтении.

ДОГРУЗКА СВЕРХУ КОМПЕНСИРУЕТ ВЫСОТУ. renderOlder запоминает scrollHeight/scrollTop до вставки, вставляет узлы перед первой строкой (после распорки .b24-log-spacer, которая обязана оставаться первым потомком) и добавляет к scrollTop реальный прирост высоты. Без этого читаемая строка уезжает с экрана. Разделитель дня, стоявший над бывшей первой строкой, снимается, если догруженный хвост того же дня.

ПОКОЛЕНИЯ. Каждое открытие диалога поднимает local.generation; ответ на страницу ПРОШЛОГО диалога отбрасывается. Пользователь щёлкает по колонке быстрее, чем отвечает портал.

КЭШ ЛЕНТЫ. b24State.messages: dialog_id → массив MessageDto по возрастанию id (format.js::insertMessage / mergeMessages схлопывают дубли по id). Возврат в диалог рисует кэш мгновенно, свежее догружается следом.

ОПТИМИСТИЧНАЯ ОТПРАВКА (Ф6). Строка появляется в ленте ДО ответа портала, с временным идентификатором TEMP_ID_BASE (9e12) + счётчик: он заведомо больше любого портального (там десятки тысяч) и меньше MAX_SAFE_INTEGER, поэтому строка встаёт в конец и не ломает сортировку по возрастанию. Ответ портала заменяет её ПО ЭТОМУ ЖЕ ВРЕМЕННОМУ id (removeMessage + appendMessage настоящей): сверять тексты нельзя — портал переписывает голые ссылки в [URL] при URL_PREVIEW='Y', и сырые строки не сойдутся никогда. Поле ввода очищается СРАЗУ, не дожидаясь сети: набор следующего сообщения не должен ждать круга до портала.

ОТСУТСТВИЕ АВТОПОВТОРА (Р9) — ГЛАВНОЕ РЕШЕНИЕ МОДУЛЯ. Любая ошибка отправки оставляет строку в ленте с классом .b24-line-failed, сохранённым payload (текст и цитата НЕ теряются) и двумя кнопками: ⟳ повторить и ✕ убрать. Автоматического повтора нет и быть не может: у im.message.add нет дедуп-идентификатора, повтор после обрыва — это второе сообщение у собеседника. Повтор по кнопке — это НОВАЯ отправка с новым временным id: семантики «та же попытка» у портала не существует.

СЧЁТЧИК СИМВОЛОВ (Р12). charCountState() считает длину через Array.from — в CODE POINT'АХ, а не в String.length: эмодзи весит две единицы UTF-16, а лимит портала символьный, и разъезд счётов означал бы отказ сервера там, где фронт разрешил. #b24-charcount появляется с CHAR_WARN_AT (MAX-1000), краснеет за лимитом, кнопка SEND блокируется. Перебор не порождает запроса вовсе — причина показывается в #b24-prompt-note.

РЕЖИМ ВВОДА — ОДИН СЛОТ НА ДВА СОСТОЯНИЯ. local.mode это либо null, либо {kind:'reply'} (цитата, Р10), либо {kind:'edit'} (правка). «Правлю сообщение и одновременно отвечаю на другое» — состояние, которого не существует; разрешив его, пришлось бы решать, что делать с цитатой при отправке правки. Показывает режим #b24-prompt-note (тот же узел показывает и ошибку действия — она относится к вводу, а не к ленте), снимает Esc или крестик. Смена диалога сбрасывает режим и очищает поле: правка ушла бы по идентификатору из другого чата.

КНОПКИ СТРОКИ (buildActions). ♥ лайк и ↩ ответ — у любой строки; ✎ правка и ✕ удаление — только у своей (msg.out), потому что портал разрешает их только автору. Отправляющаяся строка кнопок не имеет вовсе (идентификатора ещё не существует), неотправившаяся получает ⟳/✕. Удаление спрашивает подтверждение (отменить его у портала нечем).

ТРОТТЛИНГ КЛИЕНТСКОЙ СТОРОНЫ. «Печатает…» — не чаще TYPING_INTERVAL_MS (8 с) на диалог, по событию input. Отметка о прочтении — ЗАДНИМ фронтом (READ_DEBOUNCE_MS = 800 мс): пока пользователь листает, запрос не уходит вовсе, а по остановке уезжает САМЫЙ СВЕЖИЙ идентификатор. Сервер держит своё окно передним фронтом (см. bitrix-read-typing) — окна дублируются намеренно: панель бывает открыта в нескольких вкладках, а модули браузер держит в кэше PWA неделями. Колбэк onRead зовётся только на ДОШЕДШЕЙ отметке (resp.sent), и main.js по нему освежает счётчики директорий и бейдж.

СИСТЕМНЫЕ СТРОКИ. msg.system=true рисуется отдельным рядом .b24-line-system: по центру, приглушённым цветом, без ника, времени и подложки.

XSS-ИНВАРИАНТ. innerHTML не используется нигде: только createElement/textContent. Текст сообщения рисуется из СЕГМЕНТОВ (format.js::renderSegments), ссылка не становится <a href>, цвета из карточек и кнопок проходят повторную проверку шестнадцатеричным регэкспом перед записью в style. Цитата в #b24-prompt-note — тоже текстовый узел: в ней лежит чужой текст. Страж: tests/frontend/bitrix_bbcode.test.mjs.

КНОПКИ КЛАВИАТУР. botkb.js::initBotKeyboards принимает {onPutText, onSendText}. PUT подставляет ACTION_VALUE в #b24-input; SEND с Ф6 отправляет текст ТЕМ ЖЕ путём, что Enter (chat.js::submitPrompt) — второй путь отправки означал бы вторую копию проверок лимита и режима ввода. Без onSendText кнопка честно выключается (SEND_UNAVAILABLE). CALL и DIALOG приезжают выключенными с бэкенда (нет scope imbot) — фронт лишь показывает disabled_reason в title.

ГРАФ ИМПОРТОВ (ациклический). chat.js → attachments.js, botkb.js, format.js, api.js, state.js. Обратных импортов нет: attachments и botkb ленту не знают, колонка (dialogs.js) ленту не импортирует — их соединяет точка сборки main.js (onSelect → openDialog, onRead → loadFilters).

СЕТЬ. api.js: getMessages, getMessage, sendMessage, editMessage, deleteMessage, likeMessage, markRead, markUnread, sendTyping, pinDialog, hideDialog. Пути собираются из ШАБЛОНОВ объекта PATHS подстановкой сегмента — так строка во фронте дословно совпадает со строкой таблицы routes/mod.rs, и это сверяет bitrix_contract.test.mjs.

ОТЛАДКА. chat.js::_debugChatState() — {dialogId, loading, hasOlder, stickBottom, generation, messages, oldest, newest, lastText, mode, modeId, sending, pending, failed, chars}; попадает в main.js::_debugState().chat (контракт для e2e). botkb.js::_debugBotKbState() — {canPut, canSend}.

ТЕСТЫ: tmux-web/tests/frontend/bitrix_chat.test.mjs (лента), bitrix_send.test.mjs (цикл переписки: оптимистичная отправка, отсутствие автоповтора, счётчик, правка, удаление, лайк, троттлинг), bitrix_bbcode.test.mjs (безопасность рендера).
