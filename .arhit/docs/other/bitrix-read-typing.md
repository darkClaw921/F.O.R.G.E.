# bitrix-read-typing

ПРОЧТЕНИЕ, РУЧНОЕ «НЕПРОЧИТАНО» И «ПЕЧАТАЕТ…» (Ф6): plugins/bitrix/src/actions.rs + routes/dialogs.rs::{post_read, post_unread, post_typing}.

ПУТИ.
POST /api/bitrix/dialogs/:id/read    — тело {message_id?}, ответ {ok, sent}
POST /api/bitrix/dialogs/:id/unread  — тело {message_id} ОБЯЗАТЕЛЬНО, ответ {ok, sent}
POST /api/bitrix/dialogs/:id/typing  — без тела, ответ {ok, sent}

ЛОВУШКА ПЛАТФОРМЫ: im.dialog.unread БЕЗ MESSAGE_ID НЕ ВЫЗЫВАЕТСЯ ВОВСЕ.
Портал отвечает на такой вызов {error: MESSAGE_ID_ERROR, error_description: 'First unread message id can'\''t be empty'} — то есть запрос из бюджета 2 rps тратится на заведомый отказ. Поэтому обёртка B24Client::dialog_unread принимает message_id ЗНАЧЕНИЕМ (i64), а не Option: вызов без идентификатора невозможен ПО ТИПАМ, а роут отвечает 400 invalid_input раньше сети. Страж: tests/b24_stub.rs::marking_unread_without_a_message_id_never_reaches_the_portal проверяет не только код ответа, но и ПУСТОЙ журнал стенда.

ТРОТТЛИНГ: ПОЧЕМУ НА СЕРВЕРЕ И ПОЧЕМУ ПЕРЕДНИМ ФРОНТОМ.
Оба действия порождаются не кнопкой, а ЖЕСТОМ: прокруткой ленты (событие каждые ~16 мс) и набором текста (событие на клавишу). Бюджет портала — 2 запроса в секунду на ВЕСЬ плагин (leaky bucket на пару портал+IP), и один листающий пользователь способен выесть его целиком, остановив список, историю и отправку. Фронт троттлит тоже, но полагаться только на него нельзя: панель бывает открыта в нескольких вкладках, кэш PWA держит старые модули неделями, а remote-mode обслуживает несколько браузеров сразу. Сервер — единственное общее место.

RateGate — передний фронт: первый вызов в окне уходит немедленно, остальные подавляются и получают 200 {ok:true, sent:false} (это НЕ ошибка). Задний фронт (классический debounce) дал бы более точный MESSAGE_ID ценой отложенной задачи на каждый диалог и задержки перед обнулением счётчика — для прочтения это заметно: пользователь долистал, а бейдж горит. Потеря последнего идентификатора внутри окна безопасна: im.dialog.read без MESSAGE_ID читает диалог ЦЕЛИКОМ, и следующее событие ленты повторит отметку.

ИНТЕРВАЛЫ И ИХ ПРОИСХОЖДЕНИЕ.
READ_DEBOUNCE_MS = 800. Меньше 500 мс окно перестаёт ловить инерционную прокрутку трекпада; больше секунды — пользователь успевает заметить, что счётчик не гаснет.
TYPING_INTERVAL_MS = 8000. Из поведения самого портала: индикатор в его веб-клиенте живёт около десяти секунд, обновлять чаще бессмысленно, реже — значит дать ему погаснуть посреди набора длинного сообщения.
Окно считается ОТДЕЛЬНО НА ДИАЛОГ: чтение одного чата не должно отменять отметку в соседнем при быстром переключении по колонке. Карта ключей имеет потолок MAX_TRACKED_KEYS=512 и выметает записи старше KEY_TTL_MS=60000 — забытая запись стоит одного лишнего запроса, а карта без потолка это утечка на длинном аптайме.

ВРЕМЯ — ПАРАМЕТР (RateGate::allow(key, now_ms, interval_ms)), иначе тест на восьмисекундное окно обязан был бы спать восемь секунд. Часы, отпрыгнувшие назад (NTP, перевод времени), ОТКРЫВАЮТ окно, а не запирают его до конца суток.

СНИМОК СЧЁТЧИКОВ. После успешного read и unread вызывается B24State::invalidate_counters(): пользователь своими руками изменил непрочитанное, и показывать ему старое число ещё полминуты (COUNTERS_TTL_SECS=30) значит выглядеть сломанным. Новых значений взять неоткуда — im.dialog.read отдаёт счётчик ОДНОГО диалога, а бейдж собирается из четырёх независимых чисел портала. Живая проверка: unread(55) в личном диалоге -> counters.dialog=1, директория ~/unread=1; read -> обе нули.

ЧЕГО НЕТ И НЕ БУДЕТ. Входящее «печатает…» платформа вебхуку не присылает (§6 плана): отправка односторонняя, и чужой индикатор в панели не появится никогда — это ожидаемое поведение, а не баг. «Кто прочитал» доступно только по явному запросу (readed_list в im.dialog.get), realtime-уведомлений о прочтении собеседником нет.

unread дополнительно сбрасывает окно прочтения (read_gate.forget): пользователь только что сказал обратное, и следующая отметка обязана уйти немедленно.
