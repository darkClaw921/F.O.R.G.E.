# bitrix-media-routes

plugins/bitrix/src/routes/media.rs — прокси байтов: вложения и аватары (Ф8).

РОУТЫ
  GET /api/bitrix/media/file/:dialog/:mid/:index — байты вложения
  GET /api/bitrix/media/:dialog/:mid/:index      — синоним (форма соседних панелей VK/Telegram)
  GET /api/bitrix/media/avatar/:user_id          — байты аватара (Р6)
Оба пути вложения ведут в один хендлер; коллизии нет — разное число сегментов, а 'avatar' в позиции :dialog не разбирается в идентификатор.

ЕДИНСТВЕННЫЙ ПУТЬ СКАЧИВАНИЯ: страница истории (LAST_ID = mid+1, LIMIT 1 — метода «дай сообщение по id» у портала нет) -> params.FILE_ID[index] -> im.v2.File.download {fileId} -> downloadUrl -> стрим в staging -> commit -> байты. Поля urlDownload/urlShow/viewerAttrs.unifiedLink портал присылает, но без сессионной куки они отдают HTML страницы логина (HTTP 200!) и 403 — их нет ни в FileRaw, ни в MediaDto.

downloadUrl СОДЕРЖИТ КОД ВЕБХУКА ЦЕЛИКОМ и не покидает процесс: не в теле, не в логе (включая trace), не на диске (вместо него отпечаток source_tag), и РЕДИРЕКТ ЗАПРЕЩЁН — заголовка Location в ответах модуля не бывает вовсе. 302 был бы дешевле по трафику и означал бы отдать браузеру ключи от портала.

ЛЕСТНИЦА: авторизация (409) -> объект (404 unknown_dialog / unknown_message) -> параметр (400 invalid_input у индекса) -> кэш -> связь (503) -> портал. Авторизация первой, иначе роут работал бы оракулом валидности идентификаторов. 503 ПОСЛЕ кэша: скачанная картинка обязана открываться и при оборванной сети.

УДАЛЁННОЕ СООБЩЕНИЕ. state.is_deleted(mid) проверяется ДО любого сетевого вызова: портал байты удалённого сообщения не отдаёт, и 404 обязан быть бесплатным. Если признак deleted обнаружен в свежей странице истории — note_deleted запоминает его, и следующий запрос стоит нуля вызовов.

CACHE-CONTROL. CACHE_CONTROL_FILE = 'private, max-age=31536000, immutable' — законен ТОЛЬКО вместе с инвалидацией из events/recent_sync. CACHE_CONTROL_AVATAR = 'private, max-age=3600' БЕЗ immutable: фото меняют когда угодно, событий об этом платформа не присылает.

АВАТАРЫ (get_avatar / download_avatar). Адрес берётся из peers::PeerCache (наполняется бесплатно блоком user событий и строк recent). Кэш-попадание сверяется с отпечатком источника: адрес сменился — запись стирается и байты качаются заново; адрес сейчас неизвестен — отдаётся кэш. Отсутствие фото -> 404 no_media, фронт рисует инициалы. Аватар скачивается напрямую с публичного CDN (у него нет fileId и im.v2.File.download его не знает), но наружу уходят БАЙТЫ, а не ссылка.

ДЕДУП INFLIGHT. fetch_cached + acquire + InflightGuard(Drop) + Slot::{Owner,Waiter}: десять параллельных запросов одного файла = один поход в портал. Гонка «владелец закончил, пока шли к await» закрыта enable() ДО повторной проверки кэша. INFLIGHT_WAIT=300с, MAX_INFLIGHT_ATTEMPTS=2. Guard снимает запись и при панике — иначе любой '?' в середине загрузки подвесил бы ключ навсегда.

СТРИМИНГ. stream_to_file пишет тело кусками (пиковая память не зависит от размера) и шлёт кадры download_progress через progress::DownloadReporter; финальный кадр — ПОСЛЕ fsync. serve_cached отдаёт ReaderStream с буфером STREAM_CHUNK(64 КиБ). Accept-Ranges НЕ анонсируется намеренно: <video> шлёт Range и ждёт 206, а получив 200 с полным телом, ломается.

CONTENT-DISPOSITION. content_disposition(): последний сегмент пути, ASCII-версия чистится до [A-Za-z0-9._-] (заголовочная инъекция невозможна), оригинал уезжает filename*=UTF-8'' в percent-encoding. Запасное имя вложения содержит ИНДЕКС — иначе два файла одного сообщения сохранились бы под одним именем.

StagingGuard(Drop) снимает .tmp при обрыве, отмене запроса и ошибке записи.
