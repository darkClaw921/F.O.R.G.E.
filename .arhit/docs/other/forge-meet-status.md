# forge-meet-status

plugins/meet/src/status.rs — статус-машина встречи, чистый модуль без ввода-вывода и без axum/http.

МАШИНА: queued → launching → joining → [waiting_admit] → recording → leaving → transcoding → transcribing → [summarizing] → ready, плюс failed(reason) и cancelled. Перечисление MeetStatus из 12 вариантов, SummaryStatus (none|pending|ready|failed), MeetCommand (stop|cancel).

ТРИ ПРАВИЛА, РАДИ КОТОРЫХ МОДУЛЬ СУЩЕСТВУЕТ:
1. Статуса detected в базе НЕТ. Строка встречи появляется только по клику пользователя. Иначе таблица росла бы от простого скролла ленты: у каждого сообщения со ссылкой была бы своя запись, и через месяц переписки их набрались бы тысячи при нулевом числе записанных встреч. Отсутствие бейджа в ответе /api/meet/badges и означает «можно записать».
2. stop и cancel — РАЗНЫЕ операции. stop значит «встреча кончилась, обработай»: файлы сохраняются, пайплайн продолжается. cancel значит «прерви и выброси». Из Recording они ведут в Leaving и Cancelled соответственно — это единственная причина, по которой их нельзя было сделать одной кнопкой. Из queued/launching/joining/waiting_admit stop совпадает с cancel по исходу (записывать нечего), из идущей пост-обработки stop это no-op.
3. failed ТОЛЬКО когда нет транскрипта. Переход summarizing → failed ЗАПРЕЩЁН таблицей; провал Claude даёт ready плюс SummaryStatus::Failed через on_summary_finished. Час расшифровки не имеет права пропасть из-за неответившего саммаризатора.

ПУБЛИЧНАЯ ПОВЕРХНОСТЬ: MeetStatus::ALL (12), MeetStatus::ACTIVE (6 статусов, занимающих слот записи), as_str/parse/is_terminal/is_active/is_processing/has_transcript, can_transition(from,to) — ЕДИНСТВЕННАЯ таблица переходов в крейте, on_command(from,cmd), on_summary_finished(ok).

EXHAUSTIVE-ТЕСТ: матрица 12x12 выписана руками, её размер выведен из MeetStatus::ALL.len(), поэтому добавление статуса НЕ КОМПИЛИРУЕТСЯ, пока автор не допишет строку и столбец. Требование «новый статус без строки в тесте валит тест» исполнено на этапе сборки, а не в рантайме.

MeetStatus::ACTIVE построчно сверяется тестом с текстом частичного уникального индекса ux_meetings_active_url в migrations/V001_init.sql: расхождение этих двух списков означало бы, что бот входит в одну встречу дважды.

ПОВТОР ЭТАПА (Ф6, POST /api/meet/meetings/:id/retry?from=) — ЕДИНСТВЕННЫЙ ВЫХОД ИЗ ТЕРМИНАЛЬНОГО СОСТОЯНИЯ, и он объявлен строками таблицы, а не мутацией статуса в обход. Что откуда можно повторить, определяется одним вопросом — что осталось на диске:
  ready → transcoding, transcribing, summarizing (есть и звук, и транскрипт);
  failed → transcoding, transcribing (звук есть, транскрипта нет — иначе статус не был бы failed);
  cancelled → ничего («прерви и выброси» означает, что данных не осталось).
failed → summarizing запрещён не из осторожности: failed по правилу 3 достижим только там, где транскрипта ещё нет, а саммари без транскрипта — это запрос к модели о пустом файле. is_terminal() при этом по-прежнему true для всех трёх: фронт по нему решает, когда прекращать поллинг, и повтор ему не помеха — новый статус приезжает кадром meeting_update.
