# bitrix-progress

plugins/bitrix/src/progress.rs — отчёты о прогрессе передачи файлов (Р8).

Модуль ОБЩИЙ на оба направления: скачивание вложения (Ф8, кадр download_progress) и отправка файла в портал (Ф9, кадр upload_progress). Отдельным модулем — чтобы ограничитель частоты был ОДИН: разъедься он по двум копиям, и прогрессбар вёл бы себя по-разному в двух половинах одной переписки.

ЗАЧЕМ ТРОТТЛИНГ. Тело ответа читается кусками по нескольку килобайт. Без ограничения файл на сотню мегабайт дал бы десятки тысяч кадров в broadcast-канал ёмкостью BROADCAST_CAPACITY(1024): все подписчики немедленно получили бы Lagged и ушли в resync — то есть индикатор прогресса СЛОМАЛ БЫ REALTIME.

Throttle: MIN_INTERVAL=100мс, MIN_DELTA=256 КиБ. Условия работают ПО «ИЛИ»: медленную загрузку двигает время, быструю сдерживают байты. should_emit(current, is_final) МЕНЯЕТ состояние — звать ровно один раз на решение. with_limits() принимает параметры данными, иначе тест обязан был бы спать настоящие 100 мс на каждый ассерт.

ФИНАЛЬНЫЙ КАДР ПРОХОДИТ ВСЕГДА, минуя оба условия. Иначе последний кадр мог бы не дойти, и полоса навсегда осталась бы на 97 % — визуально «загрузка зависла», хотя файл давно на месте. Первый кадр тоже проходит всегда: UI обязан увидеть «загрузка началась» без ожидания.

DownloadReporter { state, key, throttle } — по ОДНОМУ вложению, собственный Throttle на отчётчик (две параллельные загрузки не глушат друг друга). Ключ — CacheKey::id(), то есть <dialog>/<mid>/<index>: без индекса прогресс второго файла сообщения прилетал бы в карточку первого. report(received, total) / finish(...). Неизвестный размер уезжает как total: null, а не ноль — ноль фронт прочитал бы как «файл пустой».

UploadReporter — ДВУХФАЗНЫЙ (Р8): PHASE_CLIENT (браузер -> devforge, проценты точные) и PHASE_PORTAL (devforge -> Битрикс24, indeterminate: true). Процентов на второй фазе не существует вообще: im.v2.File.upload принимает base64 в теле JSON и обратной связи о ходе не даёт (Р7). begin_portal() сбрасывает троттлинг — смена фазы это отдельное событие интерфейса, и подавить его из-за недавнего кадра приёма значило бы оставить полосу в состоянии прошлой фазы.

ProgressReader<R,F> — AsyncRead-обёртка, считающая прочитанные байты, для отправки (Ф9). Прозрачность — контракт: не меняет, не буферизует и не переупорядочивает данные (тест progress_reader_is_byte_transparent). Колбэк получает НАРАСТАЮЩИЙ ИТОГ, а не дельту: у дельты теряется последний кусок, если колбэк вызван не на каждом чтении.

9 юнит-тестов.
