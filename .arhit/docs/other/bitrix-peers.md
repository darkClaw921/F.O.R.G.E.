# bitrix-peers

PeerCache — кэш имён, аватаров и присутствия сотрудников портала (plugins/bitrix/src/peers.rs, Ф4).

ЗАДАЧА. Превратить user_id в отображаемое имя, НЕ ПОТРАТИВ лимит. Бюджет портала — 2 запроса в секунду на пару портал+IP, поэтому резолв по одному идентификатору за вызов означал бы, что чат из тридцати участников открывается пятнадцать секунд.

ДВА ИСТОЧНИКА, ПЕРВЫЙ БЕСПЛАТНЫЙ.
1. absorb_users(&[UserRaw]) — забирает пользователей из УЖЕ полученного ответа: блоки user в строках im.recent.get, массивы users[] в im.dialog.messages.get, data.user в событиях im.v2.Event.get. Сети не касается вовсе; вызывается сразу после каждого такого ответа.
2. resolve_uncached(client, ids) — добор ТОЛЬКО промахов и ПАЧКАМИ: промахи режутся по RESOLVE_BATCH=50 и каждая пачка кладётся отдельной командой в ОДИН batch. Тридцать неизвестных сотрудников — это один HTTP-запрос (тест thirty_unknown_peers_are_resolved_in_a_single_batch на стенде). Отказ отдельной команды ошибкой не считается: имена — украшение, подписью станет идентификатор.

ПОЧЕМУ im.user.list.get, А НЕ user.get. Метод user.get входящему вебхуку НЕДОСТУПЕН (требует scope user, живая проверка — insufficient_scope). Единственный пакетный среди доступных im.* — im.user.list.get, и он несёт ловушку формата: возвращает КАРТУ {'15':{...},'19':{...}}, а не массив, а пустой результат приезжает как [] (сериализация PHP). Тип — PhpMap<UserRaw> (UserMapRaw).

TTL И ПОТОЛОК. PEER_TTL_SECS=600: присутствие протухает, а realtime-присутствия у платформы нет вовсе — обновление приходит только фолбэк-синхронизацией раз в минуту, поэтому кэш обязан сам признавать данные устаревшими. PEER_CACHE_CAPACITY=2000: кэш наполняется ИЗ ОТВЕТОВ ПОРТАЛА, то есть его ростом управляет не наш код; на портале в тысячи сотрудников неделя работы процесса набила бы карту без шанса освободить память. Вытеснение — по возрасту записи, сортировка по паре (возраст, id), чтобы порядок не зависел от seed HashMap. now передаётся параметром (absorb_users_at, get_at, missing_at) — тест TTL не должен спать десять минут.

ТРИ ШАТАЮЩИХСЯ ПОЛЯ. birthday — '' или false; last_activity_date — datetime или false; work_position — null или строка. Плюс last_name приходит null у ботов. Все четыре гасятся в PeerInfo::from_raw. Разбор участников чата без этого падал бы на первом же боте.

НОТАЦИЯ. Методы im.* пишут snake_case, полезная нагрузка событий — camelCase (firstName, lastActivityDate, workPosition, avatarHr). UserRaw несёт serde-alias на каждое расходящееся поле: без них поглощение имён из событий (Ф7) молча давало бы пользователей без имени.

ПРОЧЕЕ. {'id':0} — заглушка блока user у ГРУППОВОГО чата, а не пользователь: в кэш не попадает (иначе системные сообщения подписывались бы 'пользователем 0'). missing() выбрасывает ноль, отрицательные, дубли и известное. Кэш синхронный (std::sync::RwLock, без await): проекция DTO дёргает его на КАЖДОЙ строке списка. clear() зовётся при logout вместе с остальными данными аккаунта. Реализует trait crate::dto::PeerNames (display_name, color, presence, is_bot).

АДРЕСА АВАТАРОВ кэшируются, но наружу не отдаются: в DialogDto уезжает путь прокси (Р6), CDN-адрес портала остаётся внутри процесса.
