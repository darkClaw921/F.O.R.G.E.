# bitrix-send-message

ОТПРАВКА СООБЩЕНИЙ (Ф6): plugins/bitrix/src/routes/dialogs.rs::post_message + api/methods.rs::B24Client::message_add.

ПУТЬ: POST /api/bitrix/dialogs/:id/messages. Тело SendReq {text, reply_to?, reply_author?, reply_text?}. Ответ MessageResp {id, message, echoed}.

ЧТО ПРОИСХОДИТ ПО ШАГАМ.
409 (вебхук не подключён) -> 503 (связи нет) -> 404 (:id не похож на диалог) -> разбор тела -> require_text (Р12) -> compose_reply (Р10) -> im.message.add -> перечитывание строки -> MessageResp.

Р9: ОТПРАВКА НЕ РЕТРАИТСЯ НИКОГДА.
Запрет живёт НЕ в роуте, а в транспорте (api/mod.rs::NO_RETRY_METHODS = [im.message.add, im.v2.file.upload]) и проверяется дважды: на прямой вызов метода и на вложение метода в batch (is_retryable разбирает поле cmd). Причина: у im.message.add нет дедуп-идентификатора — аналога random_id у VK не существует, портал принимает каждый вызов как новое сообщение. Повтор после обрыва TCP даёт собеседнику ВТОРОЕ сообщение, и отличить его от первого нельзя ничем. Поэтому транспортный отказ доезжает до фронта как 503 not_connected, строка остаётся в ленте с пометкой «не отправлено» и кнопкой ⟳, а решение повторить принимает человек. Стражи: api/mod.rs::send_methods_are_never_retryable_in_any_form (юнит), api/methods.rs::the_send_method_is_the_one_the_transport_refuses_to_retry (имя метода не разъехалось со списком), tests/b24_stub.rs::a_failed_send_reaches_the_portal_exactly_once (по проводу: счётчик стенда = 1).

Р12: ЛИМИТ 20 000 СИМВОЛОВ ПРОВЕРЯЕТ ПЛАГИН, А НЕ ПОРТАЛ.
Портал принимает текст любой длины, отвечает УСПЕХОМ и молча режет его на 20 006 символах с хвостом '(...)' — замерено живьём на 25 000. «Успешно отправленный» обрубок хуже честного отказа: отправитель уверен, что собеседник прочитал всё, и узнать обратное ему неоткуда. Поэтому require_text считает длину в CODE POINT'АХ (не в байтах: лимит символьный, байтовый счёт зарезал бы кириллицу вдвое раньше) и отвечает 400 invalid_input С ЧИСЛОМ символов в сообщении — фронту есть что показать. Ни одного сетевого вызова такой запрос не порождает. Тот же лимит действует на правку. Фронт дублирует проверку счётчиком символов (js/bitrix/chat.js::charCountState, тоже Array.from) и блокирует кнопку SEND.

Р10: ОТВЕТ = REPLY_ID + ТЕКСТОВАЯ ЦИТАТА.
Портал ПРИНИМАЕТ REPLY_ID, но при ЧТЕНИИ его не отражает: params приходят пустыми, и reply_to в MessageDto ВСЕГДА null (проверено живьём на сообщении 85). Без текстовой копии ответ в ленте неотличим от новой реплики — ни у нас, ни в веб-мессенджере портала. Поэтому compose_reply() собирает '> автор: цитата\nтекст' и отправляет его ОДНИМ вызовом вместе с REPLY_ID. Цитата однострочна (перевод строки внутри неё сделал бы вторую строку неотличимой от ответа), урезается до QUOTE_MAX_CHARS=200 и НИКОГДА не выталкивает сам ответ за лимит: не хватает места — исчезает цитата, а не текст пользователя. Собирает её СЕРВЕР, а не фронт: формат обязан быть один на все вкладки и все версии модулей, которые браузер держит в кэше PWA неделями.

ПОЧЕМУ СТРОКА ПЕРЕЧИТЫВАЕТСЯ (reread_message).
Локально собранная строка врёт минимум трижды: URL_PREVIEW='Y' (дефолт портала, мы его не переопределяем) переписывает голые ссылки в [URL]…[/URL]; ATTACH нормализуется сервером; date и порядок ставит портал. Поэтому после успешной отправки роут делает ВТОРОЙ запрос — страницу на одну строку (LAST_ID = id+1, LIMIT=1). Отказ перечитывания НЕ делает отправку неуспешной: вернуть 503 после того, как сообщение уже ушло, значит предложить пользователю повторить успешную операцию, то есть создать дубль. В этом случае строка собирается локально (synthesized_message) и приезжает с echoed:false.

ЦЕНА: два запроса к порталу на отправку при бюджете 2 rps.

ФРОНТ (js/bitrix/chat.js). Оптимистичная строка с временным id (TEMP_ID_BASE=9e12 + счётчик — заведомо больше портального, поэтому встаёт в конец ленты и не ломает сортировку по возрастанию). Замена идёт ПО ЭТОМУ ЖЕ id, а не по совпадению текста: сырые строки не сойдутся никогда из-за URL_PREVIEW, а после bbcode::to_plain сравнение всё равно было бы хрупким. Ошибка -> строка остаётся с payload (текст не теряется), кнопки ⟳ повторить / ✕ убрать. Повтор — это НОВАЯ отправка с новым временным id: семантики «та же попытка» у портала не существует.
