# Portal

Экстрактор портала для HTTP-роутов плагина Bitrix24 (plugins/bitrix/src/routes/portal.rs).

ЧТО ЭТО
Кортежная структура Portal(pub Arc<B24State>) с impl FromRequestParts<Arc<B24Registry>>. Заменила State<Arc<B24State>> во ВСЕХ хендлерах плагина (36 точек в routes/{mod,login,dialogs,tasks,media,upload,analysis,voice}.rs и ws/mod.rs). Разворачивается кортежным паттерном: 'Portal(state): Portal'.

ЗАЧЕМ
До мультипортальности портал выбирался в момент сборки роутера (with_state). Роутер собирается один раз при старте, а состав реестра меняется на живом процессе (B24Registry::add / remove, Ф4) — привязка к конкретному Arc пережила бы отключение своего портала. Поэтому состоянием роутера стал Arc<B24Registry>, а портал выбирает каждый запрос.

ПОРЯДОК РЕЗОЛВА
1. Заголовок X-Forge-Portal (константа PORTAL_HEADER = "x-forge-portal"). Дословно совпадает с константой во фронте js/bitrix/api.js.
2. Query-параметр ?portal= (PORTAL_QUERY) — фолбэк для адресов без заголовков: /ws/bitrix (браузерный WebSocket заголовков не умеет) и прямые ссылки на медиа. Значение percent-декодируется (routes::upload::percent_decode), разбирается вручную через routes::dialogs::query_str — не через Query<T>, чтобы не появилось ветки в 400.
3. Ни того, ни другого — ПЕРВЫЙ СЛОТ реестра (registry.list()[0], а не connected()[0]).

Заголовок приоритетнее query и его наличие закрывает вопрос: в query экстрактор проваливается только когда заголовка нет вовсе.

САНИТИЗАЦИЯ
Входное значение проходит config::normalize_portal_id перед сравнением: id уезжает в лог, в имя каталога кэша (Ф6) и в ключ пер-портальных настроек (Ф7). Идентификаторы в реестре уже нормализованы, поэтому сравнение нормализованного с нормализованным — единственное корректное. X-Forge-Portal: ALPHA резолвится в портал alpha.

ОШИБКИ (существующий конверт routes/error.rs)
- ApiError::unknown_portal — 404 code=unknown_portal: портал назван, но его нет в реестре. Штатная ситуация (портал отключили в соседнем окне). 404, а не 400 — иначе роут стал бы оракулом состава реестра. Присланная строка в ответ НЕ попадает.
- ApiError::no_portal — 503 code=no_portal: в реестре нет ни одного слота. Инвариант реестра это запрещает, но паника в FromRequestParts уронила бы обработку запроса.

ТРИ РЕШЕНИЯ, КОТОРЫЕ ЛЕГКО СЛУЧАЙНО ОТМЕНИТЬ
1. Фолбэк отдаёт ПЕРВЫЙ СЛОТ, а не первый подключённый портал. На свежей установке единственный слот пуст, и именно он показывает экран подключения. Фильтр по вебхуку сломал бы подключение на свежей установке.
2. Адресный запрос по неизвестному id — 404, а не фолбэк. Молчаливый сполз показал бы чужую переписку под своим именем вкладки.
3. Экстрактор НЕ отдаёт 400 никогда. Лестница data-роутов начинается с 409, и мусорный ввод обязан доезжать до неё. Пустой заголовок = «портал не назван» (фолбэк), непустой мусор = «назван несуществующий» (404).

API
- Portal::state() -> &Arc<B24State>
- Portal::resolve(registry: &B24Registry, named: Option<&str>) -> Result<Portal, ApiError> — сам резолв без HTTP; вынесен ради табличных тестов и будущего агрегирующего WS (Ф5).

ТЕСТЫ
10 юнит-тестов в самом модуле + tests/portal_isolation.rs (9 HTTP-тестов изоляции двух порталов с совпадающими идентификаторами).
