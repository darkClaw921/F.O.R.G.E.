# forge-meet-db

plugins/meet/src/db/ — SQLite-хранилище плагина встреч: mod.rs (соединение и миграции) плюс repo/{mod,meetings,sources,participants,spans,segments,events}.rs.

ПОЧЕМУ SQLITE, А НЕ JSON-СТОР ПО ОБРАЗЦУ PromptStore: час встречи это 2000-4000 сегментов. Каждое сохранение переписывало бы файл целиком, а краш посреди записи оставлял бы «последнюю удачную полную версию», то есть терял бы кусок встречи.

СХЕМА (migrations/V001_init.sql, embedded через rust-embed): meetings (статус, url_key, времена, пути на диске, СВОЙ summary_status, track_mode, capture_path), meeting_sources, meeting_participants, meeting_speaker_spans, meeting_segments, meeting_events.

meeting_sources объявлена WITHOUT ROWID: первичный ключ (plugin, chat_id, message_id) становится САМОЙ таблицей, поэтому батч ленты (равенство по плагину и чату плюс диапазон по id) это один скан по префиксу ключа без похода в дополнительную структуру за строкой. Отдельной таблицей — потому что одну ссылку кидают в двух чатах и в двух мессенджерах, и обе кнопки обязаны показывать ОДНУ запись. Инвариант id проекта соблюдён: chat_id строка, message_id число.

ЧАСТИЧНЫЙ УНИКАЛЬНЫЙ ИНДЕКС ux_meetings_active_url ON meetings(url_key) WHERE status IN (шесть активных) держит «одна активная запись на комнату» СТРУКТУРНО. Мьютекс в памяти защищает только один процесс и только пока тот жив; после перезапуска devforge посреди записи он ничего не помнит. Список статусов в индексе сверяется тестом с MeetStatus::ACTIVE.

repo::meetings::set_status — ЕДИНСТВЕННАЯ ТОЧКА МУТАЦИИ СТАТУСА. Одной функцией: строка в базе И строка в meeting_events в ОДНОЙ транзакции (поэтому «статус сменился, а журнала нет» невозможно), затем обновление тёплого индекса бейджей по всем источникам встречи и broadcast кадра meeting_update. Побочные эффекты по времени там же: вход в recording ставит started_at (фронт считает таймер от него, а не инкрементом — инкремент обнуляется при перезагрузке вкладки), выход из записи ставит ended_at и грубую duration_ms. Разъезд базы и индекса возможен ровно в одном случае — если кто-то мутирует статус мимо этой функции, поэтому на отсутствие таких мест есть ГРЕПАЮЩИЙ тест no_status_update_bypasses_set_status, обходящий все .rs крейта.

repo::meetings::create_or_attach даёт дедуп: активная запись на ту же комнату возвращается с attached=true, а не создаётся второй. Это НЕ ошибка и НЕ 409.
repo::meetings::finish_summary реализует правило «провал саммари не роняет встречу» отдельной функцией, а не двумя вызовами на месте: соблазн написать set_status(Failed) при неуспехе Claude слишком велик, а цена ошибки — час расшифровки.

meeting_speaker_spans принимает ДВА независимых источника интервалов речи: vad (пер-трековый детектор, режим PerParticipant) и dom (индикатор активного спикера самой встречи). Для Телемоста dom — ЕДИНСТВЕННЫЙ путь: проба Ф0 показала два аудиотрека при трёх удалённых участниках, и track.muted не менялся при смене говорящего. Поэтому attribute_segments (Ф5) обязана брать интервалы отсюда, а не из пер-трекового VAD напрямую.

Db::migrate идемпотентна: каждая миграция в своей транзакции, отметка в schema_migrations по имени файла. При открытии выставляются WAL (читатели не блокируются писателем идущей встречи) и foreign_keys=ON (без него ON DELETE CASCADE был бы украшением, и удаление встречи оставляло бы сироты в пяти таблицах).
