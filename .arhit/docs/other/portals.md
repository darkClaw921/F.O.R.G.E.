# portals

Модуль plugins/bitrix/src/routes/portals.rs — CRUD состава порталов поверх B24Registry (мультипортальность, Ф4).

РОУТЫ
- GET /api/bitrix/portals — список вкладок: {portals: [{id, title, connected, login, unread}]} в порядке реестра. 200 всегда.
- POST /api/bitrix/portals — подключить портал по вебхуку. Тело {webhook, title?}. Ответ — одна вкладка PortalDto.
- PATCH /api/bitrix/portals/:pid — {title?, order?}. title меняет имя вкладки (пустая строка возвращает автоподпись), order — ПОЛНЫЙ список id в новом порядке. Ответ — весь список.
- DELETE /api/bitrix/portals/:pid?purge_cache=1 — отвязать портал. Ответ — весь список.

ЧЕМ ОТЛИЧАЕТСЯ ОТ routes/portal.rs
Имена различаются одной буквой: portal — экстрактор Portal (реестр ЧИТАЕТ, выбирает состояние по X-Forge-Portal), portals — роуты, которые реестр МЕНЯЮТ. Хендлеры здесь берут State<Arc<B24Registry>>, а не Portal: DELETE через экстрактор означал бы «удали ту вкладку, что сейчас открыта».

СЕКРЕТ В ОТВЕТАХ
Вебхук проходит через фронт ровно один раз — телом POST — и не задерживается ни в query, ни в логах, ни в ответе. WebhookUrl без Serialize; PortalDto собирается вручную, поэтому есть отдельный тест the_portal_list_never_leaks_the_webhook. ХОСТ портала тоже НЕ отдаётся: GET /api/bitrix/status намеренно не отдаёт его ни в одном состоянии (замороженный тест status_never_leaks_the_webhook_in_any_state), и два соседних роута с противоположными правилами про одно поле разъехались бы. Узнаваемое имя несёт id (test-work-2.bitrix24.ru => test-work-2); пустой title фронт показывает как id.

ФИЛЬТР ПУСТЫХ СЛОТОВ
Реестр никогда не пуст: на свежей установке и после отвязки последнего портала в нём стоит слот с пустым вебхуком и пустым id. GET /portals фильтрует такие слоты по portal_id — НЕ по B24Registry::connected(), которая смотрит на конфиговый вебхук: у только что занятого пустого слота он ещё пуст, и первый портал свежей установки не появлялся бы во вкладках до перезапуска devforge.

unread берётся ИЗ СНИМКА счётчиков и никогда не ходит в сеть: список перерисовывается на каждое переключение вкладки, а сетевой вариант стоил бы N запросов из бюджета 2 rps каждого портала на один клик и сам загонял бы порталы в throttled.

АВТОПОВТОРОВ НЕТ. Портал душит интенсивность состоянием throttled (Р16), автоповтор его только продлевает. Повтор всегда инициирует пользователь.

purge_requested принимает ровно две записи истины (1 и true, как ?force= в routes/voice) — у необратимого действия значение по умолчанию обязано быть безопасным. До Ф6 все порталы делят один cache_dir, и B24Registry::remove сама отказывается сносить общий каталог.

Тесты: plugins/bitrix/tests/portals_crud.rs (23 HTTP-теста на герметичном стенде) + юниты в самом модуле.
