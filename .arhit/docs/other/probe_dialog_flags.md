# probe_dialog_flags

Ленивый резолв флагов уведомлений диалога в updates-воркере Telegram (plugins/telegram/src/updates.rs).

ЗАЧЕМ. Кэш флагов (TelegramState::notify_overrides) засевается только листингами диалогов — то есть верхушкой списка (DEFAULT_DIALOGS = 100). Чат, заглушённый ТОЧЕЧНО и не попавший ни в одну загруженную страницу, кэшу неизвестен, а resolve_dialog_flags на промахе берёт дефолт КАТЕГОРИИ — обычно false. Кадр new_message уходил во фронт с muted:false, и dialogRings разрешал тост. Это и была жалоба «уведомления приходят от чатов в муте».

ЧТО ДЕЛАЕТ. На промахе кэша делает один messages.getPeerDialogs по peer'у сообщения и запоминает ВСЁ, что узнал: muted (с наследованием), archived (folder_id) и настоящую категорию (dialog_kinds). Следующее сообщение из этого чата разрешается по кэшу — RPC больше не нужен.

ОГРАНИЧЕНИЯ (все обязательны, стоит в hot-path'е единственного потока апдейтов аккаунта):
- попытка столбится через TelegramState::claim_flags_probe ДО запроса — не более одного RPC на диалог за сессию, даже если Telegram отказывает;
- запрос под DIALOG_FLAGS_TIMEOUT = 3с — зависший RPC не имеет права задержать typing, прочтения и соседние сообщения;
- peer берётся ТОЛЬКО из кэша peers (peers::cached_peer): резолв по сети здесь означал бы скан диалогов, то есть десятки RPC;
- не запускается, пока не прочитаны глобальные дефолты (TelegramState::notify_defaults_known): значение, посчитанное от заглушки, попав в кэш, пережило бы её и звенело бы всю сессию.

Чистая часть — peer_dialogs_flags: разбирает ответ через dto::RawPeerIndex + dto::from_raw_dialog_with_defaults и возвращает (DialogFlags, Option<kind>); None означает, что такого диалога у аккаунта нет.
