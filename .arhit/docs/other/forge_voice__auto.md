# forge_voice::auto

Модуль plugins/voice/src/auto.rs — общее решение 'разбирать ли это входящее голосовое само' плюс реестр уже взятых ключей. Ф4 фичи голосовых сообщений.

ЗАЧЕМ ОБЩИЙ. Воркеры авторазбора у VK, Telegram и Bitrix разные (у каждого свой поток событий), а вопрос один и тот же, и ответы обязаны совпадать.

API:
- Skip { Disabled, Outgoing, NotVoice(String), Hidden, TooLong{secs,limit} } с методом code() — причина пропуска попадает в журнал: 'почему у меня ничего не расшифровалось' первый вопрос о фоновой фиче.
- Candidate { kind, outgoing, duration_secs, peer, peer_kind } — что плагин знает о сообщении.
- decide(prefs, cand, max_duration_secs) -> Result<(), Skip>. ПОРЯДОК СТУПЕНЕЙ — гейт фазы: тумблер -> своё исходящее -> не голосовое -> беседа скрыта -> слишком длинное. Тумблер первым и стоит разбора булева поля; все дорогие действия (докачка, движок) физически стоят ПОСЛЕ этой функции.
- SeenKeys (ограниченный FIFO, DEFAULT_SEEN_CAPACITY = 512) с claim()/forget()/len(). Проверка и занятие ОДНОЙ операцией под замком.

ЗАЧЕМ SeenKeys, ЕСЛИ ЕСТЬ ДЕДУП В HUB. Реестр не пускает второй прогон, пока идёт первый, а стор не даёт пересчитывать готовое. Между ними дыра: прогон, уже ЗАКОНЧИВШИЙСЯ ОТКАЗОМ. Повторная доставка события (переподключение лонгпола, догон истории) запускала бы его по кругу — с оплатой каждого повтора в облаке. Кнопка 'расшифровать' этот реестр не смотрит: человек, нажавший её после отказа, просит повторить осознанно.

Здесь НЕ проверяется: наличие ffmpeg/весов/ключа (это gate::check, зовётся позже — иначе диск читался бы на каждое текстовое сообщение) и потолок параллелизма (он в hub::VoiceHub, берётся под замком вместе со слотом; авторазбор ходит через ТОТ ЖЕ реестр, что и кнопка).
