# forge-cdp::launch

`plugins/forge-cdp/src/launch.rs` — запуск собственного экземпляра Chrome и получение адреса порта отладки.

## Почему «только свой Chrome» — ограничение, а не выбор

С версии 136 Chrome ИГНОРИРУЕТ `--remote-debugging-port`, если не задан нестандартный `--user-data-dir`. Подключиться к рабочему браузеру пользователя невозможно в принципе (на машине разработки Chrome 151). Отсюда весь модуль: свой профиль, свой порт, свой файл тишины, своя группа процессов.

## Порт читаем из файла, а не угадываем

`--remote-debugging-port=0` заставляет Chrome взять свободный порт и записать его в `<user_data_dir>/DevToolsActivePort` (первая строка — порт, вторая — путь `/devtools/browser/<uuid>`). Выбирать порт самим — гонка: между «нашли свободный» и «Chrome его занял» его может занять кто угодно.

`read_ws_url` возвращает `None` и при отсутствии файла, и при НЕДОПИСАННОМ файле (есть порт, нет пути): Chrome дописывает вторую строку не атомарно. Ожидание (`wait_for_ws_url`) параллельно следит за процессом через `try_wait`: если Chrome успел умереть, ждать файл целую минуту бессмысленно, и в ошибку кладётся хвост `chrome.log` (stdout+stderr Chrome перенаправлены в `<meeting_dir>/chrome.log`).

## Файл тишины — защита от тихой порчи ЖИВОЙ встречи

`--use-fake-device-for-media-stream` БЕЗ `--use-file-for-fake-audio-capture` даёт микрофон, генерирующий ПЕРИОДИЧЕСКИЙ БИП-ТОН: бот пикает живым участникам. Поэтому файл подкладывается всегда, а `ensure_silence_wav(path, ffmpeg)` идемпотентна (существующий валидный WAV не переписывается — он общий для всех встреч и весит 11,5 МБ) и имеет ДВА пути: `ffmpeg -f lavfi -i anullsrc=r=48000:cl=stereo -t 60 -c:a pcm_s16le` (как в плане, без суффикса `%noloop` — файл должен зациклиться) и собственный писатель WAV (заголовок + нули). Второй обязателен: «нет ffmpeg» не имеет права превращаться в «бот пикает».

Измеренная разница путей: собственный писатель даёт РОВНО 11 520 044 байта (44 + 60 с * 48000 * 2 канала * 2 байта), ffmpeg — 11 520 078, потому что дописывает чанк LIST/INFO со своей подписью. Тесты сверяют точный размер только для своего писателя, живой тест — диапазон.

## Флаги и почему они такие

`--user-data-dir` (обязателен с 136+), `--remote-debugging-port=0`, `--use-fake-ui-for-media-stream` (авто-грант mic/cam без диалога, нажать который некому), `--use-fake-device-for-media-stream`, `--use-file-for-fake-audio-capture`, `--autoplay-policy=no-user-gesture-required` (AudioContext стартует running, а не suspended), три анти-троттлинговых (`--disable-background-timer-throttling`, `--disable-backgrounding-occluded-windows`, `--disable-renderer-backgrounding` — окно за экраном формально не видно, а таймеры захвата обязаны идти), `--disable-blink-features=AutomationControlled`, `--no-first-run` и `--no-default-browser-check` (свежий профиль иначе показывает мастер первого запуска, который перехватывает фокус), `--window-size`.

`--no-startup-window` (поле `no_startup_window`, дефолт включён) — выполнение требования «браузер не отбирает фокус у пользователя». Это ОТДЕЛЬНАЯ проблема от видимости окна: на macOS активируется приложение, а не окно, и уехавшее за экран окно фокус всё равно утащило бы. ИЗМЕРЕНО: прямой запуск с окном переводит фронт на com.google.Chrome в первую же секунду, тот же запуск с `--no-startup-window` фронт не меняет вовсе; `DevToolsActivePort` при этом пишется как обычно. Позиционный URL вместе с этим флагом НЕ передаётся — он и есть просьба открыть окно. Подробности и таблица измерений — страница forge-meet-phase1-focus.

`--mute-audio` вынесен в ПОЛЕ `mute_audio` (дефолт true): гейт фазы 0 оставил открытым вопрос, не глушит ли флаг данные для WebAudio и MediaRecorder, и сделал его приёмочным пунктом фазы 3. Переключатель нужен, чтобы измерение не требовало правки кода.

`FORBIDDEN_ARGS` = `--no-sandbox`, `--disable-web-security`, `--disable-site-isolation-trials`. Фильтр применяется и к `extra_args`, поэтому запрет СТРУКТУРНЫЙ. Обоснование: первый снимает песочницу у браузера, ходящего на произвольные сайты встреч, второй и третий ломают изоляцию источников — а мы, наоборот, рассчитываем на OOPIF и автоаттач к ним.

## Режим окна

`WindowMode::Offscreen` (дефолт) — headful, окно уводится `--window-position` уже при старте. `Visible` — для ассистированного входа. `Headless` (`--headless=new`) НЕ дефолт: UA содержит `HeadlessChrome` (повод для антибот-отказа), поведение WebRTC-аудио на macOS в этом режиме не проверено, и главное — headless-окно нельзя показать человеку, а показ окна это несущая функция ассистированного входа.

## Группа процессов

`setsid(2)` в `pre_exec` (тот же приём, что в `tmux-web/src/daemon.rs`). Без своей группы убить Chrome целиком нельзя: рендереры, GPU-процесс и утилиты — отдельные процессы, и `kill` по лидеру оставит их держать микрофон и профиль. `kill_on_drop` НЕ ставится: он бьёт только лидера и только при выполнении деструкторов.

`ChromeProcess::terminate(grace)` использует `terminate_child_group`, который отличается от `orphans::terminate_group` одной важной деталью: мёртвый СОБСТВЕННЫЙ потомок остаётся зомби, пока его не забрал `waitpid`, а зомби для `kill(pid,0)` неотличим от живого — поэтому здесь проверка идёт через `child.try_wait()`, иначе «отсрочка» всегда доходила бы до SIGKILL. `Drop for ChromeProcess` шлёт SIGTERM группе как последняя сетка.

## Живая проверка (tests/live_chrome.rs, гейт FORGE_CDP_LIVE=1)

Подтверждено на Chrome 151: ws-адрес читается из DevToolsActivePort; `chrome.pid` содержит pid и профиль; `getpgid(pid) == pid` и не равен нашему pgid; argv содержит `--user-data-dir` (то, на что опирается двойная проверка подметальщика); после `terminate` не остаётся ни одного процесса группы; фронтовое приложение пользователя не меняется ни при запуске, ни при создании вкладки.
