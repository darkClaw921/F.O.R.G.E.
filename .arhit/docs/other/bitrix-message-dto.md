# bitrix-message-dto

МОДЕЛЬ СООБЩЕНИЯ ЛЕНТЫ (plugins/bitrix/src/dto.rs::MessageDto, Ф5).

ЧТО ЭТО. Проводная форма одного сообщения диалога Битрикс24: то, что отдаёт GET /api/bitrix/dialogs/:id/messages и что летит WS-кадром message_new (ws/protocol.rs::MessagePayload — АЛИАС на этот же тип, чтобы realtime-строка и строка из истории не разъехались формой).

ПОЛЯ.
- id: i64. Идентификаторы у портала растут ШАГОМ 2 (77, 79, 81) — арифметике id+1 доверять нельзя нигде, кроме одного места: роут /messages/:mid просит LAST_ID = mid+1 именно потому, что между mid и mid+1 не может оказаться чужого сообщения.
- dialog_id: String. Приходит АРГУМЕНТОМ проекции, а не из самого сообщения: в сообщении лежит числовой chat_id, а у личного диалога DIALOG_ID это user_id собеседника (другое число). Вернуть фронту не тот идентификатор, которым он спрашивал, значит промахнуться ключом Map на каждой странице.
- out: author_id == self_id и author_id != 0.
- date: Option<String> — ATOM, как отдал портал.
- sender: Option<SenderDto> {id, name, color, bot}. None у системных сообщений: у них автора нет. Имя приходит ТОЛЬКО из peers (PeerNames), потому что users[] в ответе im.dialog.messages.get живьём чаще всего ПУСТ.
- system: author_id == 0 ЛИБО params.SYSTEM == 'Y'. Оба признака нужны: im.message.add SYSTEM=Y сохраняет сообщение с author_id 0, но часть системных строк портал помечает только флагом. Фронт рисует их отдельным рядом без ника, времени и подложки.
- text: bbcode::to_plain — для превью, поиска и копирования.
- segments: Vec<bbcode::Segment> — единственная форма, из которой фронт собирает разметку УЗЛАМИ (innerHTML в панели запрещён).
- media: Vec<attach::MediaDto> — params.FILE_ID x корневой files[] (см. bitrix-attach).
- cards: Vec<attach::CardDto> — params.ATTACH[].BLOCKS.
- reply_markup: Option<attach::ReplyMarkupDto> — params.KEYBOARD.
- edited: params.IS_EDITED == 'Y'. Появляется с задержкой до recent_sync_secs: событий правки портал не присылает (ONIMV2MESSAGEUPDATE документирован, но живьём не приходит).
- likes: Vec<String> — params.LIKE. ЛОВУШКА: приходит и строками ['1'], и числами [1] (снято живьём после im.message.like). Разбираются обе формы, наружу уходит строковая. Лайк — единственная доступная вебхуку реакция.
- action: Option<String> — params.CODE[0]: CHAT_JOIN, CHAT_LEAVE и т.п.
- unread: bool.
- reply_to: ВСЕГДА None (Р10). REPLY_ID отправляется, но при ЧТЕНИИ портал его не отражает — цитата дублируется текстом (Ф6).
- fwd: ВСЕГДА None. Пересылки сообщений вебхуку недоступны (§6).

ПОРЯДОК И ПАГИНАЦИЯ (главное отличие от VK/Telegram).
Порядок ответа портала ЗАВИСИТ ОТ НАПРАВЛЕНИЯ запроса: базовый вызов и LAST_ID (листаем вверх) отдают по УБЫВАНИЮ id, FIRST_ID (догружаем низ) — по ВОЗРАСТАНИЮ. На выход всегда нормализуется по ВОЗРАСТАНИЮ (dto::sort_messages_ascending, там же дедуп по id: страницы приходят с пересечением по границе). Фронт про два порядка не знает вовсе.
LIMIT клампится потолком платформы 50 (api::methods::MESSAGES_MAX_LIMIT) МОЛЧА: страницу просит фронт, и 400 на ровном месте означал бы пустую ленту.

ЛОВУШКА URL_PREVIEW. im.message.add по умолчанию (URL_PREVIEW='Y') оборачивает голые ссылки в [URL]...[/URL], поэтому отправленный текст и прочитанный обратно не совпадают байт в байт. Сравнивать их (дедуп оптимистичной строки в Ф6) можно только после bbcode::to_plain.

СВЯЗИ. Проекция message_from_raw(raw, dialog_id, self_id, files, peers) — ЧИСТАЯ: ни сети, ни кэша, ни времени; тестируется на живых фикстурах tests/fixtures/msgs_chat27.json и msgs_chat3.json. Источник сырья: api/schema.rs::MessageRaw и MessagesRaw. Потребители: routes/dialogs.rs::get_messages / get_message, ws/protocol.rs, tmux-web/static/js/bitrix/chat.js.

ЧТО ДОБАВИЛА Ф6 (цикл переписки).
- edited становится true после im.message.update — метку IS_EDITED ставит САМ портал, мы её не отправляем. Своя правка видна сразу (строка перечитывается тем же запросом), ЧУЖАЯ — с задержкой до минуты: событие ONIMV2MESSAGEUPDATE документировано, но живьём не приходит, и ловит правки только фолбэк-воркер (Ф7).
- likes меняется через im.message.like (единственная реакция вебхука). Ответ портала всегда true и о состоянии не говорит ничего — новый состав берётся ТОЛЬКО из перечитанной строки.
- reply_to остаётся ВСЕГДА null и после Ф6: REPLY_ID отправляется, но при чтении портал его не отражает (Р10). Ответ виден как текстовая цитата в самом text/segments — так и задумано.
- УДАЛЁННОЕ сообщение портал не убирает из истории: text становится «Это сообщение было удалено», а в params появляется IS_DELETED="Y". Поля is_deleted в DTO НЕТ намеренно — панель не рисует такие строки иначе. Если Ф7 захочет отличать их визуально (событие ONIMV2MESSAGEDELETE), поле придётся добавить и в DTO, и во фронт.
- Оптимистичная строка фронта (js/bitrix/chat.js) добавляет к форме DTO четыре СВОИХ поля: pending, failed, error, payload. Сервер их не отдаёт и не принимает; живут они ровно до замены строки настоящей.
