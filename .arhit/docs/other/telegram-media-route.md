# telegram-media-route

plugins/telegram/src/routes/media.rs (крейт forge-telegram, Фаза 4) — единственный роут отдачи принятых медиа: GET /api/telegram/media/:dialog_id/:message_id?kind=thumb|full.

ПОРЯДОК ПРОВЕРОК (часть контракта): форма параметров через CacheKey::parse (400 invalid_input) -> require_authorized (409 not_authorized) -> кэш (media_cache::get) -> require_client (503 not_connected) -> Telegram. Закэшированное медиа отдаётся БЕЗ живого MTProto-подключения: реконнект не должен гасить уже принятые картинки. Мусорный kind — ошибка клиента в любом состоянии логина, поэтому валидация раньше авторизации.

serve_cached(hit, key, touch_mtime): tokio_util ReaderStream(STREAM_CHUNK=64 КиБ) + Body::from_stream (RSS не зависит от размера файла), Content-Type из меты (fallback application/octet-stream), Content-Length, Cache-Control: private, max-age=31536000, immutable (законно только потому, что updates.rs инвалидирует кэш при edit/delete), Content-Disposition inline. Accept-Ranges НЕ анонсируется: без 206 браузер, увидев его, ломает <video>; фронт всё равно грузит через fetch+blob (у <img>/<video> нет Bearer). На попадании фоновая задача дёргает media_cache::touch (LRU).

content_disposition(file_name, key, mime): имя приходит из Telegram, то есть от чужого аккаунта -> берётся последний сегмент пути (rsplit по / и \), ASCII-версия чистится до [A-Za-z0-9._-] (ни кавычки, ни ';', ни CRLF в заголовке, ни '..'), оригинал добавляется как filename*=UTF-8'' в percent-encoding (кириллица не теряется). Пустое имя -> telegram_<mid>_<kind>.<ext>, расширение по mime_guess::get_mime_extensions_str, иначе .bin.

INFLIGHT-ДЕДУП: fetch_cached(state, key, download) — download зовётся ТОЛЬКО владельцем ключа state.media_inflight; остальные ждут Notify (INFLIGHT_WAIT=5 мин) и перечитывают кэш. Гонка 'владелец закончил, пока мы шли к await' закрыта тем же приёмом, что в updates::wait_authorized: notified().enable() ДО повторной проверки кэша (notify_waiters не оставляет permit). MAX_INFLIGHT_ATTEMPTS=2, после чего запрос качает сам — упавший владелец не должен вешать остальных до таймаута. InflightGuard снимает запись и при штатном выходе (release), и при панике/отмене (Drop -> tokio::spawn).

ЗАГРУЗКА: download_media(state, client, key) — resolve_peer -> ОДИН get_messages_by_id -> msg.media() -> dto::media_dto. kind=thumb: media_thumbs (Photo/Document/Sticker) -> pick_thumb_index (ЧИСТАЯ функция над ThumbCandidate{bytes,downloadable,embedded}, потому что конструкторы PhotoSize приватны и в тесте их не собрать): самое МАЛЕНЬКОЕ из скачиваемых (превью в ленте 184px, тянуть 'y'-вариант — платить мегабайтами), при их отсутствии — самое КРУПНОЕ из встроенных (Cached/Stripped приходят бесплатно, крупнее = менее размыто); нет ни одного -> 404 no_media, фронт рисует generic-иконку. kind=full: iter_download(&media) чанками в staging-файл. stream_to_file: DownloadReporter на каждый чанк + finish ПОСЛЕ fsync (событие 'готово' не должно опережать данные), final_total(total, received) подставляет фактический размер, если Telegram не сообщил его заранее (иначе прогрессбар навсегда индетерминирован). Пустой ответ Telegram -> 404 no_media. Затем media_cache::commit (rename) и перечитывание записи, чтобы отдавать её ТЕМ ЖЕ serve_cached.

МУСОР: StagingGuard(Drop) сносит .tmp при любом выходе — обрыв, FLOOD_WAIT посередине, отменённый клиентом запрос. Ошибки RPC классифицирует общий dialogs::map_invocation (420->429+retry_after_secs, 401->409, *_ID_INVALID->404, 400->400, прочее->503).

СВЯЗИ: media_cache.rs, progress.rs (DownloadReporter), peers.rs (resolve_peer), dto.rs (media_dto), routes/dialogs.rs (require_authorized/require_client/map_invocation), routes/mod.rs (build_router merge). 23 unit-теста: заголовки и тело попадания, стриминг 4 МиБ чанками, независимость kind, touch mtime, 7 битых параметров, 409/503, 5 параллельных запросов = 1 загрузка, снятие inflight при ошибке и при панике, отмена запроса не оставляет .tmp, throttle прогресса (2048 чанков -> <64 кадров) и полный финал. Хост-контракт продублирован в tmux-web/tests/telegram_smoke.rs.
