# bitrix-upload-routes

plugins/bitrix/src/routes/upload.rs — приём файла и заливка его в портал (Ф9).

РОУТ
  POST /api/bitrix/upload — raw-тело (сами байты файла) + заголовок
  X-Forge-File-Name (percent-encoded имя). Ответ: {upload_id, file_name, size, mime}.

Второй половины у роутера НЕТ намеренно: файл уезжает в портал внутри
POST /api/bitrix/dialogs/:id/messages (routes::dialogs::post_message) — тем же
роутом, что и текст. Причина в методе платформы: im.v2.File.upload это не
«залить файл», а «залить файл И отправить сообщение» одним вызовом. Отдельный
роут /files означал бы второй путь отправки со своей копией дедупа (Р19),
рассылки кадра message_new и перечитывания строки — и первая же правка одного
из них разъехалась бы со вторым.

ПОЧЕМУ ПРИЁМ И ОТПРАВКА — ДВА ЗАПРОСА
Пользователь вправе выбрать файл и передумать, куда его слать (или не слать
вовсе). POST /api/bitrix/upload кладёт байты на НАШ диск и не делает ни одного
обращения к порталу; upload_id — идентификатор НАШЕГО полуфабриката, а не
адрес чего-либо в Bitrix24.

ПОРЯДОК ПРОВЕРОК (нарушен быть не может)
  1. авторизация            -> 409 not_authorized   (тело НЕ читается)
  2. Content-Length есть?   -> 411 length_required  (нет размера — нечем ни
                               проверить лимит, ни показать проценты)
  3. размер <= max_upload_bytes -> 413 too_large    (ТЕЛО НЕ ЧИТАЕТСЯ ВООБЩЕ)
  4. имя файла              -> 400 invalid_input
  5. и только теперь тело стримится на диск

Ступень 3 стоит ДО чтения намеренно: иначе гигабайтный файл был бы принят на
диск ровно затем, чтобы его отвергнуть. Инвариант закреплён тестом
an_over_limit_body_is_never_polled — телом запроса там служит поток, считающий
собственные опросы, и счётчик обязан остаться нулевым. Мусорный Content-Length
даёт 400, а не 411: заголовок ЕСТЬ, он просто нечитаем, и «пришли размер» было
бы неверной подсказкой.

Проверки связи (503) на лестнице СОЗНАТЕЛЬНО нет: staging — целиком локальная
операция, а сетевой отказ штатно отдаётся там, где реально идёт сеть, — в
POST /messages. Так короткий сетевой чих не заставляет заново выбирать файл.

КЛЮЧЕВЫЕ ФУНКЦИИ
  router(max_upload_bytes) — лимит тела навешивается ТОЧЕЧНО на этот роут
    (DefaultBodyLimit); глобальный лимит приложения не трогается, иначе любой
    JSON-роут хоста начал бы принимать десятки мегабайт. Слой — вторая линия
    обороны: экстрактор Body тело не лимитирует, поэтому предел проверяется по
    Content-Length до чтения и по счётчику записанных байт во время чтения.
  post_upload(State, HeaderMap, Body) — сама лестница.
  stream_to_file / stream_body — чанк пришёл, чанк записан; буферизации целиком
    в памяти нет ни на одном шаге. sync_all, а не только flush: дальше файл
    читает сборщик base64, и он обязан увидеть все байты, а не хвост в
    страничном кэше.
  percent_decode / sanitize_upload_name / truncate_utf8 — своя реализация вместо
    крейта percent-encoding: любая новая зависимость проходит через гейт дерева
    (cargo tree -i openssl-sys, cargo tree -d). Санитизация: последний сегмент
    пути и по '/', и по '\\'; выброс управляющих символов (в т.ч. CRLF —
    попытка инжекции заголовка); обрезка до 255 байт по границе UTF-8; '.',
    '..' и пустая строка -> "file". None означает «клиент не передал имя» (400),
    а не «подставь заглушку».
  guess_mime — только по расширению и никогда по содержимому. Порталу MIME не
    отправляется вовсе (im.v2.File.upload принимает лишь name и content, тип он
    выводит сам): значение нужно фронту для значка карточки.
  send_staged_file(state, client, dialog_id, upload_id, caption) — вторая
    половина конвейера: take_upload (потребляет) -> begin_portal -> base64 из
    файла -> im.v2.File.upload (БЕЗ ПОВТОРА) -> финальный кадр прогресса ->
    удаление staging. Возвращает messageId портала.
  encode_base64(file, size, reporter) — кодирование кусками по B64_CHUNK
    (48 KiB, КРАТНО ТРЁМ). Некратный кусок дал бы '='-набивку ПОСЕРЕДИНЕ
    строки: портал получил бы битое содержимое, а ошибки на нашей стороне не
    было бы никакой. Тест chunked_base64_matches_whole_file_base64 сверяет
    склейку с кодированием целиком.
  read_full — AsyncReadExt::read вправе вернуть меньше запрошенного в любой
    момент; наивный цикл «прочитал сколько дали — закодировал» разорвал бы
    base64 на некратной трём границе.

ЦЕНА РЕШЕНИЯ Р7 (одношаговая заливка)
base64 живёт в памяти целиком: ~1.33 размера файла плюс столько же на
сериализованное JSON-тело. Именно поэтому дефолтный потолок 25 MiB, а не
платформенные 100 MiB: сотня мегабайт превратилась бы в ~266 МБ пиковой памяти
на ОДНУ отправку. Приём файла при этом RSS не двигает — он потоковый.
