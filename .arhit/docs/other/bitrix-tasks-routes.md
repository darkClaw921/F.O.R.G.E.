# bitrix-tasks-routes

РОУТЫ ЗАДАЧ — plugins/bitrix/src/routes/tasks.rs (Ф10).

| метод | путь | что делает |
|---|---|---|
| GET | /api/bitrix/tasks?filter&start&responsible&group | страница задач (50 записей) |
| GET | /api/bitrix/tasks/counters | ОБА семейства счётчиков |
| GET | /api/bitrix/tasks/:id | карточка БЕЗ select |
| POST | /api/bitrix/tasks/:id/:action | действие по матрице action |

ЛЕСТНИЦА ПРОВЕРОК — та же, что у диалогов: 409 (не подключён) -> 503 (нет связи) -> 404 (нет такой задачи) -> 400 (разбор параметров). Query разбирается ВРУЧНУЮ (query_i64/query_str из dialogs.rs): типизированный экстрактор отработал бы ДО тела хендлера и вернул бы 400 раньше 409, превратив роут в оракул валидности идентификаторов портала.

require_task_id() — ступень 3: неразбираемый или неположительный :id это 404 unknown_task, а не 400. Враждебная строка в текст ответа НЕ попадает: ответ не должен работать рефлектором чужого ввода.

ПРЕСЕТЫ ФИЛЬТРА (FILTERS, замороженные ключи): all | mine | active | expired | closed. Фильтр портала собирается СЕРВЕРОМ (portal_filter): подпускать фронт к сборке означало бы однажды получить пустую директорию из-за псевдополя STATUS. Открытость выражается операторной формой "<REAL_STATUS": 5, закрытость — прямым REAL_STATUS: 5, просрочка добавляет "<DEADLINE": <ISO UTC>. НИ ОДИН пресет не рождает ключ STATUS — есть тест no_preset_ever_produces_the_forbidden_status_key. Уточнения responsible/group ложатся ПОВЕРХ пресета и не отменяют его.

get_tasks: страница платформенная и фиксированная (50), start кратен ей. total берётся из КОНВЕРТА (B24Response::total) — у tasks.task.list он лежит рядом с result, а не внутри. total = None означает «портал числа не прислал» (start:-1 отключает подсчёт) — выдавать за него ноль нельзя. Индекс наполняется бесплатно: строка списка несёт chatId, поэтому после просмотра списка лента задачи открывается без лишнего запроса; матрицы в списке НЕТ, и пустая её не затирает.

get_task: tasks.task.get БЕЗ select (ловушка 2) и БЕЗ im.chat.get — чат берётся из chatId карточки, а его отсутствие это законная ветка Р20, а не повод для второго запроса. «Задачи нет» приезжает от портала УСПЕХОМ с {"result":[]} (проверено живьём на taskId 999999), поэтому B24Client::task_get отдаёт Option, а роут превращает пустоту в 404 unknown_task, а не в 502.

get_task_counters: два независимых семейства одним ответом (TaskCountersResp). Оба берутся из снимков, оставленных фолбэк-воркером, и пока снимки свежи роут не стоит ни одного запроса к порталу.

post_task_action — порядок решений:
1. лестница 409 -> 503 -> 404 (задача) -> 400 (форма имени действия);
2. умеет ли ПАНЕЛЬ (tasks::ACTION_METHODS) — иначе 501 method_unavailable («откройте задачу в Битриксе»);
3. можно ли СЕЙЧАС (матрица action) — иначе 409 invalid_state, причём ПО КЭШУ (TaskIndex), то есть без обращения к порталу. Карточка уже на экране в момент нажатия, значит матрица прочитана; спрашивать её второй раз ради ответа «нельзя» означало бы тратить один из двух запросов в секунду впустую. При промахе индекса карточка читается один раз — единственная ветка, где отказ стоит запроса;
4. вызов семантического метода (имя берётся ИЗ ТАБЛИЦЫ, а не из URL: собирать имя метода из чужой строки означало бы позволить дёрнуть любой метод портала);
5. ПЕРЕЧИТЫВАНИЕ карточки — статус и МАТРИЦА уже другие, собрать новую матрицу локально невозможно;
6. кадр task_update всем вкладкам + инвалидация счётчиков + побудка фолбэк-синхронизации.

Ответ TaskActionResp несёт свежую карточку и dialog_id — по нему фронт перезапрашивает ленту: портал написал в чат задачи системное сообщение о смене статуса (author_id: 0), и ждать его realtime нельзя (событий задач вебхуку не приходит вовсе).

Р20: если после действия чата у карточки всё ещё нет, он добирается вторым путём — im.chat.get {ENTITY_TYPE:"TASKS_TASK"}. Это ЕДИНСТВЕННОЕ место, где метод вызывается: роут карточки его не трогает никогда.

КОЛЛИЗИЯ РОУТОВ: /tasks/counters — статический сегмент рядом с /:id. У matchit статика приоритетнее параметра, но полагаться на это молча нельзя: перепутанный приоритет увёл бы счётчики в разбор идентификатора, тот ответил бы 404 unknown_task, и бейдж просто перестал бы обновляться без единой ошибки. Тест — the_counters_route_is_not_shadowed_by_the_id_route.
